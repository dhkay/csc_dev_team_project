# 04. 식약청 API 연동

**2026-09-06 전면 정정**: 이전 버전은 엔드포인트조차 확인 안 된 추측이었다. 실제로는 2026-09-02에
이미 실호출로 검증되고 21,897건이 동기화까지 끝난 연동이다(`08_개발인계/04_외부API/
식약처_화장품_원료성분정보_API.md`가 원본). 아래는 그 내용을 그대로 옮긴 것이고, 이 문서와
원본이 어긋나면 원본이 맞다(00_개요.md 원칙).

## 1. 기본 정보

| 항목 | 값 |
|---|---|
| 제공 | 식품의약품안전처(공공데이터포털) |
| Base | `https://apis.data.go.kr/1471000/CsmtcsIngdCpntInfoService01` |
| Operation | `getCsmtcsIngdCpntInfoService01` |
| 포맷 | JSON/XML(`type=json` 지정) |
| 전체 건수 | 21,897건(2026-09-02 기준) |
| 인증키 | `08_개발인계/02_서버환경/인증키_대외비.txt`에 실제 값 존재. **절대 이 문서/코드/커밋에
옮겨 적지 않는다**(아래 "인증키 취급" 절) |

```
GET https://apis.data.go.kr/1471000/CsmtcsIngdCpntInfoService01/getCsmtcsIngdCpntInfoService01
    ?serviceKey={URL인코딩된_인증키}
    &pageNo=1
    &numOfRows=1000
    &type=json
```

인증키는 발급 시점에 이미 URL 인코딩된 형태다. 다시 인코딩하면 호출이 실패한다.

## 2. 파라미터와 알려진 함정

| 이름 | 필수 | 설명 |
|---|---|---|
| `serviceKey` | 필수 | 인증키 |
| `pageNo` | 선택 | 페이지 번호(1부터) |
| `numOfRows` | 선택 | 페이지당 건수 |
| `type` | 선택 | `json` 지정 시 JSON, 미지정 시 XML |
| `INGR_KOR_NAME` | 선택 | 한글명 검색. **부분 일치로 동작**(예: `나이아신아마이드` 검색 시 `아이소나이아신아마이드` 포함 10건) |
| `INGR_ENG_NAME` | — | **작동하지 않는다.** 값을 넣어도 무시되고 전체(21,897건)가 그대로 반환된다 |

**영문명(INCI)으로 원료를 찾으려면 API 검색 파라미터를 쓸 수 없다.** 전체를 내려받아
`rbfr_ingredient_dictionary`에 넣어두고, 영문명 검색은 항상 이 로컬 테이블에서 한다(아래
"F-92 사전 동기화" 참고). 이 제약이 애초에 전체 동기화 방식을 채택한 이유다.

## 3. 응답 구조 (필드는 5개뿐)

```json
{
  "header": { "resultCode": "00", "resultMsg": "NORMAL SERVICE." },
  "body": {
    "pageNo": 1,
    "totalCount": 21897,
    "numOfRows": 2,
    "items": [
      {
        "INGR_KOR_NAME": "가공소금",
        "INGR_ENG_NAME": null,
        "CAS_NO": null,
        "ORIGIN_MAJOR_KOR_NAME": null,
        "INGR_SYNONYM": null
      }
    ]
  }
}
```

| 필드 | 내용 | DB 매핑(03번 `rbfr_ingredient_dictionary`) |
|---|---|---|
| `INGR_KOR_NAME` | 한글 표시명칭 | `name_ko` (UNIQUE) |
| `INGR_ENG_NAME` | 영문 표시명칭(INCI) | `name_en` |
| `CAS_NO` | CAS 번호 | `cas_no` |
| `ORIGIN_MAJOR_KOR_NAME` | 기원, 정의 설명 | `origin_desc` |
| `INGR_SYNONYM` | 이명 | `synonym` |

`null`이 흔하다. 위 예시의 `가공소금`도 영문명, CAS가 전부 비어 있다. 다섯 필드 전부 nullable로
다루고, 필수값처럼 검증하지 않는다.

## 4. 이 API로 되는 것과 안 되는 것 (가장 중요한 구분)

이 API는 **성분 표시명칭 사전이지 규제 확인용이 아니다.**

| | 내용 |
|---|---|
| 되는 것 | 한글명으로 조회해 영문명/CAS/기원/이명 채우기, 표시명칭 표준 확인, 전체 사전 동기화 |
| 안 되는 것 | 역할 기여도, 권장 농도, 배합조건, 규제 정보, EWG 등급, 단가 |

- 역할 기여도, 농도, 배합조건은 연구소가 직접 등록한다(`rbfr_ingredient_roles`,
  `rbfr_ingredients`의 농도/pH 등 필드, 03번 참고).
- 사용제한 원료, 국가별 규제(`rbfr_ingredient_regulations`)는 이 API와 무관한 **별도
  데이터셋**이 필요하다. 국가마다 출처가 다르고(05_참고자료/전성분_검토경로.md 참고, 한국은
  대한화장품협회/식약처, 미국은 네거티브 규제 목록, EU는 CosIng 등) 사람이 직접 찾아 확인하는
  경로다. 자동 API로 대체되지 않는다.

## 5. 구현 방향 (기능 정의서 F-90/F-91/F-92)

**구현 위치**: RBFR 도메인의 `adapters/outbound/external/`에 이 연동 어댑터를 둔다.
`core/application/services`는 이 어댑터를 Outbound Port로만 참조하고 실제 호출 방식(REST,
인증키 주입 등)을 모른다. 나중에 API 스펙이 바뀌어도 어댑터만 고치면 된다(그룹웨어 헥사고날
원칙과 일치, 이전 버전에서 이미 맞게 짚었던 부분이라 유지).

### F-92 사전 동기화 (배치, 월 1회)

매 조회마다 외부를 호출하지 않는다. 전체를 받아 `rbfr_ingredient_dictionary`에 upsert하고,
이후 검색(한글명, 영문명 모두)은 전부 이 로컬 테이블에서 한다.

```
numOfRows=1000 으로 22페이지 순회 → upsert(name_ko 기준) → synced_at 갱신
```

- 주기는 월 1회 정도로 충분하다. 표시명칭은 자주 바뀌지 않는다.
- 실패 시 **이전 사전을 그대로 쓴다.** 동기화 실패가 서비스 중단으로 이어지면 안 된다(05번
  "자료 없음은 사용 가능이 아니다"와 같은 종류의 원칙: 오래된 데이터라도 없는 것보다 낫고,
  없는 데이터를 있는 것처럼 보이게 하지 않는다).

### F-90 성분 등록 시 자동 채움

02번 문서 탭3 "성분사전 조회" 버튼이 이 동작이다. 한글명을 입력하면
`rbfr_ingredient_dictionary`에서 찾아 영문명, CAS, 기원을 자동으로 채운다. 사전에 없으면
직접 입력하게 두고 "표시명칭 미확인" 상태로 남긴다(자동으로 지어내지 않는다).

### F-91 표시명칭 검증

이미 등록된 성분(`rbfr_ingredients`)의 명칭이 사전(`rbfr_ingredient_dictionary`)과 다르면
목록에만 표시한다. **자동으로 고치지 않는다.** DATA 권한자가 확인하고 직접 갱신해야 한다.

## 6. 인증키 취급 (반드시 지킬 것)

실제 인증키는 `08_개발인계/02_서버환경/인증키_대외비.txt`에 있고, 그 문서 자체가 명시한
규칙을 그대로 따른다.

- 소스 코드에 넣지 않는다. **서버 `.env`로만 주입**한다(`RBFR_MFDS_API_KEY` 등 환경변수명은
  실제 구현 시점에 그룹웨어 `.env` 관례에 맞춰 정한다).
- 저장소(git)에 커밋하지 않는다.
- 화면, 로그, 오류 메시지에 찍히지 않게 한다(호출 실패 시 키 값을 그대로 로그에 남기는 실수를
  특히 주의).
- 이 파일을 메신저, 메일로 재전달하지 않는다.
- 유출이 의심되면 즉시 알린다.

## 7. 주의

- **호출 한도가 있다.** 공공데이터포털 마이페이지에서 일일 트래픽을 확인한다. 동기화 배치는
  야간에 도는 편이 안전하다.
- 응답이 `resultCode != "00"`이면 `resultMsg`를 로그에 남기고 재시도한다.
- HTTPS 인증서 체인 문제가 나는 환경이 실제로 있었다. 서버의 `ca-certificates`를 최신으로
  유지한다.
