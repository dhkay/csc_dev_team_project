# 01. 연동 구조

**상위 원칙 (가장 먼저 확인)**
- 이 폴더(RBFR 개발지침)는 그룹웨어 저장소(`groupware/.claude/rules/*.md`)의 하위 규칙이다.
  이 문서와 그룹웨어 자체 규칙이 어긋나는 부분이 생기면 **항상 그룹웨어 쪽 규칙이 우선**하고,
  이 문서를 그쪽에 맞춰 고친다. 반대로 이 문서가 그룹웨어 규칙에 없는 걸 새로 정하는 건
  괜찮다(RBFR 고유 결정: 오각형 애니메이션, RBFR 5축 검증 등).
- 신규 기능을 그룹웨어에 넣는 방법 자체(파일 구조/DB 규칙/문서화 규칙)는 이 문서가 아니라
  **`groupware 맞춤 설계용 파일지침.md`**에 기능 공통 규칙으로 정리되어 있다(RBFR 전용이 아니라
  다른 기능 개발자에게도 그대로 전달할 문서라 00~07 번호 체계 밖에 별도 이름으로 둠). 01~07번
  문서는 그 공통 규칙을 RBFR에 적용한 결과물이라고 보면 된다. 다음에 다른 기능(근태관리 등)을
  만들 때도 그 문서를 먼저 따라가면 된다.

**연동 방식 (확정)**
- cscuniverse.com 이 아니라 **그룹웨어(csc groupware) 내부의 신규 메뉴**로 통합한다.
- 그룹웨어 좌측 사이드바에 **"RBFR 연구"** 메뉴 항목을 추가하고, 그 메뉴를 눌러 들어가는 화면 안에서
  정방향 계산/역방향 추천/원료 등록·검증/관리자 대시보드 4개 화면이 모두 동작한다.
- 이유: 그룹웨어의 기존 로그인/세션/조직(organization) 체계를 그대로 재사용할 수 있어, 연구원이
  별도 계정이나 별도 로그인 없이 그룹웨어에 로그인한 상태로 바로 사용 가능.

**스택 (그룹웨어 실제 구조 기준으로 확정)**
- 프론트: `apps/web/groupware` (SvelteKit 5 + Vite + TailwindCSS 4). 신규 기능은 그룹웨어의 기존
  레이어 구조를 그대로 따른다.
  - 화면: `lib/pages/tools/RBFR/RBFRPage.svelte` (+ 하위 `components/`)
  - 데이터: `lib/features/RBFR/` 아래 `apis/`(BFF 호출) → `queries/`·`mutations/`(TanStack Svelte
    Query) → `services/`(조합 로직) 순으로 쌓는다. 컴포넌트는 `services`만 호출한다.
  - 클라이언트 상태: 필요시 `lib/shared/lib/stores/RBFR/`
  - BFF: `routes/api/RBFR/<도메인>/+server.ts` — 브라우저는 이 BFF만 호출하고, BFF가 서비스 토큰을
    붙여 백엔드(csc-groupware)를 호출한다 (그룹웨어의 기존 BFF 패턴과 동일).
- 백엔드: 별도 서버를 새로 만들지 않고, **기존 `apps/api/nestjs/csc-groupware`(NestJS, 헥사고날)에
  새 도메인 `RBFR`을 추가**한다. `domains/RBFR/{core,adapters}` 구조를 그대로 따른다
  (Inbound Port/Service/Outbound Port/Repository Adapter). 정확한 폴더 골격과 네이밍 규칙은
  그룹웨어 `.claude/rules/clean-architecture-structure.md`, `api-architecture.md`를 그대로 따른다
  (이 문서에서 재설명하지 않음).
- DB: 새 DB를 만들지 않고 **groupwaredb(Drizzle ORM, PostgreSQL)에 테이블만 추가**한다.
  실제 스펙(`09_서버앱/db/schema.sql`)을 그대로 옮기되, 다른 도메인과 이름이 겹치지 않도록
  전부 `rbfr_` 접두어를 붙인다(`rbfr_ingredients`, `rbfr_ingredient_roles` 등, 03번 문서가
  테이블 전체 목록의 원본). 마이그레이션 절차(스키마 파일 위치, `drizzle-kit generate` 흐름,
  hash 정책 등)는 그룹웨어 `.claude/rules/database-migration-workflow.md`를 그대로 따른다.
- 백엔드 등록: 새 도메인 모듈은 `apps/api/nestjs/csc-groupware/src/app.module.ts`에 import해서
  등록해야 실제로 동작한다. DB 테이블은 `packages/database/src/groupwaredb/schema/index.ts`(barrel
  export)와 `schema/enums.ts`(신규 enum 값)에도 반영해야 한다.

**권한 (그룹웨어 엔타이틀먼트 체계 + RBFR 고유 5단계 역할, 2026-09-06 정정)**
- 메뉴 자체 노출은 그룹웨어의 기존 기능 접근권 메커니즘인 **`FeatureKey`(userdb `features`/
  `organization_features`)를 그대로 사용**한다. 새 `FeatureKey`(예: `RBFR`)를 하나 추가하고,
  조직 단위로 이 기능을 grant한 뒤 필요한 유저에게만 유저 토글(`organization_user_features`)로
  켠다(`applies_to_all=false`, 조직 전원이 아니라 지정 유저만).
- 메뉴 안에서의 세부 동작 권한은 실제 스펙의 **5단계 역할(ADMIN/REVIEWER/DESIGNER/DATA/VIEWER,
  02번 문서 표 참고)**을 그대로 가져온다. 다만 실제 스펙처럼 RBFR 전용 `users`/`user_roles`
  테이블을 새로 만들지 않고, **ADMIN은 그룹웨어 조직 관리 권한자(루트 권한자 ∨
  `system-management`)로 대체**하고, 나머지 REVIEWER/DESIGNER/DATA/VIEWER만 신규 테이블
  `rbfr_user_roles`(03번 문서)에 저장한다. "설정(Profile 관리)" 화면이 ADMIN 전용인 것도 이
  대체 규칙에서 나온다(조직 관리 권한자만 그 화면에 들어간다).
- 이 엔타이틀먼트 체계 자체(조직/역할/FeatureKey 구조)는 그룹웨어 `.claude/rules/multi-tenancy.md`가
  원본이다. 새 FeatureKey(`RBFR`)는 `packages/entitlements/src/catalog.ts`에 추가하고, 한글 라벨은
  같은 패키지의 `labels.ts`에 추가해야 사이드바에 "RBFR 연구"라는 이름으로 표시된다.

**외부 API 인증키 취급 (신규, 04번 문서 원본)**
- 실제 식약처 API 인증키가 이미 `08_개발인계/02_서버환경/인증키_대외비.txt`에 존재한다(값
  자체는 이 문서에도, 어떤 그룹웨어 문서에도 절대 옮겨 적지 않는다). 그룹웨어로 이식할 때는
  이 값을 그대로 groupwaredb 관련 서버(`csc-groupware`)의 `.env`에 환경변수로만 주입한다.
  코드에 하드코딩하지 않고, 저장소에 커밋하지 않고, 로그/화면/오류 메시지에 찍히지 않게 한다
  (04번 문서 "인증키 취급" 절 참고, 이 규칙은 협상 대상이 아니다).
