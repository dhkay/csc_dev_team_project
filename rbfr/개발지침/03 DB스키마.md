# 03. 원료 DB 스키마

**상위 원칙**: 이 문서는 테이블 컬럼만 정의한다. 마이그레이션 생성/적용 절차, 파일 위치,
hash 정책 등 실행 방법은 전부 그룹웨어 `.claude/rules/database-migration-workflow.md`를 따른다
(여기서 재설명하지 않음). 컬럼명은 groupwaredb의 기존 레거시 테이블처럼 camelCase/snake_case가
섞이지 않도록, **RBFR 신규 테이블은 전부 snake_case로 통일**한다(레거시는 옛 ORM 잔재라 혼재된
것뿐, 새로 만드는 테이블까지 따라할 이유가 없음).

**2026-09-06 실제 스키마 대조 반영 (중요, 이 문서의 기준이 바뀜)**

`09_서버앱/db/schema.sql`(ver2, MariaDB, 34테이블)을 직접 읽고 대조했다. 지금부터 이 문서는
그 스키마를 **PostgreSQL/Drizzle/그룹웨어 관례로 옮긴 번역본**이고, 아래 내용이 실제 스키마와
어긋나면 실제 스키마가 맞다(00_개요.md 원칙). 이전에 `05_참고자료` 분석만으로 추정해서 만들었던
테이블(`ingredient_RBFR_scores`, `ingredient_rdfr_score_attachments` 등, RDFR→RBFR 일괄
치환 스크립트로 어색해진 이름 포함)은 이번 대조로 실제 이름(`ingredient_roles` 등)에 맞춰
전부 다시 정리한다.

## 테이블 접두어: 왜 `rbfr_`을 붙이는가 (실제 스키마와의 유일한 구조적 차이)

실제 ver2는 **RBFR 전용 독립 DB**라 `users`, `profiles`, `formulas`, `projects`, `countries`,
`audit_log`, `app_settings`처럼 짧고 일반적인 이름을 그대로 써도 충돌이 없다. 하지만 그룹웨어는
**groupwaredb 하나를 여러 도메인이 공유**하는 스키마라, 이 이름들을 그대로 가져오면 다른 도메인
테이블(혹은 향후 추가될 도메인)과 충돌하거나 혼동을 준다(`audit_log`, `app_settings`는 특히
그룹웨어 공통 인프라와 이름이 겹칠 가능성이 높다). 그래서 **RBFR 도메인 테이블은 전부 `rbfr_`
접두어를 붙인다.** 이것이 실제 스키마와 이 문서 사이의 유일하게 의도된 이름 차이이고, 컬럼
구성·의미·제약조건은 실제 스키마를 그대로 따른다(표에 별도 표시 없으면 1:1 대응).

## 사용자·권한: 실제 스키마의 `users`/`user_roles`를 그대로 옮기지 않는다

실제 스키마의 `users`(로그인 계정, 세션 판번호, 실패 잠금 등)와 `user_roles`(ADMIN/DESIGNER/
DATA/VIEWER)는 **RBFR가 독립 앱일 때 자체 로그인 시스템이 필요해서 만든 테이블**이다. 01번
문서에서 이미 결정한 대로, 그룹웨어에 통합되는 RBFR은 **그룹웨어의 기존 계정/조직 체계
(`organization_users`, userdb)를 그대로 재사용**하고 별도 로그인 테이블을 만들지 않는다. 대신:

- **`rbfr_user_roles`** (신규, 실제 스키마 `user_roles`의 역할 개념만 이식): `user_id`(groupware
  `organization_users.id` 값을 그대로 저장하되, **DB가 다르므로 FK는 걸지 않는다**, 크로스 DB
  금지 원칙), `role_code`(REVIEWER/DESIGNER/DATA/VIEWER, snake_case pgEnum), `granted_at`,
  `granted_by`. **ADMIN은 이 테이블에 넣지 않는다** — 02번 문서대로 그룹웨어의 조직 관리
  권한자(루트 권한자 또는 `system-management`)가 곧 RBFR의 ADMIN이므로, userdb 권한 판정을
  그대로 재사용하고 중복 저장하지 않는다.
- 실제 스키마의 `session_epoch`/`fail_count`/`last_fail_at`(자체 로그인 잠금)은 그룹웨어 `user`
  서버가 이미 처리하는 영역이라 이식하지 않는다.

## Profile/역할 도메인/코드 테이블 (실제 스키마 1:1, 접두어만 추가)

| 실제 스키마 | 그룹웨어 테이블명 | 비고 |
|---|---|---|
| `profiles` | `rbfr_profiles` | `profile_code`(PK), `profile_type`(PRIMARY/CROSS), `is_active`. 지금은 스킨(Skin) 하나만 `is_active=1` |
| `role_domains` | `rbfr_role_domains` | `domain_code`(PK), `profile_code`(FK), `domain_type`(DIRECT/INTEGRATED), `sort_order`. 이름·순서 미확정(보습/진정/보호/정돈/균형은 잠정값) |

02번 문서의 "설정(Profile 관리)" 화면이 다루는 대상이 바로 `rbfr_profiles`/`rbfr_role_domains`

## 처방(Formula) 테이블 (실제 스키마 1:1, 접두어만 추가)

실제 스키마는 **2계층**이다: `projects`(제품 개발 단위) 아래 여러 `formulas`(시안)가 달린다.
우리가 이전에 만든 단일 `formulas` 설계보다 한 계층 더 깊다. 이 구조를 그대로 가져온다.

| 실제 스키마 | 그룹웨어 테이블명 | 비고 |
|---|---|---|
| `projects` | `rbfr_projects` | 제품 개발 단위(그룹). `owner_id`(organization_users.id, FK 없음) |
| `formulas` | `rbfr_formulas` | 처방 시안 1건. `lab_no`(랩 넘버, 확정할 때 부여), `status`(DRAFT/CALC/REVIEW/FIXED/ARCHIVED) |
| `formula_conditions` | `rbfr_formula_conditions` | 설계 조건 본체(배치량, 목표 단가, 목표 pH 범위) |
| `formula_condition_codes` | `rbfr_formula_condition_codes` | 복수 선택 조건(FUNC/TEXTURE/CERT/NOADD) |
| `formula_countries` | `rbfr_formula_countries` | 이 처방이 점검할 수출 대상국 |
| `formula_ratios` | `rbfr_formula_ratios` | 역할별 목표 비중(%)과 `cell_count`(0~5). 통합역할은 `evidence` 없이 채우지 않는다(05번 원칙5) |
| `formula_ingredients` | `rbfr_formula_ingredients` | 선정 성분. `is_pinned`/`pinned_pct`로 고가 원료 배합량 고정 |

**랩 넘버(`lab_no`) 채번 규칙은 미확정**이다(실제 스펙의 "아직 정해지지 않은 것" 목록에도 있음).
사내 규칙이 정해지기 전까지는 `FIXED` 전환 시 관리자가 수동 입력하는 것으로 임시 처리한다.

## 공통 (2026-09-06 확정 — 그룹웨어 실제 구조 확인 완료)

`groupware/packages/database/src/groupwaredb/schema/`를 직접 검색해 확인한 결과, **그룹웨어에는
범용 `audit_log`/`app_settings` 테이블이 없다.** 대신 도메인마다 자기 설정 테이블을 따로 두는
관례만 있다(예: `organizationAssistantSettings`). 또한 csc-groupware는 아직 중앙 로그 서버
(log-server)를 호출하지 않는다. 즉 재사용할 공용 인프라 자체가 없으므로, 재사용 여부를 더
따질 필요 없이 **RBFR 전용 테이블을 그대로 만든다.**

| 실제 스키마 | 그룹웨어 테이블명 | 비고 |
|---|---|---|
| `audit_log` | `rbfr_audit_log` | RBFR 도메인 전용 감사 기록. `action`(LOGIN/ING_UPDATE/PROJECT_FIX/EXPORT 등), `target`, `detail`, `ip` |
| `app_settings` | `rbfr_app_settings` | RBFR 전용 설정(고가 판정 기준액, 기본 Cell 규칙 버전 등). `setting_key`(PK)/`setting_val`/`descr` |

(향후 그룹웨어에 중앙 로그 서버(log-server) 연동이 도입되면, `rbfr_audit_log`의 행 단위 기록을
그쪽으로 이관하는 건 별도 마이그레이션 작업이지 지금 2단계 결정을 바꾸는 사유는 아니다.)

## pgEnum 매핑 (MariaDB VARCHAR 코멘트 표기 → PostgreSQL pgEnum)

실제 스키마는 MariaDB라 "enum 값 목록"을 컬럼 코멘트로만 적어두고 타입은 `VARCHAR`다.
PostgreSQL/Drizzle로 옮길 때는 05번 원칙2("규칙 숫자를 코드에 박지 않는다")에 어긋나지 않는
범위에서, **값 집합이 사실상 고정된 것만** pgEnum으로 만든다(값 집합 자체가 아직 유동적인
`code_items`류는 계속 테이블로 남긴다).

| pgEnum 이름 | 값 | 어느 컬럼 |
|---|---|---|
| `rbfr_domain_type_enum` | DIRECT, INTEGRATED | `rbfr_role_domains.domain_type` |
| `rbfr_profile_type_enum` | PRIMARY, CROSS | `rbfr_profiles.profile_type` |
| `rbfr_reg_type_enum` | ALLOW, BAN, LIMIT, COND, NODATA | `rbfr_ingredient_regulations.reg_type` |
| `rbfr_confirm_status_enum` | CONFIRMED, PROPOSED, REJECTED | `rbfr_ingredient_regulations.status` |
| `rbfr_incompat_severity_enum` | BLOCK, WARN | `rbfr_ingredient_incompat.severity` |
| `rbfr_formula_status_enum` | DRAFT, CALC, REVIEW, FIXED, ARCHIVED | `rbfr_formulas.status` |
| `rbfr_review_status_enum` | PENDING, REVIEWING, APPROVED, CHANGES, REJECTED | `rbfr_formula_reviews.status` |
| `rbfr_user_role_enum` | REVIEWER, DESIGNER, DATA, VIEWER | `rbfr_user_roles.role_code`(ADMIN 제외, 위 설명 참고) |
| `rbfr_fill_direction_enum` | CCW, CW | `rbfr_cell_rule_limits.fill_direction` |
| `rbfr_tox_status_enum` | NONE, LISTED, UNKNOWN | `rbfr_ingredient_tox.status` |
| `rbfr_interaction_type_enum` | synergy, conflict, neutral, unknown | `rbfr_ingredient_interactions.interaction_type` |
| `rbfr_data_source_enum` | manual_estimate, lab_test, literature, expert_review, unknown | `rbfr_ingredient_interactions.data_source`, `rbfr_formula_sensory_stability_records.data_source` |
| `rbfr_confidence_level_enum` | low, medium, high | `rbfr_ingredient_interactions.confidence_level`, `rbfr_formula_sensory_stability_records.confidence_level` |
| `rbfr_risk_level_enum` | 상, 중, 하 | `rbfr_formula_sensory_stability_records`의 4개 위험도 필드 |

## 실제 스펙에 없는 우리 쪽 확장 테이블 (2026-09-06 채택 확정)

`05_참고자료` 벤치마크 분석 과정에서 제안했던 아래 두 테이블은 **실제 ver2 스키마(schema.sql)
어디에도 없다.** 원본 설계팀이 검토했지만 채택하지 않았거나 아직 다루지 않은 영역이라는 뜻이라,
2단계 데이터 모델 확정 시점에 **지금 바로 포함하기로 확정**했다(사용자 확인). 00번 문서 원칙상
"실제 스펙과 어긋나면 실제 스펙이 맞다"는 이 둘에는 해당하지 않는다 — 어긋나는 게 아니라
원본에 없던 걸 더하는 것이기 때문이다. 실제 연구소 데이터가 쌓이기 전까지는 두 테이블 모두
빈 상태로 시작하고, 실측 데이터가 쌓이는 대로 검증한다.

**`rbfr_ingredient_interactions`** (원료쌍 시너지/충돌 계수)

`rbfr_ingredient_incompat`는 BLOCK/WARN 이분법만 제공해 "같이 쓰면 10% 상승/감소" 같은
정도차를 표현하지 못한다. 이 테이블이 그 정도차를 담는다. **이론 계산이 아니라 실측/평가로
채워지는 테이블**이다(05번 원칙6 "무작위를 쓰지 않는다"와 별개로, 계수 자체를 공식이 지어내지
않는다는 원칙).

| 필드 | 타입 | 설명 |
|---|---|---|
| id | PK | 조합 고유 ID |
| ingredient_a_id / ingredient_b_id | FK(`rbfr_ingredients`) | **정규화 규칙**: 항상 `ingredient_a_id < ingredient_b_id`로 저장해 (A,B)/(B,A) 중복 행을 막는다 |
| domain_code | FK(`rbfr_role_domains`) | 이 조합이 영향을 주는 역할 도메인 |
| interaction_type | `rbfr_interaction_type_enum` | synergy(상승) / conflict(충돌) / neutral(무관) / unknown(미측정) |
| coefficient | decimal | 1.0=변화 없음, 1.1=10% 상승, 0.9=10% 감소, 0=사용 불가. 기본값 1.0 |
| confidence_level | `rbfr_confidence_level_enum` | low / medium / high |
| data_source | `rbfr_data_source_enum` | manual_estimate / lab_test / literature / expert_review / unknown |
| measured_at | timestamp | 측정/평가 일시 |
| notes | text | 비고 |

**`rbfr_formula_sensory_stability_records`** (처방 사용감·안정성 실측 기록)

완성된 처방(`rbfr_formulas`) 단위로 실측해야 하는 값이라 원료 테이블과 분리한다. 계산 결과가
아니라 실험/관능평가 기록이다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | PK | 기록 고유 ID |
| formula_id | FK(`rbfr_formulas`) | 대상 처방 |
| stickiness_score / freshness_score / absorption_score / spreadability_score / afterfeel_score / viscosity_score | smallint | 사용감 항목별 점수(척도는 추후 확정, 확인 필요) |
| separation_risk / precipitation_risk / color_change_risk / odor_change_risk | `rbfr_risk_level_enum`(상/중/하) | 안정성 리스크 항목 |
| ph_stability_score / heat_stability_score / low_temp_stability_score / overall_stability_score | smallint | 조건별 안정성 점수 |
| test_condition | text | 실험 조건(온도/기간 등) |
| data_source | `rbfr_data_source_enum` | 위 `rbfr_ingredient_interactions`와 동일 값 집합 |
| confidence_level | `rbfr_confidence_level_enum` | low / medium / high |
| notes | text | 비고 |
| created_by / created_at | integer/timestamp | 기록한 사람(organization_users.id, FK 없음)/시각 |

두 테이블 모두 **`data_source`가 `lab_test`가 아니면 실측값과 다른 배지("예측값"/"미측정")로
구분 표시**하는 원칙(05번 "AI 추론 데이터 폴백"과 동일한 원칙)을 그대로 적용한다.

## 2단계(데이터 모델 확정) 완료 요약

이 문서 기준으로 RBFR 도메인의 최종 테이블 수는 **36개**다(2026-09-06 실제 마이그레이션 적용
시점에 재확인, 이전 요약의 "34개"는 집계 오류였다): 실제 스키마 1:1 이식 32개
(`rbfr_profiles`~`rbfr_version_ratios`, `rbfr_user_roles` 포함), 신규 보완 1개
(`rbfr_ingredient_role_evidence_files`), 확정 채택된 확장 2개(`rbfr_ingredient_interactions`,
`rbfr_formula_sensory_stability_records`), 공통 인프라 2개(`rbfr_audit_log`,
`rbfr_app_settings`) 세 갈래를 합친 것이다. 남은 미확정 항목(랩 넘버 채번 규칙 등)은
"확인 필요"로 `develop_status.md`에 남아 있으나, 스키마 구조 자체를 바꾸는 항목은 아니라서
2단계 완료를 막지 않는다. 이 문서를 실제 Drizzle 스키마 파일로 옮기는 작업은 5단계
(DB 저장/조회 구현)에서 진행한다.

## 테스트/시드 데이터 정책 (유지)

- 개발/QA 단계에서 넣는 테스트용 원료는 반드시 `TEST-001`처럼 실제 원료명이 아닌 명확한
  샘플명으로 등록한다.
- 이때도 `rbfr_ingredient_regulations.status='PROPOSED'`, `found_by='ai:test'`처럼 실제
  데이터와 혼동되지 않는 값으로 채운다.
- 실제 원료명으로 임의 추정치를 넣어두는 것은 금지한다(연구팀이 실사용 데이터로 착각할 위험).
