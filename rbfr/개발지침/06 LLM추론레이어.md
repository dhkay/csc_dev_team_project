# 06. LLM 추론 레이어

00_개요.md에 문서 목록으로만 이름이 있고 실제 내용이 없던 문서. 아래 내용으로 신규 작성한다.

**역할 경계 (가장 중요한 원칙)**
- LLM은 계산을 하지 않는다. 05_스코어링엔진.md의 원칙대로 "수치 계산은 항상 엔진(코드)이 담당,
  LLM은 계산 결과 해석에만 사용"을 그대로 따른다.
- LLM에게 원료의 RBFR 5축 수치나 배합비율 계산을 다시 시켜서 그 결과를 화면에 쓰지 않는다. LLM이
  내놓는 숫자는 절대 신뢰하지 않고, 화면에 보여줄 모든 수치는 엔진이 계산한 값만 사용한다.

**입력 (LLM에게 무엇을 주는가)**
- 탭1(정방향): 선택된 원료 목록(이름, 배합비율%), 엔진이 계산한 최종 RBFR 5축 점수, 각 원료의
  식약청 등급(mfds_grade)
- 탭2(역방향): 사용자가 슬라이더로 입력한 목표 5축 벡터, 엔진이 유사도 계산으로 뽑은 추천 원료
  후보 목록(이름, 근접도, RBFR 5축 값)
- 공통: 원료명/수치/등급 등 프롬프트에 들어가는 값은 전부 엔진이 DB에서 조회한 값을 그대로 문자열로
  치환한 것이지, LLM이 추측해서 채우는 값이 아니다.

**출력 형식**
- 탭1 해석 텍스트: 어느 축이 낮은지/높은지, 그 이유를 원료 성분과 연결해 1~3문장으로 설명. 예:
  "정화 수치가 낮음, 정화 원료 보강 팁" 같은 짧은 조언 카드 1개 + 상세 설명 텍스트.
- 탭2 후보별 설명: 왜 이 원료가 추천됐는지(어느 축이 목표에 가까운지), 대체 가능한 원료가 있다면
  같이 언급. 후보 1개당 짧은 설명 1~2문장.
- 출력은 항상 구조화된 형식(JSON)으로 받아 화면에서 파싱한다. 자유 텍스트를 그대로 렌더링하지
  않는다 (예상치 못한 형식이 섞여 화면이 깨지는 것을 방지).

**구현 위치(그룹웨어 규칙 정렬)**: language-model 서버 호출 코드는 서버 간 HTTP 호출 패턴을 따라
`shared/adapters/outbound/language-model-api/`에 타깃별 클라이언트(`NestServiceClient` 상속)를
두고, RBFR 도메인의 Outbound Port 구현 어댑터는 그 클라이언트를 주입받아서만 호출한다(원본:
`api-architecture.md` §2.8 "서버 간 HTTP 클라이언트"). 직접 axios/fetch를 새로 만들지 않는다.

**모델/인프라 (그룹웨어 기존 AI 인프라 재사용, 추가)**
- 그룹웨어에는 이미 AI 어시스턴트용 `language-model`(FastAPI) 서버와, 조직별 모델 설정
  (`organization_assistant_settings`) 체계가 있다. RBFR의 해석 텍스트 생성도 이 인프라를 그대로
  재사용하고, 별도 LLM 서버를 새로 만들지 않는다.
- csc-groupware(NestJS, RBFR 도메인)가 language-model 서버를 서버 간 호출(HTTP + 서비스 토큰)로
  호출해 해석 텍스트를 받아온다. 브라우저가 language-model을 직접 호출하지 않는다(BFF 원칙 동일).
- 기본 모델은 조직 설정의 기본 모델(미설정 시 내장 Qwen)을 따르되, RBFR 전용 system prompt(위 "역할
  경계" 원칙을 명시하는 문구)를 덧붙인다.

**오류/할루시네이션 방지**
- LLM 응답이 기대한 JSON 형식이 아니거나 타임아웃이면, 해석 텍스트 자리에 "AI 해석을 불러오지
  못했습니다"만 표시하고 나머지 화면(오각형 차트, 등급 배지, 추천 리스트)은 정상 노출한다. LLM
  실패가 전체 화면을 막지 않는다.
- LLM이 프롬프트에 없는 원료명이나 수치를 답변에 만들어내는 경우를 대비해, 응답에서 원료명이
  언급되면 그 이름이 실제 입력 목록에 있었는지 검사하고 없으면 그 문장은 버린다(화면에 노출 안 함).

**확인 필요**
- 조직별 프롬프트/모델 커스터마이징이 RBFR 기능에도 필요한지, 아니면 RBFR은 항상 고정 프롬프트를
  쓸지는 미확정. 정책 확정 전까지는 고정 프롬프트(위 "역할 경계" 문구 고정)로 시작한다.
