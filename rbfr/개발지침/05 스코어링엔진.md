# 05. RBFR 역할 비중 산출 로직

**상위 원칙 (2026-09-06 전면 정정)**: 이 문서의 계산 로직은 새로 발명하는 게 아니라
`08_개발인계/00_인계안내.md`에 이미 정리된 "개발 시 반드시 지켜야 할 규칙"과
`09_서버앱/README.md`의 "절대 바꾸지 말 것" 9가지를 그룹웨어 구조로 옮기는 것이다.
아래 원칙과 이 문서 하단의 계산식이 어긋나면 원칙이 맞다.

## 절대 원칙 9가지 (원본 그대로, 최우선)

1. **재현성** — 같은 입력이면 항상 같은 결과. 성분값은 DB에서만 가져온다. AI가 만든 값을
   산출에 바로 쓰지 않는다.
2. **규칙 숫자를 코드에 박지 않는다** — Cell 변환표, 총합 범위 등은 표(`cell_mapping`,
   `cell_rule_limits`)에서 읽는다.
3. **조건 우선순위** — 규제 > 무첨가 > 인증 > 고정값 > 역할 적합도. 이 순서로 성분을 걸러낸다.
4. **자료 없음(NODATA)은 사용 가능(ALLOW)이 아니다** — 반드시 구분 표시.
5. **통합 역할은 남는 비중·평균·총량 채우기로 채우지 않는다** — 독립적인 근거가 있을 때만
   값이 들어간다 (아래 "직접 역할 vs 통합 역할" 참고).
6. **무작위를 쓰지 않는다** — 같은 입력이면 같은 결과.
7. **확정 후 불변** — 확정된 산출값은 수정하지 않는다. 새 버전(스냅샷)을 만든다.
8. **성분마다 정해진 농도 범위를 넘지 않는다.**
9. **산출은 서버에서만 한다** — 화면에서 계산해 값을 보내는 방식을 쓰지 않는다. 그룹웨어
   구조에서는 "계산 로직은 `core/application/services`에만 있고 프론트는 결과만 받는다"는
   뜻이다(그룹웨어 헥사고날 원칙과 정확히 일치).

## 역할 도메인 — 직접 역할 vs 통합 역할 (중요, 이전 설계 정정)

스킨(Skin) Profile 잠정값은 **보습·진정·보호·정돈·균형** 5개, 이 중 **균형만 통합 역할**이고
나머지 4개는 직접 역할이다. **4개 직접 + 1개 통합 구조 자체는 특허 청구항에 나오는 확정
사항**이라 개수·구조는 안 바뀐다(이름·순서는 잠정, 확인 필요 — `09_서버앱/db/seed.sql` 참고).

- **직접 역할(DIRECT)**: 아래 "직접 역할 계산식"으로 산출한다.
- **통합 역할(INTEGRATED, 균형)**: 아래 계산식을 그대로 적용하면 안 된다. 남는 비중이나
  나머지 4개의 평균으로 채우는 걸 명시적으로 금지한다. 반드시 별도의 **독립 근거**(연구원이
  입력한 근거 텍스트/데이터)가 있어야 값이 들어가고, 근거가 없으면 그 처방의 균형 값은
  **미입력 상태로 남는다**(0이나 평균으로 자동 채우지 않는다).
  - **확인 필요**: 통합 역할의 정확한 산출 방식은 원본에서도 미확정(③)으로 남아 있다.
    그룹웨어 포팅 시에도 같이 확인해야 한다.

## 직접 역할 계산식 (이전 "정방향 계산"을 대체)

```
직접 역할 효능값 =
  Σ(원료별 그 역할 기여도 × 실제 배합비) × 유효농도계수 × 안정성계수 × 조합계수
```

- **1단계(기본 효능값)**: `Σ(원료별 기여도 × 배합비/100)`. 원료를 추가해도 기존 원료의
  기여분은 줄지 않고 새 원료의 기여분이 더해질 뿐이다(가산 방식, 비율로 나눠 평균내지 않음 —
  화장품 유효성분 배합의 일반 원리와 일치. 실제로 화면에서 이 오류를 발견해 수정함).
- **2단계(조합계수)**: `ingredient_interactions`에서 이 처방에 실제로 같이 들어간 원료 쌍 중
  이 역할에 해당하는 행을 조회, 계수를 전부 곱한다. 데이터 없으면 1.0.
  - **확인 필요**: 원료 3개 이상일 때 여러 쌍의 계수를 전부 곱할지, 다른 합성 규칙(최댓값만
    반영 등)이 맞는지는 실측 데이터가 쌓인 뒤 재검토한다. 지금은 "전부 곱하기"를 기본값으로 시작.
- **3단계(유효농도계수)**: 배합비가 원료의 권장 최소치보다 낮으면 1.0 미만으로 감쇠(구체 감쇠
  곡선은 확인 필요, 우선은 선형 감쇠).
- **4단계(안정성계수)**: 처방의 실측 안정성 기록이 있으면 반영, 없으면 1.0.
- 캡: 각 역할 값은 0~100으로 clamp(배합비 합계가 100% 이내면 이론상 넘지 않음, 방어적 안전장치).
- **중요 원칙**: 2~4단계 보정계수는 전부 실험/평가로 저장된 값을 곱하는 것이지, 계수 자체를
  공식이나 AI가 새로 만들어내지 않는다. 화면에는 "보정 반영됨(실측)" / "보정 없음(미측정)"을
  구분 표시한다.

## 비중값 계산

```
역할별 비중값 = 그 역할의 효능값 ÷ (5개 역할 효능값 전체 합)
```

효능값(절대 강도)과 비중값(상대 비율)은 다른 값이다. "진정 90"과 "진정 비중 37.5%"는 서로
다른 정보이며 항상 같이 표시하되 합치지 않는다. 이 계산은 위 "직접 역할 효능값"이 다 끝난
뒤에만 수행한다 — 이미 확정된 결과값들끼리 사후 비교하는 것이지, 원료 기여도 자체를 비율로
희석하는 게 아니다(위에서 폐기한 가중평균 방식과는 다른 것).

## Cell(칸)·오각형 — 공식 표현 방식 (신규 반영, 중요)

**비중(%) 값 자체가 화면·승인·RBDR 전달의 최종 단위가 아니다.** 실제 시스템은 비중(%)을
**Cell(칸) 수**로 변환해서 오각형에 표시하고, 그 칸 수 합계로 승인 여부를 가른다. 그룹웨어
포팅 시에도 이 변환 단계를 생략하면 안 된다.

- 역할마다 오각형 하나, 오각형 하나는 5칸.
- 지정된 시작 칸에서 **시계 반대 방향(CCW)**으로 채운다. 건너뛰지 않는다.
- **비중(%) → 칸 수 변환표**(`cell_mapping`, 구간은 "이상~미만")로 변환한다. 코드에 박지 않고
  화면(관리 > Cell 규칙)에서 승인한다.
- **다섯 오각형의 채운 칸 합계는 15 이상 18 이하**여야 한다(기준선 = 역할 수 × 3칸 = 15).
- 이 범위·변환표는 **규칙 판(rule_version)** 단위로 관리되고, 승인자·승인일자가 남는다.
  승인된 판은 화면에서 못 고치고, 바꾸려면 새 판을 만든다.
- **02_화면구성.md 정정**: 앞서 만든 "부드럽게 애니메이션되는 연속값 오각형"은 사용자가 배합비를
  조정하는 동안의 실시간 프리뷰로는 유지해도 되지만, **승인·확정·RBDR 전달용 공식 표현은 반드시
  이 이산 Cell 변환을 거친 값**이어야 한다. 연속값 애니메이션이 Cell 변환을 대체하지 않는다.

## HLB 계산 (유화 설계, 신규 반영)

```
Required HLB = Σ(HLBi × %i) / Σ(%i)      (유상부 내 상대 비율로 정규화)
혼합 HLB     = (HLB_A × A% + HLB_B × B%) / 100
판정         = |Required − 혼합| 가 허용치를 넘으면 유화 불안정 경고
```

이 계산도 원료의 `hlb`, `emulsion_role` 값이 있어야 가능하다(03_DB스키마.md 참고). 값이 없는
원료가 섞인 처방은 HLB 판정을 "미확인"으로 표시하고 경고를 막지 않는다(원칙 4).

## AI 추론 데이터 폴백

"AI는 찾아오기만 하고 확정은 사람이 한다"는 사상은 `08_개발인계/00_인계안내.md`의 설계 의도와
정확히 일치함을 확인했다. 상태값 이름도 실제 시스템과 맞춘다: `CONFIRMED`(사람 확정, 산출·검증에
사용) / `PROPOSED`(AI 제안, 표시만 하고 산출에 미사용) / `REJECTED`(확인해보니 아님, 재상정
방지용 기록).

- **토글**: 화면에 "AI 추론 데이터 사용" on/off. 기본 OFF.
- **트리거**: 계산에 포함하려는 원료 중 `CONFIRMED` 데이터가 하나도 없는 경우.
  - OFF: 그 원료 제외, "확정 데이터 없음"만 표시.
  - ON: LLM에게 역할 기여도(직접 역할 4개에 한함 — 통합 역할은 AI 추론 대상 아님, 원칙 5)
    추정치를 요청, `PROPOSED` 상태로 저장 후 계산에 포함, 화면에 "AI 추론 데이터" 배지 필수 표시.
- 저장된 `PROPOSED` 값은 재추론하지 않고 캐시처럼 재사용, 사람이 검토해 `CONFIRMED`로 바꾸면
  그 순간부터 일반 데이터와 동일 취급.

## 처방 검증 로직 (원칙 3 순서 반영, 정정)

1. 배합비 합계 100% 확인
2. **조건 우선순위 순서로 필터링**: 규제(REG_TYPE=BAN/LIMIT/NODATA 확인) → 무첨가 조건 →
   인증 조건 → 고정값(배합량 고정 성분 우선 보존) → 역할 적합도. 이 순서를 바꾸지 않는다.
3. pH 충돌 확인
4. `ingredient_incompat`(병용 금기) 확인 — `BLOCK`이면 확정 자체를 막고, `WARN`이면 경고만
5. 조합계수(시너지/충돌) 조회, 없으면 1.0
6. HLB 판정(유상부 있는 경우)
7. 사용감·안정성 실측 기록 반영(있는 경우만)
8. 실측값/AI 제안값/미확인값을 결과 화면에서 항상 구분 표시
9. 원가 = Σ 배합비 × 원료 단가

## 그룹웨어 구조 반영 (기존 유지)

이 계산 로직은 rbfr 도메인의 `core/application/services`에 둔다. NestJS 데코레이터나 Drizzle
ORM을 이 파일에서 직접 import하지 않는다(core는 프레임워크를 모른다는 그룹웨어 헥사고날 원칙).
원료 데이터는 Outbound Port를 통해서만 받아온다 — 그래야 이 계산 로직만 떼어서 프레임워크 없이
단위 테스트할 수 있다.
