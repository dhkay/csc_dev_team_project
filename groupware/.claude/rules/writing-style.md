# 텍스트 스타일 가이드

프로젝트 내 모든 산출물의 텍스트에 적용한다. 코드 주석, UI 문구(라벨/버튼/안내문), 커밋 메시지,
PR 본문, 문서(`docs/`, `.claude/rules/`) 모두 포함한다.

두 가지가 이 문서의 뼈대다.

**주석은 지울 수 있는지 먼저 본다. 판별은 한 문장으로 한다. 이 주석을 지우면 다음 사람이 무엇을
잘못하는가.** 답이 나오지 않으면 지운다. 뒤의 주석 규칙 대부분이 여기서 따라 나온다.

**문장 구조는 마침표, 쉼표, 괄호, 콜론으로 표현한다.** 그래서 대시와 가운뎃점을 쓰지 않는다.
같은 이유로 이모지도 쓰지 않는다. 의미를 색과 그림에 실으면 흑백 출력, 스크린리더, 폰트가 없는
터미널에서 그 의미가 사라지고 `grep` 으로 찾을 수도 없다.

## 문체: 글의 용도가 정한다

| 문체 | 예시 | 쓰는 곳 |
|------|------|--------|
| 한다체 | 사용한다, 호출한다, 없다 | 설명문, 규칙, 설계 문서, 커밋 본문의 배경 문장, PR 본문의 서술 |
| 개조식 | 사용, 호출, 없음, 방지, 도입함 | 나열, 이름표, 표의 칸, 짧은 메모, 커밋 제목과 본문의 변경 항목 |

**코드 주석은 둘 다 쓴다.** 어느 쪽인지는 그 주석의 모양이 정한다. 사실 하나를 서술하면 한다체,
항목을 늘어놓거나 이름표를 붙이면 개조식이다(아래 "코드 주석" 절).

**하나의 주석 단위에서는 섞지 않는다.** 금지 대상은 한 문장 안의 혼용이다.

```ts
// 섞은 것:   응답이 불안정해서 재시도하지 않는다. 재시도 횟수 3회, timeout 5초
// 가른 것:   응답이 불안정해서 재시도하지 않는다.
//            재시도 횟수 3회, timeout 5초
```

한 블록 안에서 문장형 설명 뒤에 개조식 목록이 오는 것은 정상이고 읽기도 쉽다.

```ts
/**
 * 요청을 검증하고 데이터를 생성한다.
 *
 * 검증 대상:
 * - 권한
 * - 중복 요청
 * - 필수 필드
 */
```

**커밋 제목과 본문의 변경 항목은 개조식이다.** 제목은 `type(scope): ` 뒤에 무엇이 바뀌었는지를
명사형(`~도입`, `~제거`, `~함`)으로 끝내고 마침표를 붙이지 않는다. 본문은 배경을 한다체 문장
한두 개로 적은 뒤 변경 항목을 한 줄씩 개조식으로 나열한다. 변경이 여럿이면 묶음마다 소제목 한
줄을 두고 그 아래에 항목을 놓는다. `git log --oneline` 은 제목만 보이므로 제목이 문장이면 목록이
아니라 문단으로 읽힌다.

```
feat(marketing): v1.5 기획 앞 Sonnet 입력 정제 단계 도입

자유 서술 입력을 기획 LLM 이 매번 다르게 해석해 결과가 흔들렸다.

- 파이프라인 표에 briefRefinerLlm 추가(v1.5 = claude-sonnet-5)
- 정제 실패 시 원문으로 진행하지 않고 중단
```

### 한다체

`-한다` / `-이다` / `-없다` 로 끝낸다. `-합니다` / `-입니다` / `-없습니다` 를 쓰지 않는다.

| 합니다체 | 한다체 |
|---------|-------|
| 사용합니다 / 호출합니다 | 사용한다 / 호출한다 |
| 있습니다 / 없습니다 | 있다 / 없다 |
| 쓰지 않습니다 / 어렵지 않습니다 | 쓰지 않는다 / 어렵지 않다 |
| 게이트키퍼입니다 (받침 없음) | 게이트키퍼다 |
| 단일 진실원입니다 (받침 있음) | 단일 진실원이다 |

예외로 그대로 두는 것: 화면에 실제로 나가는 UI 문구를 인용한 자리(`'준비중입니다'`), 예제 코드
블록 안의 문자열, README 등 외부 독자용 안내문.

### 개조식

명사로 끝내고 마침표를 붙이지 않는다. 항목은 쉼표로 잇고, 근거를 붙여야 하면 `~때문`,
`~하기 위함`, `~방지` 처럼 명사형으로 끝낸다.

| 서술형 | 개조식 |
|-------|-------|
| 커스텀 key 인지 판정한다. 기본 축 key 사칭을 막는다. | 커스텀 key 여부 판정, 기본 축 key 사칭 방지 |
| 이름이 바뀌어도 유지되는 값이라 기존 선택을 보존한다. | 이름이 바뀌어도 유지되는 값이라 기존 선택 보존 |
| 조직 로고의 원본 uploadId 이며 제출과 폼 baseline 에 쓴다. | 조직 로고 원본 uploadId(제출/폼 baseline 용) |

## 어투: 사실을 적는다

- **1인칭을 쓰지 않는다.** "우리는 A를 쓴다" 대신 "A를 쓴다".
- **권유형을 쓰지 않는다.** "~해 보자", "~하세요" 대신 "~한다", "~하지 않는다".
- **느낌표를 쓰지 않는다.** 강조가 필요하면 `**` 를, 그것도 오해하면 사고가 나는 곳에만.
- **의문형으로 절 제목을 달지 않는다.** "왜 분리했는가?" 대신 "분리한 이유".

## 코드 주석

주석은 공짜가 아니다. 한 줄마다 유지할 대상이 하나 늘고, 코드가 바뀔 때 먼저 낡는 쪽은 언제나
주석이다. 낡은 주석은 없느니만 못하다. 틀린 근거를 확신을 갖고 주장하기 때문이다.

그래서 순서가 있다. **지울 수 있는지 먼저 보고, 남길 것만 어디에 어떤 형태로 쓸지 정한다.**

### 1. 기본값은 달지 않는 것

판별은 첫 원칙 한 문장으로 한다. **이 주석을 지우면 다음 사람이 무엇을 잘못하는가.** 답이
나오지 않으면 지운다.

남기는 것은 넷뿐이다.

| 무엇 | 예 |
|------|-----|
| 의도. 왜 다른 방식이 아니라 이 방식인가 | 맵을 통째로 다시 쓰므로 남은 슬롯을 잃으면 그 버전 설정이 사라진다. |
| 불변식. 어기면 깨지는 제약 | 사실 테이블 insert 와 outbox insert 는 한 트랜잭션이어야 한다. |
| 외부 계약. 우리가 정하지 않은 사실 | Anthropic 은 Bearer 가 아니라 x-api-key 를 쓴다. |
| 함정. 직관과 반대로 동작하는 것 | 쿠키는 포트로 격리되지 않아 두 앱이 한 jar 를 공유한다. |

달지 않는 것.

| 무엇 | 이유 |
|------|-----|
| 코드를 한국어로 옮긴 것 | 코드가 이미 말한다. 코드가 바뀌면 먼저 틀린다 |
| 이름이 이미 말하는 것 | 주석 대신 이름을 고친다 |
| 과거 경위, 대안 비교, 회고 | 커밋 메시지와 `docs/` 의 자리 |
| 절 제목, 구분선 | 주석이 문단이 되었다는 신호. 함수를 쪼갠다 |
| 모든 필드에 하나씩 | 전부 달리면 어느 것도 신호가 아니다 |

**주석으로 풀지 말고 코드로 푼다.** 설명이 필요한 이름은 이름을 고치고, 단계를 설명해야 하는
블록은 함수로 뽑는다. 그러면 설명이 이름이 되어 낡지 않는다.

**분량은 한 줄이 기본이다.** 근거가 길어지면 실수를 막는 한 절만 남기고 나머지는 지운다.

**어디까지가 주석인지는 줄 수가 아니라 정보의 성격이 정한다.** 지금 이 코드를 고치는 사람에게
필요한 사실이면 네 줄이어도 주석이다. 그 코드를 안 보는 사람에게도 필요한 배경이거나, 여러 파일에
걸친 맥락이면 `docs/` 로 옮기고 주석에는 그 경로만 남긴다.

### 2. 어디에 다는가: `/** */` 와 `//`

**선언 자체를 설명하면 `/** */`, 선언 안의 필드나 구현 세부를 설명하면 `//` 다.** `/** */` 대상은
클래스, 인터페이스, 함수, 타입 별칭, enum, 그리고 클래스와 인터페이스의 메서드다. 함수 선언은
크기와 관계없이 `/** */` 다(길이를 기준으로 삼으면 어디부터인지 사람마다 갈린다).

`//` 자리는 인터페이스와 클래스의 필드, 객체 속성, 상수, 함수 본문, 파일 머리의 메모다. 한 줄이
기본이지만 필요하면 여러 줄로 잇는다. 필드에 `/** */` 를 붙이지 않는 이유는 선언과 그 안의 항목이
같은 무게로 보여 무엇이 이 파일의 주제인지 흐려지기 때문이다.

### 3. 어떤 형태로 쓰는가

| 주석의 모양 | 형태 | 예 |
|------------|------|-----|
| 사실이나 의도 하나를 서술 | 문장형(한다체, 마침표) | `// 응답이 불안정해서 재시도하지 않는다.` |
| 항목을 나열하거나 이름표를 붙임 | 개조식(명사형, 마침표 없음) | `/** 커스텀 key 여부 판정, 기본 축 key 사칭 방지 */` |
| 할 일 표시 | `TODO:` / `FIXME:` 한 줄 | `// TODO: 비동기 처리로 변경` |

```ts
// 커스텀 key 형식: `x:` + 소문자 hex 4~32
const KEY_PATTERN = /^x:[0-9a-f]{4,32}$/;

/** 커스텀 key 여부 판정, 기본 축 key 사칭 방지 */
export function isCustomKey(value: string): boolean {
  return KEY_PATTERN.test(value);
}

/** 기획 생성 요청 */
export interface PlanGenerateInput {
  // 이름이 바뀌어도 유지되는 값이라 기존 선택 보존
  key: string;
  // 후보를 제시하지 않은 프롬프트의 응답에는 그 id 가 올 수 없어, 부재가 곧 그 사실이다.
  sfxCandidates?: AudioAssetCandidate[];
}
```

- **별표 강조를 쓰지 않는다.** 주석과 터미널에 찍히는 글(테스트 이름 등)은 마크다운으로 렌더되지
  않아 `**` 가 그대로 보인다.
- **태그에는 무엇을 해야 하는지만 적는다.** 배경과 조건이 붙으면 이슈로 옮기고 주석에는 그 번호만
  남긴다.

예외: API 문서 설명(`@ApiOperation`, `summary`/`description`, Pydantic `description`)은 이 규칙
밖이다. 그 글은 문서 포털에서 읽히는 레퍼런스라 [api-architecture.md](./api-architecture.md) 의
작성 규칙을 따른다.

## 대시 사용 금지

**문장을 연결하거나 부연하는 대시는 쓰지 않는다.** `—`, `–`, 문장 중간의 `-` 를 모두 포함한다.
**대등한 항목을 나타내는 대조 기호와 코드 문법은 예외다.**

금지되는 것은 문자가 아니라 역할이다. 같은 `-` 라도 앞뒤 관계가 다르면 판정이 갈린다.

```ts
// 그대로 둔다: 대등한 두 항목을 견줌
// landscape - 좌측 사이드바 / portrait - 상단 바
// dev - staging - prod

// 고친다: 뒤가 앞의 부연이나 이유
// 높이를 측정한다 — 상수로 두면 어긋나기 때문
// 높이를 측정한다. 상수로 두면 어긋나기 때문.
```

부연하는 자리에 쓸 대안.

| 상황 | 대신 쓸 것 | 바꾸기 전 → 바꾼 뒤 |
|------|-----------|------------------|
| 부연 설명 붙이기 | 괄호 `()` | `알림 — 기능 준비중입니다.` → `알림 기능 준비중입니다.` |
| 이유/근거 잇기 | 마침표로 끊고 새 문장 | `측정한다 — 값이 바뀌기 때문이다.` → `측정한다. 값이 바뀌기 때문이다.` |
| 정의/환언 | 쉼표 또는 `:` | `인셋 — 하단 점유 높이` → `인셋: 하단 점유 높이` |
| 목록 항목의 설명 | 마침표 또는 줄바꿈 | `합산한다 — 바가 쌓이므로` → `합산한다(바가 쌓이므로).` |

코드 식별자와 kebab-case 키(`video-model`, `X-Service-Token`), 명령행 플래그와 범위 표기
(`--no-cache`, `0~10`), 마크다운 목록 머리표는 문장부호가 아니라 문법이라 그대로 둔다.

## 가운뎃점(·, 중간점) 사용 금지

가운뎃점(`·`, U+00B7 및 유사 중간점)을 쓰지 않는다. 항목 나열이나 구분이 필요하면 아래 대안을 쓴다.

| 상황 | 대신 쓸 것 | 예 |
|------|-----------|-----|
| 대등한 항목 나열 | 쉼표 `,` | `연관 키워드, 검색량` |
| 두 대상을 함께 묶음 | `+` 또는 `와/과` | `쇼핑 리뷰 + 쇼핑인사이트` |
| 경로/택일 구분 | 슬래시 `/` | `API/크롤링` |
| 부가 설명 | 괄호 `()` | `목적 키워드 (화장품)` |

> 슬래시(`/`)는 금지 대상이 아니다. 금지되는 건 대시와 가운뎃점이다.

## 이모지 사용 금지

코드 주석, 문서, UI 문구, 커밋 메시지 어디에도 이모지를 쓰지 않는다. 좋음/나쁨 표시(체크, X),
계층 표시(색 원), 강조(경고, 불꽃) 전부 해당한다.

| 쓰던 것 | 대신 쓸 것 |
|---------|-----------|
| 좋은 예/나쁜 예 표시(체크, X) | 무엇이 다른지 설명으로 적는다: `바꾸기 전`, `바꾼 뒤` |
| 계층/분류 표시(색 원, 사각형) | 계층 이름을 그대로 적는다: `Inbound Adapter`, `Core` |
| 경고/주의 강조 | `**주의:**`, `**중요:**` |

## 적용

- 새로 작성하는 텍스트에는 처음부터 대시, 가운뎃점, 이모지를 넣지 않는다.
- 기존 텍스트를 수정할 때 그 줄에 금지 대상이 있으면 위 대안으로 함께 정리한다.
- **일괄 치환하지 않는다.** 문장마다 콜론, 괄호, 마침표 중에 골라야 제대로 읽히고 대조 기호는
  그대로 둬야 한다. 기계적 치환은 글을 망친다.
- 좋음/나쁨 라벨을 새로 만들지 않는다. 이모지를 걷어낸 자리에 `(좋음)`/`(나쁨)` 같은 딱지를 붙이면
  기호만 글자로 바뀐 것이라 나아지지 않는다. 무엇이 왜 다른지 문장으로 적는다.
