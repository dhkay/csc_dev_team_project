# 런북: MES 현장 문제 대응

> 설계 기준 한 줄: **전화로 진단이 되는가.**
>
> 현장 PC 는 원격 접속이 어렵고, 문제를 알려주는 사람은 개발자가 아니다. 이 문서의 모든 절차는
> "작업자에게 전화로 시킬 수 있는가" 를 기준으로 쓰였다.

## 0. 첫 질문 셋

무슨 증상이든 이것부터 묻는다. 앱 하단 상태바에 상시 노출되어 있다.

1. **연결** 이 뭐라고 되어 있습니까 (연결됨 / 지연 / 오프라인 / 확인 중)
2. **미전송** 이 몇 건입니까
3. **마지막 동기화** 가 몇 시입니까

이 셋으로 대부분의 분기가 결정된다. 더 필요하면 화면 오른쪽 아래 **진단** 링크를 눌러
`/diagnostics` 로 보낸다.

---

## 1. 진단 번들

가장 강력한 도구다. 진단 화면의 **진단 번들 내보내기** 버튼이 최근 로그 + 스키마 버전 +
config(비밀 마스킹) + outbox 요약을 zip 으로 **바탕화면에** 저장한다.

> 전화로 "바탕화면에 생긴 파일 메일로 보내주세요" 가 되는 것과, 원격 지원 도구를 설치하러
> 공장에 가는 것의 차이다.

Phase 1 에서 제공된다. Phase 0 에서는 진단 화면의 값을 읽어 받는다.

---

## 2. 증상별 대응

### 2-1. "실적이 저장이 안 돼요"

| 확인 | 진단 화면 위치 | 원인 |
|---|---|---|
| 읽기 전용 경고가 떠 있나 | 상단 경고 박스 | 로컬 DB 가 앱보다 최신(롤백 후 미복구) -> 2-4 |
| 로컬 스키마 vs 기대 | 신원 > 로컬 스키마 | 위와 같음 |
| 디스크가 꽉 찼나 | OS | 로그 로테이션 실패 -> 2-5 |

**저장 자체가 실패하는 것과 서버로 안 가는 것은 다른 문제다.** 저장은 됐는데 미전송이 쌓이는
것은 정상 동작이다(오프라인 우선). 작업자에게 이 차이를 먼저 설명한다.

### 2-2. 미전송이 계속 쌓인다

```
연결 = 오프라인  -> 네트워크 문제. 2-3
연결 = 연결됨    -> 서버가 거부하고 있다. 진단 화면 "최근 실패" 를 본다
```

최근 실패의 사유별 대응:

| 사유 | 의미 | 대응 |
|---|---|---|
| `VALIDATION_FAILED` | 클라이언트가 잘못된 데이터를 만들었다 | 버그. 진단 번들 수집 후 에스컬레이션 |
| `ENTITY_NOT_FOUND` | 참조 마스터가 로컬에 없다 | 진단 화면의 "지금 동기화" 를 누른다 |
| `VERSION_CONFLICT` | 다른 PC 가 먼저 바꿨다 | 자동 리베이스된다. 반복되면 에스컬레이션 |
| `QTY_EXCEEDS_PLAN` | 지시 수량 초과 | **정상 거부.** 관리자 승인이 필요하다 |
| `FORBIDDEN_SCOPE` | 이 단말에 배정되지 않은 라인 | 단말 라인 배정 확인(관리자) |
| `REQUIRES_ELEVATION` | 감독자 권한 필요 | 감독자 인증 후 재시도 |
| `OP_ID_REUSED` | 클라이언트 버그 | 진단 번들 수집 후 에스컬레이션 |

**미전송 항목을 임의로 지우지 않는다.** 폐기는 사유 입력이 필수이고 `sync_audit` 에 기록된다.

### 2-3. "오프라인" 인데 인터넷은 된다

공장 네트워크에서 흔하다. 링크는 살아 있고 게이트웨이만 죽는 경우다. 그래서 앱은
`navigator.onLine` 이 아니라 서버 `/health` 를 직접 프로브한다.

확인 순서:

1. 진단 화면의 **API 주소** 를 읽는다.
2. 그 PC 브라우저에서 `<API 주소>/health` 를 연다.
   - 열리면: 앱 문제. 진단 번들 수집.
   - 안 열리면: 네트워크 또는 서버 문제. 3절로.
3. 주소 자체가 틀렸으면 `%APPDATA%/csc-mes/config.json` 을 고친다(4절).

`/health` 는 **의도적으로 비인증**이다. 토큰이 만료돼도 응답하므로, 열리는데 다른 기능이 안
되면 그건 네트워크가 아니라 인증 문제다.

### 2-4. 앱을 롤백했더니 읽기 전용이 됐다

정상 동작이다. 로컬 DB(`user_version`)가 앱이 기대하는 버전보다 높으면 앱이 쓰기를 막는다.
그냥 열면 신버전 컬럼의 데이터가 조용히 잘려 나가기 때문이다.

복구:

1. **앱을 최신 버전으로 다시 올린다.** 이게 정답이다.
2. 그럴 수 없다면(릴리스가 취소됨) 마이그레이션 백업에서 되돌린다.
   ```
   %APPDATA%/com.cscuniverse.mes/mes.db.bak-v<이전버전>
   ```
   앱 종료 상태에서 `mes.db` 로 복사한다. **그 백업 이후의 미전송 실적은 사라진다.**
   반드시 먼저 현재 `mes.db` 를 다른 이름으로 복사해 둔다.

### 2-5. 디스크가 찼다

증상이 "생산실적이 저장 안 돼요" 로 나타나 원인 추적에 하루가 걸리는 유형이다.

앱 자체 상한(파일 50MB / 7일, 로그 outbox 20,000건)이 있어 앱 로그가 원인인 경우는 드물다.
대개 다른 프로그램이다. 그래도 진단 화면의 DB 경로를 확인해 파일 크기를 본다.
500MB 를 넘으면 앱이 설정 화면에 경고를 띄운다.

## 3. 서버 쪽 확인 (관리자)

```bash
# 컨테이너 상태
docker compose -f infra/docker/prod/web/docker-compose.yml ps api-csc-mes

# 헬스 (비인증)
curl -s http://127.0.0.1:4007/health

# 단말 현황: 마지막 동기화 시각, 클라이언트 버전, 미전송 추정치 (Phase 1)
#   서비스토큰이 필요하다. /internal 은 현장 단말이 접근하지 않는다.
```

로그는 통합 로그 서버(ClickHouse)에 있다. control-tower 의 로그 조회 화면에서
`service=csc-mes` 로 필터한다.

## 4. 단말 설정 변경

`%APPDATA%/csc-mes/config.json` 을 편집한다. 앱 재시작이 필요하다.

```jsonc
{
  "apiBaseUrl": "https://mes.cscuniverse.com",
  "updateEndpoint": "https://mes.cscuniverse.com/desktop/latest.json",
  "channel": "prod",
  "deviceId": "term-lineA-01",
  "siteCode": "A"
}
```

- 일부 필드만 적어도 된다. 나머지는 빌드 기본값이 채운다.
- **JSON 이 깨져도 앱은 뜬다.** 기본값으로 떨어지고 진단 화면이 실제 적용값을 보여준다.
  쉼표 하나 빠뜨려도 앱이 안 뜨는 일은 없다.
- 적용 확인은 진단 화면의 **설정** 절.

---

## 5. 단말 폐기 (분실, 탈취)

단말이 물리적으로 탈취되면 배지 위조가 가능하다. 이건 암호로 막을 수 없고 폐기로 대응한다.

```
관리자 -> 단말 폐기 (mes_devices.status = REVOKED)
       -> 그 단말의 다음 요청부터 401 DEVICE_REVOKED
       -> 앱은 동기화를 영구 중단하되 outbox 는 보존한다
```

보존하는 이유: 폐기 이전에 만들어진 실적은 진짜 생산의 기록이다. 회수 후 관리자가 검토해
수동 반영할 수 있어야 한다.

---

## 6. 에스컬레이션 시 첨부할 것

1. 진단 번들 zip (없으면 진단 화면 스크린샷 전체)
2. 증상이 언제부터인지, 그 전에 무슨 일이 있었는지(앱 업데이트, 정전, 네트워크 공사)
3. 같은 라인의 다른 PC 도 같은 증상인지 (한 대만이면 단말 문제, 전부면 서버 또는 네트워크)
