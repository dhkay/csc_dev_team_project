# 마케팅 영상 도구: 쓰기 일관성 계약 (취소, 보상, 멱등)

## 왜 이 문서인가

이 도구의 쓰기는 거의 전부 **로컬 DB 한 행 + 원격 부수효과**의 조합이다. 부수효과는 두 종류다.
file-upload 의 자산(씬 이미지, 업로드물)과 video-model 의 렌더 잡이다. 둘 다 marketingdb 트랜잭션
밖에 있어서 `db.transaction` 으로 묶을 수 없다.

개별 보상 코드는 이미 곳곳에 있다. 없는 것은 그것들을 묶는 규칙이다. 그래서 새 쓰기 흐름을 추가할
때마다 보상을 넣을지 말지를 사람이 매번 새로 판단하고, 빠뜨려도 아무것도 알려주지 않는다.

이 문서는 그 규칙을 정한다. 규칙(4절)이 먼저 정해졌고, 그 규칙을 사람의 기억이 아니라 코드가
집행하도록 지금은 **오케스트레이션 사가**가 다단계 쓰기를 돌린다(4.5). 처음에 그것을 미뤘던 이유와
도입한 이유는 3절에 있다.

관련: [service-http-contract.md](./service-http-contract.md)(서버 간 호출 계약),
[../../.claude/rules/file-upload-limits.md](../../.claude/rules/file-upload-limits.md)(자산 수명),
[../../.claude/rules/system-architecture.md](../../.claude/rules/system-architecture.md)(DB 소유권 경계).

## 1. 지금 있는 것

| 흐름 | 무엇이 되어 있는가 | 위치 |
|------|------------------|------|
| 생성 중 기획안 삭제 | `removed` 마킹 → 아직 나가지 않은 씬 이미지 요청을 보내지 않고(동시 실행 게이트 대기 중인 것 포함), 자동 저장 콜백도 막는다 | `planSceneImagesStore.remove` / `PlanBatch` 완료 효과의 `isRemoved` 가드 |
| 자동 저장 중복 | `markReported` 가 기획안당 1회로 묶어, 재마운트가 재저장을 만들지 않는다 | `planSceneImagesStore.markReported` |
| 렌더 중 삭제 | 삭제 **전에** 원격 잡을 취소한다. 실패해도 삭제는 진행하고 경고를 남긴다. 활동 로그에 `render_canceled` 를 남겨 요금이 왜 끊겼는지(또는 왜 더 나갔는지) 추적된다 | `video-project.service.ts` `cancelRenderIfRunning` |
| 저장본 삭제 | 참조 씬 이미지를 file-upload 에서 함께 지운다 | `saved-plan.service.ts` `deletePersonal` |
| 씬 이미지 교체 | 교체가 커밋된 뒤 이전 자산을 지운다 | `saved-plan.service.ts` `updateScenePersonal` |
| 참조 무효화 | 채널, 저장본, 원천을 지워도 산출물은 남는다(`onDelete: 'set null'` + 필요한 값은 컬럼으로 스냅샷) | `marketing-tables.ts` |
| 비멱등 호출 보호 | LLM 생성 쿼리는 자동 재시도, 재요청, 포커스 리페치를 전부 끈다 | `plans.query.ts` |
| 다중 행 갱신 | 채널 재정렬은 한 트랜잭션 | `channel.adapter.ts` `reorderChannelRecords` |

즉 **"생성 도중 삭제"는 씬 이미지 단계에서는 정확히 다뤄지고 있다.**

## 2. 없던 것 (이 문서가 고친 것)

아래 다섯은 **고치기 전의 상태**다. 진단을 남겨 두는 이유는 4절의 규칙이 왜 그 모양인지가 여기에
있어서다. 그 규칙을 나중에 손댈 사람은 무엇을 막으려고 그렇게 했는지를 알아야 한다.

### A. 텍스트 생성을 멈출 방법이 없다

`generatePlans` 는 `AbortSignal` 을 받지 않는다. 쿼리 옵션도 `gcTime: Infinity` 라 관측자가 사라져도
취소되지 않는다. 그리고 `planGenerationStore` 에 배치를 지우는 메서드가 없다.

결과: 씬 이미지는 취소되는데 그 앞단계인 기획안 텍스트 생성은 못 멈춘다. 비대칭이다. 사용자가 화면을
떠나거나 탭을 닫아도 LLM 은 끝까지 돌고 조직에 과금된다. 받을 사람이 없는 결과다.

### B. 저장이 분산 쓰기인데 되돌리는 코드가 없다

`saveSavedPlanMutationOptions` 는 `N × (presign → PUT → confirm)` 을 먼저 하고 그다음 `INSERT` 한다.

INSERT 가 실패하면 confirm 까지 끝난 자산이 아무도 참조하지 않는 채로 영구히 남는다. 실패는 가상이
아니다. 생성 도중 채널을 지우면 `channel_id` FK 위반(23503)으로 INSERT 가 깨진다. 그때 씬 이미지
여러 장이 스토리지에 그대로 남는다.

### C. 멱등키가 없다

저장 실패 알림에 `다시 저장` 이 붙어 있고, 그것은 뮤테이션 전체를 다시 돌린다. 이미지를 다시
업로드하므로 첫 시도의 자산이 고아가 되고, 첫 INSERT 가 실제로는 성공했는데 응답만 유실된
경우에는 같은 기획안이 두 행이 된다.

### D. 보상 실패가 유실된다

`FileUploadStorageAdapter.deleteAsset` 은 `.catch(() => undefined)` 다. 삭제 실패가 로그에도 남지
않는다. 렌더 취소는 경고를 남기는데 자산 삭제는 남기지 않아, 고아가 생겼다는 사실 자체를 알 방법이
없다. 재시도할 근거도 없다.

### E. 고아 수거자가 없다

file-upload 에 `PENDING`(presign 했지만 PUT 이나 confirm 이 오지 않은) 자산을 정리하는 잡이 없다.
B 와 D 가 남긴 `UPLOADED` 고아도 마찬가지다. 둘 다 무한히 쌓인다.

## 3. 사가를 미룬 이유, 그리고 도입한 이유

처음 판단은 "교과서적 사가(단계별 상태를 durable 하게 적고 실패하면 역순으로 보상하는 오케스트레이터)
는 여기에 맞지 않는다" 였다. 근거가 셋이었고, 넷째 규칙(4.4)까지 적용한 뒤 그 셋을 다시 보면 둘이
사실과 달랐다. 판단을 남겨 두는 이유는 같은 저울을 다시 달 사람에게 무게가 어디서 바뀌었는지가
필요해서다.

| 미룬 근거 | 실제 |
|---|---|
| 쓰기의 단계가 둘이다(부수효과 하나 + 행 하나) | **넷이다.** 저장은 모델 해석, 행 INSERT, 자산 확정, 원장 기록이고 영상 둘은 예약, 잡 등록, 잡 부착, 원장 기록이다. 순서만으로는 중간에서 죽은 상태를 다루지 못한다 |
| 보상이 필요 없게 만들 수 있다 | 저장 흐름에서는 맞았다(4.2 가 되돌릴 것을 없앴다). **영상 흐름에서는 틀렸다.** 벤더 렌더 잡은 우리 DB 밖에 있고 뒤 단계가 실패하면 반드시 취소해야 한다(안 하면 요금만 나간다) |
| 상태기계를 하나 더 두면 렌더 상태와 경쟁한다 | 경쟁하지 않는다. 두 상태가 답하는 질문이 다르다. `RenderStatus` 는 **산출물이 지금 어떤 상태인가**(폴링과 reconcile 이 따라 돈다), 사가 상태는 **그 산출물을 만드는 쓰기 시도가 어디까지 갔는가**다. 사가는 완료되면 다시 읽히지 않고, 산출물의 상태를 대신 말하지 않는다 |

결정적이었던 것은 셋 다 아니라 **크래시**다. 4.1~4.4 를 다 적용해도 프로세스가 단계 사이에서 죽으면
(배포 재시작, OOM) 보상 코드는 아예 실행되지 않는다. 그때 남는 것 둘이 스스로 낫지 않았다.

- 잡 없이 `PENDING` 인 예약 행. `reconcile` 이 `renderJobId` 없는 행을 건너뛰므로 "만드는 중" 으로
  영구히 남는다.
- 확정되지 않은 자산을 가리키는 저장본. 수거자가 그 `PENDING` 자산을 지우면 저장본이 빈 이미지를
  가리킨다.

되돌리는 코드를 어디에 더 넣어도 이것은 막히지 않는다. **중단된 지점을 적어 두고 나중에 이어 가는
주체**가 있어야 막힌다. 그것이 오케스트레이션 사가이고, 그래서 도입했다.

네 개의 이음새(seam)는 그대로 유지된다. 각각은 여전히 독립적인 규칙이고, 사가는 그 규칙들을 대체하지
않고 **집행**한다(4.5).

## 4. 설계

### 4.1 이음새 1: 취소 신호 경로

**규칙: 비싼 원격 호출은 전부 `AbortSignal` 을 받는다. 그 신호를 끊는 주체는 그 작업을 화면에서
없앤 액션이다.**

- `planApi.generatePlans(channelId, req, signal?)`: 씬 이미지 생성과 같은 형태로 맞춘다(그쪽은 이미
  받는다).
- `plans.query.ts` 의 `queryFn: async ({ signal }) => api.generatePlans(..., signal)`.
- `planGenerationStore.removeBatch(batchId)` 를 추가한다. 지금 이 스토어에는 배치를 없애는 수단이
  아예 없다.
- 배치를 없애는 액션이 그 배치의 쿼리 키로 `cancelQueries` 를 불러 신호를 끊는다. **키를 손으로
  적지 않는다**: 조립은 `plans.query.ts` 의 `planBatchQueryKey` 하나가 소유한다(축이 하나 늘 때
  사본만 옛 모양으로 남으면 취소가 에러 없이 no-op 이 된다. 실제로 겪었다).

**확장 지점**: 다른 장시간 호출(영상 프롬프트 생성 등)이 붙을 때 같은 세 줄을 따른다. 신호를 받지
않는 새 호출은 리뷰에서 막는다.

**끊는 쪽도 다단계다.** 위의 셋(신호 끊기, 목록에서 없애기, 캐시 비우기)은 순서가 있고 중간에서
멈추면 "멈추지 못했는데 화면에서는 사라진" 상태가 남는다. 그래서 브라우저 쪽 취소도 사가로 적는다
(`marketing-channels/lib/cancelGeneratingBatch.ts`). 엔진은 `@csc/saga` 가 아니라 브라우저용
러너(`shared/lib/saga/clientSaga.ts`)다: durable 저장소와 실행권과 복구는 프로세스가 죽어도 상태가
남는다는 전제 위에 있고 탭에는 그 전제가 없다. **계약(`name`/`execute`/선택적 `compensate`)만 같게
맞춘다.** 위 한계를 없앨 language-model 취소 엔드포인트가 생기면 그 호출은 이 사가의 단계로 들어온다
(원격 호출이라 실패할 수 있고, 실패하면 뒤 단계로 가면 안 된다는 규칙이 이미 거기 있다).

**한계를 문서에 적어 둔다**: fetch abort 는 이 서버와의 소켓을 닫을 뿐이고, csc-marketing 이 이미
language-model 로 보낸 요청은 계속 돈다. 그것까지 끊으려면 language-model 쪽 취소 엔드포인트가
필요하다(별건). 그래도 abort 는 값이 있다. 결과를 기다리는 화면이 사라졌다는 사실이 서버 로그에
남고, 이후 단계(씬 이미지 N장)가 시작되지 않는다.

### 4.2 이음새 2: 확인(confirm)을 서버로 미룬다 (고아를 구조적으로 없앤다)

**규칙: 자산의 확인은 그 자산을 참조할 행을 만드는 쪽이 한다. 브라우저는 presign + PUT 까지만 한다.**

```
지금:  presign → PUT → confirm(브라우저)  ×N   →  INSERT       실패 시 UPLOADED 고아 N장
뒤:    presign → PUT               ×N   →  INSERT → confirm(서버)
                                            확정 실패 → 그 행 삭제
```

각 실패 지점의 결과:

| 실패 지점 | 지금 | 뒤 |
|---|---|---|
| 업로드 중 | 아무것도 저장 안 됨 + 일부 UPLOADED 고아 | 아무것도 저장 안 됨 + PENDING(수거됨) |
| INSERT | 아무것도 저장 안 됨 + **UPLOADED 고아 N장 영구** | 아무것도 저장 안 됨 + PENDING(수거됨) |
| confirm | (해당 없음) | 아무것도 저장 안 됨 + PENDING(수거됨) |
| 성공 | 행 + UPLOADED | **동일** |

**성공 경로도 실패 경로도 사용자가 보는 것이 달라지지 않는다.** 그런데 참조 없는 `UPLOADED` 가
생길 수 있는 순서가 아예 사라진다. `PENDING` 은 원래부터 수거 대상이므로(presign 만 받고 끝난 업로드)
새 고아 분류를 만들지 않고 기존 한 메커니즘이 둘 다 거둔다.

확정 실패의 보상 대상이 **우리 DB 행**이라는 점이 이 순서의 이점이다. 원격 자산을 지우는 보상은
그 자체가 실패할 수 있지만, 자기 DB 의 행을 지우는 것은 훨씬 확실하다.

씬 이미지 교체(`updateScenePersonal`)도 같은 규칙을 따른다. 갱신 후 확정하고, 확정이 실패하면
이전 `scenes`/`sceneImages` 로 되돌린다(이전 배열이 이미 손에 있다).

**행을 먼저 만들고 이미지를 나중에 붙이는 안은 채택하지 않았다.** 그 순서도 고아를 없애지만 실패
시 **이미지가 빠진 저장본**이 남는다. 이 저장소는 반쪽 산출물을 목록에 남기지 않는다는 규칙을
이미 여러 곳에서 지킨다(렌더 `CANCELLED`, `planCancellation` 의 배치 되돌리기). 확인 미루기는 그
규칙을 지키면서 같은 결과를 낸다.

### 4.3 이음새 3: 멱등키

**규칙: 재시도 버튼이 붙거나 누르면 유료 작업이 생기는 쓰기는 클라이언트가 만든 키를 함께 보낸다.**

컬럼 규약은 세 테이블이 같다: `client_request_id varchar(120)` + `(organization_id, owner_user_id,
client_request_id)` 부분 유니크(`WHERE client_request_id IS NOT NULL`). 부분인 이유는 null 이
유니크에서 서로 다르게 취급되어 옛 행과 키를 쓰지 않는 경로를 막지 않기 때문이다.

**키를 무엇으로 만드는지는 쓰기마다 다르다.** 이것을 한 규칙으로 통일하면 한쪽이 망가진다.

| 쓰기 | 키 | 이유 |
|---|---|---|
| 기획안 저장 | `` `${batchId}:${proposal.id}` `` (결정적) | 자동 저장은 기획안당 정확히 한 번이어야 한다. 결정적 키가 그 의미다 |
| 영상 만들기 / 세트 적용 | 클릭 시점 `crypto.randomUUID()` | **같은 대상으로 다시 만드는 것은 정상 사용**이다(재생성 버튼도 있다). 대상 id 로 키를 만들면 두 번째가 막힌다 |

**키가 없는 쓰기도 있다.** 작업 공간 배치(대표 썸네일 붙이기를 겸한다)와 보관함 이동이 그렇다. 같은
영상을 몇 번 배치하든 결과는 하나이고(배치 시각은 처음 것을 유지하고, 그림은 컬럼 하나가 덮인다)
되돌릴 유료 작업도 만들어지지 않는다. 이동은 조건부 갱신이라 두 번째 요청이 아무것도 바꾸지 못한다
(그 반환값이 곧 "내가 옮겼다" 는 증표이고, 그래서 활동 로그도 한 번만 남는다). 키는 중복이
**무언가를 남기거나 돈을 쓸 때** 필요하다.

두 번째는 `packages/mes-contracts` 의 `clientOpId` 규약과 같다: "작업자가 확인 버튼을 누른 순간
생성한다(전송 시점이 아니다)". 뮤테이션 변수에 담아 재시도가 같은 값을 재사용한다.

**키를 판정하는 곳은 사가 저장소다**(4.5 도입 이후). 같은 키로 다시 오면 `startOrGet` 이 그 사가를
찾아 돌려주고, 이미 COMPLETED 면 단계를 하나도 실행하지 않은 채 만들어진 것을 응답한다(생성도 로그도
없다). 사전 조회를 통과한 두 요청이 동시에 사가를 INSERT 하면 하나는 유니크에 걸리는데, 그 실패는
**성공으로 접는다**(재조회해서 이긴 사가를 쓴다). 실패로 올리면 사용자에겐 실패로 보이는데 실제로는
저장돼 있어, 그 어긋남이 다시 누르게 만든다.

행 수준의 부분 유니크는 그 위의 **마지막 방어선**으로 남는다. 도메인 행이 키당 둘이 되는 일은 어떤
경로로도 없다는 보장이다.

**동시 중복도 같은 답을 받는다(실행권).** 사가 하나는 한 번에 한 실행만 돈다. 겹치면 하나가 실행권을
잡고 다른 하나는 그것이 끝나기를 기다렸다가 **같은 산출물**을 돌려받는다. 그래서 중복 제출의 답은
요청이 순차든 동시든 하나이고, 사용자는 두 번 눌렀다는 사실을 화면에서 알 수 없다. 상세는 4.5.

실행권이 없으면 어떻게 되는지가 이 장치의 존재 이유다. 두 실행이 같은 사가의 남은 단계를 각자 한 번씩
수행하는데, 영상 흐름에서 그것은 **유료 잡 두 개**를 뜻한다(나중에 붙은 잡만 폴링되므로 먼저 만든 잡은
요금만 나가는 고아가 된다). 예약을 잡보다 앞에 두어(4.3.1) 막으려던 바로 그 사고가 동시 요청에서는
그대로 일어났다.

### 4.3.1 유료 작업 앞에 행을 예약한다

영상 두 경로(원천/최종)는 `createJob` 을 `INSERT` **앞**에서 불렀다. 그러면 멱등키 유니크가 이미
돈이 나간 뒤에 중복을 거절한다(더블클릭 = 유료 잡 2개). 순서를 뒤집는다.

```
1. 멱등키로 조회 → 있으면 그 행 반환 (잡 만들지 않음)
2. 예약 INSERT (renderJobId=null, renderStatus='PENDING')   ← 유니크가 여기서 중복을 막는다
     충돌 = 다른 요청이 이겼다 → 그 행을 조회해 반환 (잡 만들지 않음)
3. render.createJob(spec)
4. startRenderRecord(jobId) → RENDERING
   3 실패 → 예약 행 삭제 + rethrow  (결과: 아무것도 만들어지지 않음, 예전과 같다)
```

전제가 이미 성립해 있었다: `render_job_id` 는 nullable, `render_status` 기본값은 `'PENDING'`,
폴링(`reconcile`)이 `!renderJobId` 를 건너뛴다. 그래서 예약 행은 새로운 상태가 아니다.

`startRenderRecord` 는 재렌더가 쓰던 메서드다(구 `restartRenderRecord`). 하는 일이 같아서 이름만
"다시"를 떼고 두 쓰임이 공유한다.

충돌 판정을 드라이버 에러 코드로 하지 않는다. **다시 조회해서 있으면** 충돌로 본다(그 행이 답이다).
드라이버 교체에 깨지지 않고, 다른 실패는 그대로 올라간다.

### 4.4 이음새 4: 보상 실패를 기록하고 거둔다

**규칙: 보상이 실패하면 삼키지 않고 기록한다. 기록된 것은 나중에 다시 거둔다.**

1. **당장(코드 한 줄 수준)**: `FileUploadStorageAdapter.deleteAsset` 의 `.catch(() => undefined)` 를
   경고 로그로 바꾼다. 렌더 취소 실패와 같은 취급이다. 그것만으로 "고아가 생겼다"는 사실이 추적
   가능해진다.
2. **활동 로그에 남긴다**: 자산 정리 실패를 `detail.asset_cleanup_failed` 로 남긴다. 활동 로그는 이미
   조직, 채널, 행위자로 조회되므로 별도 조회 화면이 필요 없다.
3. **수거자는 file-upload 가 갖는다**: 자산의 주인이 그 서버다. `PENDING` 이면서 presign 후 TTL(예
   24시간)을 넘긴 자산을 지우는 주기 잡을 그쪽에 둔다. 이것이 A~E 중 유일하게 다른 서비스의 일이다.

**`UPLOADED` 고아는 수거자로 풀지 않는다.** 참조 여부를 아는 것은 file-upload 가 아니라 소비 서비스이고,
그 판정을 file-upload 에 넣으면 자산 소유권 경계가 깨진다. 4.2 가 애초에 그 고아를 만들지 않게 하는
것이 정답이고, 그래서 4.2 가 이 문서의 핵심이다.

### 4.5 오케스트레이터가 이 규칙들을 집행한다

**규칙: 다단계 쓰기는 서비스 메서드가 순서대로 부르지 않고 사가 정의로 적는다.**

엔진은 **공유 패키지 `@csc/saga`** 이고 도메인을 모른다. 무엇을 하는 단계인지는 각 도메인이 소유한
정의(`core/application/sagas/`)에 있다. 그래서 새 다단계 쓰기가 늘어도 엔진은 그대로다.

**앱 안이 아니라 패키지에 두는 이유**: 이 문제(로컬 행 + 원격 부수효과)는 이 앱만의 것이 아니다. 두
번째 앱이 필요해질 때 엔진을 복사하면 그 순간 규칙이 둘로 갈리고, 한쪽만 고쳐진 채 오래 간다. 코어는
런타임 의존성이 0 이라(프레임워크도 ORM 도 모른다) 옮기는 비용이 낮았다. 다른 앱에 붙이는 절차는
[packages/saga/README.md](../../packages/saga/README.md) 가 단일 출처다.

| 조각 | 파일 | 하는 일 |
|---|---|---|
| 계약 | `@csc/saga` `saga.types.ts` | `SagaStep`(execute + 선택적 compensate), `SagaDefinition`(type + steps + hydrate) |
| 진행 상태 | `@csc/saga` 포트 + marketingdb `marketing_sagas` | 단계 번호와 컨텍스트를 행 하나에 적는다 |
| 조율 | `@csc/saga` `saga-runner.ts` | 단계 실행, 매 단계 직후 진행 기록, 실패 시 역순 보상, 중단분 이어가기 |
| 복구 | `@csc/saga` 복구 서비스 + `@csc/saga/nest` 스케줄러 | 중단된 인스턴스를 집어 러너에게 넘긴다(1분 주기) |
| 실행권 | `marketing_sagas.claimed_at` | 한 사가를 한 실행만 돌린다(요청 경로와 복구 경로가 같은 컬럼을 쓴다) |
| 저장소 | `@csc/saga/drizzle` | 표 정의(`sagaTable`) + 어댑터 팩토리. 앱은 자기 db 와 표를 넘긴다 |
| **앱이 갖는 것** | `shared/saga.module.ts`, 도메인별 `sagas/`, 운영 컨트롤러 | 우리 DB 를 끼우는 배선, 단계 정의, HTTP 표면 |

지금 사가로 도는 쓰기는 여섯이다.

| 사가 | 종류 key | 단계 |
|---|---|---|
| 기획안 저장 | `saved_plan.save` | 이미지 모델 해석, 행 INSERT, 자산 확정, 원장 |
| 원천 영상 생성 | `video_project.create` | 예약, 잡 등록, 잡 부착, 원장 |
| 원천 영상 재렌더 | `video_project.rerender` | 잡 등록, 잡 부착, 원장 |
| 세그먼트 재생성 | `video_project.rerender_segment` | 예약, 씬 재렌더 요청, 원장 |
| 최종 영상 생성 | `video_final.create` | 예약, 잡 등록, 잡 부착, 원장 |
| 최종 영상 재렌더 | `video_final.rerender` | 잡 등록, 잡 부착, 원장 |

**모든 다단계 쓰기가 사가인 것은 아니다.** 작업 공간 배치(`placeInWorkspacePersonal`)는 두 단계지만
(행 갱신 → 썸네일 자산 확정) 되돌릴 것이 우리 DB 의 컬럼 하나뿐이고 그 이전 값이 이미 손에 있어,
중단 지점을 적어 두고 이어 갈 주체가 필요하지 않다. 씬 이미지 교체(4.2 의 `updateScenePersonal`)와
같은 모양이다. **사가는 되돌릴 것이 우리 밖에 있거나(유료 잡) 이어 가지 않으면 스스로 낫지 않는
상태가 남을 때** 쓴다.

**보관함 이동은 단계가 하나다**(조건부 UPDATE 한 번). 원격 부수효과도 자산 확정도 없어 되돌릴 것이
없다. 보관물 **삭제**는 개인 삭제와 같은 절차를 쓴다(진행 중 렌더 취소 → 행 삭제 → 그 행이 소유한
썸네일 자산 삭제). 다른 것은 누가 지울 수 있는가뿐이고 그 판정은 호출부가 끝낸다.

**미리보기 산출물 등록**(dev 전용, `[VIDEO-027]`)도 사가가 아니다. 행을 만들고 그 행이 참조하는 자산
둘을 확정하는 두 단계인데, 확정이 실패하면 **행을 지운다**: 방금 만든 행이라 참조하는 것이 없고,
그대로 두면 서빙되지 않는 자산(PENDING)을 가리키는 완성본이 목록에 남는다. 그 카드는 고칠 수도 없다
(재렌더할 잡이 없다). 되돌리면 그 자산들은 PENDING 으로 남아 수거자가 거둔다. 이 경로에는 멱등키가
있다: 업로드가 끝난 뒤 등록만 재시도될 수 있고, 그때 행이 둘이 되면 같은 영상이 두 카드가 된다.

**전체 재렌더에는 예약할 행이 없다**(행은 이미 있다). 그래서 4.3.1 의 순서를 쓸 수 없고 잡이 먼저
만들어진다. 그 잡을 붙이지 못하면 아무도 폴링하지 않는 유료 잡이 남으므로(예전 동작) 1단계 보상이
그것을 취소하고, 그 사이에서 죽으면 복구가 붙이기를 이어 간다. 재렌더에 멱등키는 없다: 같은 산출물을
다시 만드는 것이 그 기능의 목적이라 키를 대상 id 로 잡으면 두 번째 클릭이 막힌다.

**세그먼트 재생성은 순서가 반대다.** 그쪽은 **이미 있는 잡을 다시 돌리는 것**이라 새로 만들 잡이 없고,
예약할 자리가 행 하나뿐이다. 그래서 4.3.1 대로 행을 먼저 RENDERING 으로 옮기고(그 전환이 곧 예약이다)
원격 호출이 실패하면 1단계 보상이 **이전 상태로 되돌린다.** 되돌리지 않으면 아무 일도 시작되지 않은
렌더를 화면이 영원히 기다린다.

**2단계에는 보상이 없다.** 그 시점엔 이미 벤더에 그 씬을 다시 만들라고 보냈고, 되돌리려면 잡 전체를
취소해야 하는데 그러면 **다른 씬까지 죽인다**(이 기능이 지키려는 것이 정확히 그 반대다).

**새 잡을 만들지 않는 것이 이 사가의 요점이다.** 만들면 렌더가 이어서 할 근거(씬 체크포인트)를 못 찾아
전 씬이 다시 돌고 전액 재과금된다. 그래서 렌더가 잡 행에 남겨 둔 씬 결과(`video_jobs.scene_states`)로
체크포인트를 되살린 뒤 대상 씬 하나만 버린다. 비용은 원장에서 따로 다루지 않는다: 종료 전이를 실제로
쓴 쪽(reconcile)이 남기고, 다시 만든 잡의 청구 단위는 렌더가 체크포인트에서 다시 집계하므로
(건드리지 않은 씬의 청구 초가 보존된다) 값이 자동으로 맞는다.

**단계를 쓸 때의 규칙 셋**(엔진이 강제하지 못하고 작성자가 지켜야 하는 것들이다).

1. **산출물을 반환한다.** 다음 단계가 쓸 값은 컨텍스트로 돌려준다. 클로저 변수에 담으면 재개 때
   사라진다(프로세스가 바뀌었다).
2. **재실행에 안전해야 한다.** 진행 기록 직전에 죽으면 그 단계가 한 번 더 돈다. 두 번 돌아도 결과가
   같아야 한다.

   **예약 단계는 이것을 그냥 얻지 못한다.** 그냥 INSERT 하면 재실행이 멱등키 부분 유니크에 걸려
   23505 로 죽고, 첫 실행이 만든 행의 id 는 컨텍스트에 없어(그 쓰기 직전에 죽었다) 보상도 그 행을
   지우지 못한다. 남는 것은 아무도 렌더하지 않는 PENDING 행이고, 그 행은 되돌려진 상태가 아니라
   워크스페이스 목록에 그대로 보인다. 그래서 세 예약 어댑터는 `reserveOnce` 로 충돌을 접어 **같은
   멱등키면 이미 만든 행을 돌려준다**(그 멱등성은 이제 레포지토리 포트의 계약이다).
3. **자기 단계만 되돌린다.** 앞 단계는 그 단계의 `compensate` 가 되돌린다.

**어느 버전의 파이프라인인지는 payload 에 담는다.** 마케팅 영상 도구는 UI 버전이 둘이고 제품으로는
별개다([marketing-tool-versions.md](./marketing-tool-versions.md)). payload 는 불변이라 재개가 늘 처음
요청한 버전으로 진행한다. 재개 시점에 개인 설정 등에서 다시 읽으면 그 사이 사람이 바꿔 둔 값으로
이어져, 만들다 만 산출물이 다른 버전 것이 된다. `hydrate` 가 그 값을 스코프로 되살리며, 모르는 값이면
던져서 사가를 멈춘다(조용히 다른 버전으로 재라우팅하지 않는다).

**컨텍스트에 자격증명을 담지 않는다.** 컨텍스트는 jsonb 로 저장된다. 렌더 스펙에는 조직 API 키가
들어가므로 스펙을 담으면 키가 DB 에 남는다. 그래서 스펙은 컨텍스트가 아니라 **예약 행에서 그때그때
다시 조립한다**(행이 곧 생성 시점 스냅샷이라 값이 어긋나지도 않는다).

이 규칙과 "JSON 왕복이 안전한 값만" 은 **엔진이 저장 직전에 검사한다**(`saga-context.ts`). 둘 다 어겨도
평소 테스트는 통과하고 사고는 뒤에서 드러나기 때문이다. 자격증명은 아무 증상 없이 DB 에 남고, Date 는
재개 경로에서만 문자열이 되어 터진다. 위반이면 그 단계가 실패한다(키 이름은 사가마다 고정이라 한 번
통과하면 계속 통과한다).

**새 사가를 복구 목록에 등록했는지도 검사한다**(`saga-registry.spec.ts`). 소스에서 정의를 찾아
`SagaRecoveryModule` 배열과 맞춘다. 등록을 잊은 사가는 DI 에 나타나지 않아 런타임으로는 "없는 것" 과
"잊은 것" 이 구분되지 않는다.

**예외를 감싸지 않는다.** 러너는 보상을 끝낸 뒤 단계가 던진 예외를 그대로 올린다. 감싸면 컨트롤러의
상태코드 매핑(400/404)이 전부 500 이 된다. 그래서 복구 러너도 성패를 예외 유무가 아니라 **사가 행의
상태**로 판정한다(COMPLETED 와 COMPENSATED 는 둘 다 "더는 걸려 있지 않다" 다).

**복구는 전진을 택한다.** 중단된 사가는 되돌리지 않고 남은 단계를 실행한다. 남은 단계가 값이 있고
(자산 확정, 잡 등록) 재실행에 안전하기 때문이고, 되돌리면 사용자가 만든 것이 사라지는데 크래시는
사용자의 실수가 아니기 때문이다. 남은 단계가 실패하면 그때 보상한다(정상 실패 경로와 같다).

복구가 중단분을 집는 규칙 둘. **유예**: 최종 수정이 5분보다 오래된 것만 집는다(정상 실행 중인 사가를
가로채지 않는다). **claim**: 조회와 claim 을 한 문장으로 해 러너가 여럿이어도 같은 사가를 동시에 집는
일이 드물고, 방금 집힌 것은 유예가 다시 지날 때까지 집지 않는다(계속 실패하는 사가가 매 주기를
독점하지 않는다).

claim 을 잠금으로 보지 않는다. 중복을 좁히는 장치이고, 같은 사가가 두 번 돌아도 안전한 근거는 위의
규칙 2(재실행 안전성)다. 더 강한 배제가 필요해지면 `SELECT ... FOR UPDATE SKIP LOCKED` 로 바꾼다.

**끝난 사가는 30일 뒤에 지운다.** 이 표는 쓰기 시도마다 한 행이 생겨 정리하지 않으면 무한히 자란다.
복구 틱이 같은 자리에서 종료 상태(COMPLETED/COMPENSATED)만 지우며, 진행 중인 것은 어떤 경우에도
대상이 아니다(지우면 이어 갈 근거를 잃는다). 30일인 이유는 사고 조사가 그 안에 끝나고, 사용자에게
보이는 흔적은 활동 원장이 따로 갖기 때문이다.

**실행권은 한 컬럼(`claimed_at`)으로 두 경로가 공유한다.** 요청 경로와 복구 경로가 각자의 컬럼을 쓰면
서로의 실행을 보지 못해 같은 사가를 함께 돌린다. "지금 이 사가를 누가 돌리고 있나" 라는 질문은 하나뿐이니
답을 적는 자리도 하나다.

리스 시간은 두 경로가 다르게 읽는다(요청 30초, 복구 5분). 답하는 질문이 달라서다. 요청 경로는 "지금
살아 있는 실행이 있나" 를 묻고(사가는 수 초에 끝나므로 30초면 넉넉하다), 복구는 "이 사가가 버려졌나" 를
묻는다. 요청 쪽 리스를 5분으로 맞추면 크래시 직후의 재시도가 5분 동안 막힌다.

기다리는 쪽이 정해진 시간(5초) 안에 답을 못 받으면 409(`SAGA_BUSY`)를 받는다. 실패가 아니라 "지금은
대답할 수 없다" 이고, 잠시 뒤 같은 요청이 그 산출물을 그대로 받는다. 앞 실행이 되돌아간 경우(COMPENSATED)
에는 오류를 주지 않고 기다린 쪽이 **자기 실행으로** 처음부터 시도한다(되돌린 뒤라 남은 부수효과가 없다).

**그 창도 닫혔다(벤더 멱등키).** 잡 등록 단계의 재실행은 벤더 잡을 하나 더 만들 수 있었다. 벤더를
부르고 진행을 기록하기 전(쓰기 한 번 폭)에 죽는 경우다. 호출자 쪽에서는 닫을 수 없다: 이미 만들어진
잡을 알아보는 일은 잡을 만든 쪽만 할 수 있다.

그래서 엔진이 단계마다 **재실행에 불변인 키**를 준다(`meta.idempotencyKey` = `saga:<사가 id>:<단계 번호>`).
재실행은 진행 기록 전에 죽은 경우이므로 단계 번호가 그대로다. 잡 등록 단계가 그 키를 video-model 로
보내고(`client_request_id`, 호출자 이름을 접두사로), video-model 은 부분 유니크로 같은 키의 잡이 하나임을
보장한다. 사전 조회로 찾으면 그 잡을 돌려주고, 동시 등록으로 유니크에 걸리면 **재조회해서 이긴 잡을**
돌려준다(실패로 올리면 호출자에겐 실패로 보이는데 잡은 이미 돌고 있다).

키를 컨텍스트에서 만들지 않는 이유: 행 id 같은 값은 그 행이 생기기 전에 호출하는 단계가 쓸 수 없다.
사가 id 와 단계 번호는 언제나 있고, 재시도에는 같고, 사가마다 단계마다 다르다.

## 5. 도입 순서

각 단계는 독립적이다. 앞 단계 없이 뒤 단계를 해도 되고, 멈춰도 그 자리가 지금보다 나쁘지 않다.

| 단계 | 내용 | 마이그레이션 | 상태 |
|---|---|---|---|
| 1 | 취소 = 삭제(4.1) | 없음 | 적용 |
| 2 | 확인 미루기(4.2) | 없음 | 적용 |
| 3 | 멱등키(4.3) + 예약 먼저(4.3.1) | marketingdb `0054` | 적용 |
| 4 | 보상 실패 기록(4.4) | 없음 | 적용 |
| 5 | PENDING 수거자 + 크론(4.4 의 3) | file-upload alembic `0004` | 적용 |
| 6 | 오케스트레이션 사가로 다단계 쓰기 이관(4.5) | marketingdb `0055` | 적용 |
| 7 | 중단분 복구 러너 + 1분 주기 + 운영 엔드포인트(4.5) | 없음 | 적용 |
| 8 | 재렌더 두 경로도 사가로(유료 잡 누출 차단) + 끝난 사가 30일 정리 | 없음 | 적용 |
| 9 | 실행권(동시 중복이 유료 잡을 둘 만들던 구멍) + 409 `SAGA_BUSY` 안내 | 없음 | 적용 |
| 10 | 엔진을 공유 패키지 `@csc/saga` 로 추출(다른 앱이 쓸 수 있게) | 없음 | 적용 |
| 11 | 단계 멱등키 + video-model 잡 중복 접기(마지막 이중 과금 창) | video-model alembic `c8d42f1a` | 적용 |

**남은 것 하나.** fetch abort 는 이 서버와의 소켓만 닫는다. csc-marketing 이 language-model 로 이미 보낸
요청까지 끊으려면 그쪽 취소 엔드포인트가 필요하다(별건).

## 6. 새 쓰기 흐름을 추가할 때의 체크리스트

- [ ] 단계가 둘을 넘고 그중 원격 부수효과가 있는가. 있으면 서비스 메서드가 아니라 **사가 정의**로 짰는가(4.5)
- [ ] 각 단계가 산출물을 반환하고, 두 번 돌아도 결과가 같고, 자기 단계만 되돌리는가(4.5 의 규칙 셋)
- [ ] 컨텍스트에 자격증명이나 큰 스펙을 담지 않았는가. 필요하면 행에서 다시 조립하는가(4.5)
- [ ] 새 사가 종류를 `SagaRecoveryModule` 의 정의 배열에 넣었는가(빠뜨리면 중단됐을 때 방치된다)
- [ ] 중복 제출이 **같은 산출물**을 받는가. 순차만 확인하지 말고 동시도 확인했는가(4.5)
- [ ] 새 오류 응답을 사용자 문장으로 번역했는가. 상태코드만 보고 문장을 지어내지 않았는가(코드로 판별)
- [ ] 원격 부수효과가 있는가. 있으면 **행을 먼저 만드는 순서**로 짰는가(4.2)
- [ ] 장시간 호출이면 `AbortSignal` 을 받고, 그 작업을 화면에서 없애는 액션이 신호를 끊는가(4.1)
- [ ] 재시도 버튼이 붙는가. 붙으면 멱등키가 있는가(4.3)
- [ ] 보상(원격 취소, 자산 삭제)이 실패했을 때 흔적이 남는가. 삼키고 있지 않은가(4.4)
- [ ] 삭제가 산출물을 파괴하는가. 스냅샷으로 살릴 값은 컬럼으로 굳혔는가(`onDelete: 'set null'` 관용)
- [ ] 다중 행 갱신이면 한 트랜잭션인가
