# 마케팅 영상 도구: v1.0 / v1.5 버전 축

마케팅 영상 도구에는 UI 버전이 둘 있고, **제품으로는 별개**다. 화면 구성이 다르고 앞으로 생성
파이프라인도 갈린다. 이 문서는 그 "별개"가 코드에서 어떻게 성립하는지의 단일 출처다.

관련: [marketing-write-consistency.md](./marketing-write-consistency.md)(다단계 쓰기 계약),
[../../.claude/rules/api-architecture.md](../../.claude/rules/api-architecture.md)(헥사고날 규칙).

---

## 원칙 넷

### 1. 버전은 주소다

요청이 버전을 명시하고, 서버는 그것을 다른 데서 유추하지 않는다.

```
web       /{org}/{tool}/{version}/{channel}/...     ← 라우트 세그먼트
BFF       ?version=v1.5                             ← 쿼리(메서드 무관, 눈에 보인다)
backend   /v/:version/saved-plans                   ← 경로 세그먼트
```

**예전에는 서버가 개인 설정에서 "지금 보는 버전" 을 읽었다.** 그래서 화면만 바꾸고 요청을 보내면
다른 버전의 모델과 연출로 만들어질 수 있었고, 진입할 때마다 v1.5 로 리셋해야 그 어긋남을 줄일 수
있었다(그 리셋 자체가 "새로고침하면 다른 데이터가 보인다" 를 만들었다).

| 값 | 어디서 오는가 | 모르는 값이면 |
|---|---|---|
| 지금 보는 버전 | 주소 | **거절한다**(경로 세그먼트 404, 쿼리/경로 파싱 400) |
| 진입 기본 버전 | `marketing_user_tool_settings.version_mode` | 기본으로 좁힌다 |

두 파서가 반대로 동작하는 것이 의도다. 요청을 조용히 접으면 `/v/v9.9/saved-plans` 가 v1.5 목록을
200 으로 내주는데, 그게 곧 크로스 버전 누출이다. 반대로 진입 기본값이 폐기된 버전이라고 도구에 못
들어가면 안 된다.

### 2. 산출물은 버전 소유다

기획안, 원천 영상, 최종 영상은 만들어질 때 **요청이 말한 버전**으로 굳는다
(`version_mode` NOT NULL, DEFAULT 없음). 보는 시점에 판정하지 않는 이유: 판정을 미루면 버전을 바꾼
순간 이미 만든 것이 어느 목록에도 없게 된다.

조회는 스코프 객체로만 가능하다.

```ts
interface OwnerVersionScope { organizationId; ownerUserId; version }   // 단건
interface WorkspaceScope extends OwnerVersionScope { channelId }       // 목록
interface OrgVersionScope { organizationId; version }                 // 조직 공용(보관함)
```

앞의 둘은 개인 축이고 마지막은 조직 축이다. 무엇이 어느 축인지는 아래 "보관함은 축이 다르다" 참고.

버전을 빠뜨린 질의는 **컴파일되지 않는다.** 그리고 소유 검증이 서비스의 `if` 문에서 질의의 WHERE 로
옮겨졌다: 남의 것도 다른 버전 것도 레포가 내주지 않는다(`findOneOwned`).

DB 컬럼에 DEFAULT 를 두지 않는 이유: 기본값이 있으면 컬럼을 빠뜨린 INSERT 가 조용히 한쪽 버전 행을
만들어, NOT NULL 로 조인 목적 자체가 무너진다.

### 3. 갈릴 자리에만 이음새를 둔다

파이프라인이 갈릴 지점은 다섯이고, 각각 포트 + `VersionRegistry<T>` 로 열려 있다.

| 이음새 | 포트 | 고르는 근거 |
|---|---|---|
| 기획안 프롬프트 조립 | `PlanPromptAssembler` | 요청 버전(`scope.version`) |
| 기획 생성 호출과 응답 파싱 | `PlanGeneratorPort` | 요청 버전(`scope.version`) |
| 프로세스 서술(화면이 읽는 단계 목록) | `PlanProcessViewBuilder` | 요청 버전(`scope.version`) |
| 원천 렌더 스펙 조립 | `VideoRenderSpecBuilder` | **행에 굳은 버전**(`project.version`) |
| 최종 합성 스펙 조립 | `FinalRenderSpecBuilder` | **행에 굳은 버전**(`final.version`) |

기획 생성이 이음새인 이유: 갈리는 것은 모델 key 하나가 아니다. 온도와 토큰 예산 공식이 다르고
(기획안 여러 벌 대 영상 한 편), 응답에서 읽는 씬 항목이 다르다. 한 어댑터가 두 스키마를 다 알면
한쪽의 필드 폴백이 다른 쪽 결과에 적용된다(실제로 그랬다). 공유하는 것은 전송과 JSON 복구,
사용량 매핑처럼 **무엇을 물었는지와 무관한 것들**뿐이다.

렌더 두 개가 행의 버전을 보는 이유: v1.0 으로 만든 영상이 v1.5 규칙으로 다시 렌더되면 결과물을
보고서야 안다. 스코프 질의가 이미 요청 버전과 행 버전을 같게 만들지만, 고르는 근거를 행에 두는 편이
의도를 드러낸다.

```ts
type VersionRegistry<T> = Readonly<Record<ToolVersion, T>>;
```

`Record` 가 exhaustive 라, `ToolVersion` 에 값을 하나 더하면 **채우지 않은 레지스트리가 전부
컴파일되지 않는다.** 맵이나 스위치로 두면 런타임에 `undefined` 가 되어 그 버전에서만 조용히 터진다.

**요청 스코프 DI 를 쓰지 않는다.** 사가 복구 러너는 HTTP 요청 밖에서 중단분을 이어 간다. 요청에
매달린 주입은 그 경로에서 성립하지 않으므로, 어디서든 같은 방식(`registry[version]`)으로 고른다.

지금은 두 버전이 같은 동작을 유지한다. 프롬프트는 `core/domain/prompt/{v10,v15}/` 로 **파일이
갈려 있고**(변화가 문구/세그먼트 배열이라 각자 자기 것을 들고 있는 편이 낫다), 렌더 스펙 둘은 같은
구현을 가리키는 두 슬롯이다(변화가 클래스 교체라 복제된 빈 클래스는 차이를 찾게만 만든다).

### 4. 공유 커널은 버전을 모른다

채널, 에셋(공통/세트/카탈로그), 저장소, 활동 원장, 사가 엔진, 렌더 상태. 이들이 버전을 알기
시작하면 축이 다시 흩어진다. 채널 하나 안에서 두 버전의 워크스페이스가 각자 존재하는 것이 의도다.

## 보관함은 축이 다르다

산출물은 개인 축(작업자 × 채널)으로 갈리지만 **보관함(`location='archive'`)은 조직 공용**이다.
같은 표의 두 위치가 서로 다른 스코프를 갖는다.

| 위치 | 조회 스코프 | 타입 |
|---|---|---|
| `personal` | 조직, 작업자, 채널, 버전 | `WorkspaceScope` |
| `archive` | 조직, 버전 | `OrgVersionScope` |

### 어느 표가 보관물을 갖는가

보관함은 **화면 하나**이고 버전마다 따로 있지 않다. 갈리는 것은 그 안에 무엇이 들어가는가다.

| 버전 | 보관물의 표 | 근거 |
|---|---|---|
| v1.0 | `marketing_video_finals` | 세트를 입힌 배포본이 그 버전의 완성물이다 |
| v1.5 | `marketing_video_projects` | 최종 구역이 없어 그 하나뿐인 영상이 곧 배포본이다 |

그래서 **두 표가 같은 `location` 컬럼과 같은 네 메서드**(`findRecordsByLocation` / `findOneArchived` /
`archiveRecord` / `moveArchivedToWorkspaceRecord`)를 갖는다. 규칙과 경계는 위아래 표 그대로 같고,
바뀌는 것은 대상 표뿐이다.

**판정은 BFF 한 곳에서만 한다**(`lib/server/marketing/archiveTarget`, 근거 값은
`versionProfile.archiveSource`). 브라우저에 두면 화면이 어느 표를 고칠지 정하게 되고, 백엔드에 두면
두 도메인 중 하나가 남의 표를 알아야 한다. 버전을 아는 것은 주소를 해석하는 BFF 라 거기서 자원
이름으로 한 번 바꾼다. 브라우저는 버전만 실어 `/api/marketing/archive` 를 부른다.

`archiveSource` 를 `workspaceStages` 의 마지막 값으로 대신하지 않는다. 지금은 같지만 이 값은
**서버가 어느 표에 쓰는지**를 정하고 틀리면 조용히 다른 표를 고친다. 구역 목록의 순서에서 유도하면
구역이 하나 늘어나는 날 그 사고가 저절로 일어난다.

**v1.5 는 보관 조건이 하나 더 있다: 작업 공간에 배치된 것만 보낼 수 있다**(`placed_at`). 배치를
거치지 않은 영상은 아직 만든 사람의 것으로 확정되지 않았고, 확정 없이 조직 공용 공간에 올라가면
만든 사람이 버릴 셈이었던 결과가 남의 눈에 남는다. 화면에서는 고를 방법이 없지만(목록에 없다)
경계는 계약이 지킨다.

**채널로 나누지 않는다.** 채널이 개인 소유(`marketing_channels.owner_user_id`)라 남의 완성본은 남의
채널 id 를 달고 있다. 채널로 묶으면 owner 조건을 떼도 목록이 자기 것만 남아 "공용" 이 성립하지 않는다.
채널은 묶는 키가 아니라 만든 맥락이고, 화면에서는 만든 사람 라벨이 그 역할을 대신한다.

스코프 타입을 따로 둔 이유는 어댑터가 **읽을 수 없는 값은 조건으로 넣을 수도 없다**는 것이다.
`OrgVersionScope` 에는 작업자도 채널도 없어, 보관함 질의가 개인 것으로 좁아지는 실수를 컴파일러가
막는다. 예전에 그렇게 좁아져 있었고, 좁아진 목록은 오류가 아니라 "남의 것이 안 보인다" 로만 드러났다.

동작마다 경계가 다르다.

| 동작 | 누가 | 왜 |
|---|---|---|
| 목록, 다운로드 | 조직 전체 | 공용 공간의 목적 |
| 보내기 | 만든 사람 | 자기 워크스페이스 항목만 보낼 수 있다 |
| 꺼내기 | 누구나 | 원본이 사라지지 않고 **꺼낸 사람** 워크스페이스로 옮겨간다 |
| 삭제 | 만든 사람 + 관리급(대표/팀장) | 되돌릴 수 없는 손실이라 전원에게 열지 않는다. 공용 공간을 정리할 주체는 필요하다 |

**꺼내기는 소유자와 채널을 함께 옮긴다.** 그러지 않으면 남이 만든 항목이 원 소유자의 채널에 남아
꺼낸 사람의 어느 목록에도 나타나지 않는다("꺼냈는데 사라졌다"). 그래서 보내기와 꺼내기가 다른
레포 메서드다(`archiveRecord` / `moveArchivedToWorkspaceRecord`).

**삭제 권한은 BFF 가 판정한다**(세션의 직책을 아는 곳이 거기다). 백엔드는 그 결과를 `manageAll` 로
받아 소유 질의와 소유 무관 질의 중 하나를 고른다. 값이 없으면 소유자 경로로 동작한다: 넓은 쪽이
기본값이 되지 않게.

## 조직 전체 화면이 개인 소유 채널의 이름을 읽는 법

보관함만 조직 공용인 게 아니다. **활동 원장(로그)** 도 조직 전체를 담는다. 그런데 원장의 각 줄은
채널 id 를 달고 있고 채널은 개인 소유다. 그래서 "남의 채널 id 를 이름으로 바꾸는" 통로가 따로
필요하다. 없으면 원장의 채널 컬럼이 전부 "삭제된 채널" 로 보인다. 실제로 그랬다.

| 통로 | 스코프 | 무엇이 오는가 |
|---|---|---|
| `GET /channels` (CHANNEL-003) | 조직 + 주인 | 그 사람의 채널. CRUD 의 입구 |
| `GET /channels/roster` (CHANNEL-015) | 조직 | 조직 전체 채널의 id, 이름, 주인 id **만** |

로스터로는 채널 안의 것(설정, 기획서, 영상)이 오지 않으므로 개인 소유 경계는 유지된다. 이름을
레코드에 스냅샷하지 않는 이유는 멤버 로스터와 같다(개명하면 과거 줄이 옛 이름으로 굳는다).

**이름이 겹치는 문제를 함께 풀어야 한다.** 채널 이름은 주인 안에서만 유일하고 모두에게 기본 채널이
자동 생성되므로, 조직 전체 목록에는 "기본" 이 사람 수만큼 나온다. 규칙은 한 모듈이 소유하고
(`features/marketing-activity-logs/lib/channelOptions.ts`) 표와 필터, CSV 가 그 결과만 소비한다.

| 상황 | 표시 |
|---|---|
| 이름이 조직에서 유일 | `블로그` |
| 이름이 겹침 | `기본 (김보섭)` |
| 주인까지 동명이인 | `기본 (김보섭 (a@x.com))` |
| 주인이 로스터에 없음(퇴사) | `기본 (알 수 없는 사용자 (#99))` |

겹칠 때만 길어진다. 표의 한 칸은 좁고 대부분의 채널은 이름이 겹치지 않는다. 사람을 이메일로
갈라 주는 규칙 자체는 [multi-tenancy.md](../../.claude/rules/multi-tenancy.md) 가 SSOT 다.

## 사가와 버전

버전은 사가 **payload**(불변)에 실린다. context 가 아니다.

```ts
payload: { organizationId, ownerUserId, version, ...입력 }
hydrate: scope = ownerVersionScope({ ..., version: payload.version })   // 모르는 값이면 던진다
```

복구 러너가 중단분을 이어 갈 때 버전을 다시 읽으면(개인 설정 등) 그 사이 사람이 바꿔 둔 값으로
재개해, 만들다 만 산출물이 다른 버전 것이 된다. payload 는 불변이라 재개가 늘 같은 버전으로 진행한다.
모르는 값이면 `hydrate` 가 던져 사가를 멈춘다(조용히 다른 버전으로 재라우팅하지 않는다).

## 화면 폴더는 섹션 축을 따른다

이 도구의 화면 컴포넌트는 `lib/pages/tools/marketing-video/<섹션>/` 에 있다. 폴더 이름은
`WorkspaceSection`(주소의 섹션 세그먼트, `versionProfile.sections`)과 **같은 축**이고, 거기에 둘이
더 있다.

| 폴더 | 담는 것 |
|---|---|
| `create/` | 생성 모달과 그 폼, 섹션들(섹션이 아니라 nav 에서 여는 흐름이다) |
| `workspace/` `assets/` `archive/` `process/` `price/` `log/` `settings/` | 그 섹션 화면과 부품 |
| `shared/` | 두 섹션 이상이 쓰는 것(도구 크롬, 선택 토글, 그리드 등) |

**배치 규칙은 하나다: 한 섹션만 쓰면 그 섹션, 둘 이상이 쓰면 `shared/`.** 그래서 어디에 둘지가
논쟁거리가 되지 않고, 어디에 있는지도 찾기 전에 알 수 있다.

예전에는 44개가 `components/` 한 폴더에 평면으로 있었다. 화면 전체(`LogPage`, 359줄)와 모달 부품
하나(`SegmentModeSection`, 53줄)가 이름만으로 구분되지 않았고, 새 컴포넌트를 어디 둘지 정하는
근거도 없어 계속 그 폴더로 들어갔다.

## 화면 분기

버전마다 갈리는 화면 구성은 한 곳에 있다:
`apps/web/groupware/src/lib/pages/tools/marketing-video/versionProfile.ts`.

| 담는 것 | 쓰는 곳 |
|---|---|
| `sections` (이 버전에 있는 섹션) | 사이드바 nav 목록 + **각 섹션의 서버 게이트** |
| `createLabel` | 생성 버튼 + 위저드 제목/확정 버튼 |
| `tabLabels` | 제작 구역의 이름. 토글이 있으면 탭 라벨, 없으면 **쌓인 구역의 제목** |
| `hasStageTabs` | 워크스페이스에 제작 단계 전환 토글이 있는가 |
| `workspaceStages` | 워크스페이스가 **어떤 제작 구역을 보여주는가** |
| `createModes` (생성 모달의 입력 방식) | 모달 상단 탭 + 어느 폼을 그릴지 |
| `createEyebrow` (무엇을 만드는지) | 모달 본문 머리의 윗줄 |
| `hasPlanCompose` / `hasDirectBriefs` / `hasVideoSettings` / `hasNarrationToggle` | 생성 폼에 그 칸이 있는가 |
| `hasPlanPromptShortcut` | 생성 모달 헤더에 기획서 생성 프롬프트 바로가기가 있는가 |
| `hasGenerationProgress` | 생성 버튼을 누르면 모달이 진행 화면으로 바뀌는가 |
| `hasWorkContinuity` | 끝내지 않은 일로 돌아가는 길을 두는가(하단 탭 + 새로고침 뒤 창 자리) |

### 구역을 몇 개 보여주는가부터 갈린다

v1.0 은 셋이다: 기획안 → 원천 영상 → 프레임 적용. **v1.5 는 하나다: 영상.**

v1.5 의 '영상 생성' 은 누른 한 번으로 **최종 영상까지** 만든다. 파이프라인 전체가 그 창 안에서
끝나므로 나눌 것이 없다. 그 하나의 구역에 서는 영상이 곧 그 버전의 최종본이다.

| 구역 | v1.5 에서 없앤 이유 |
|---|---|
| 기획안 | 도중에 만들어졌다 저장되는 **중간 산출물**이다. 사람이 골라 다음 단계로 넘기는 물건이 아니다 |
| 최종 영상 | 원천에 세트(프레임 + 아웃트로)를 입힌 배포본인데, 세트를 만드는 에셋 화면이 없어 **만들어질 수 없다** |

최종 구역은 그래서 **늘 비어 있었고**, 비어 있는 채로 "세트를 적용하면 최종본이 여기에 만들어집니다"
라며 그 버전에 없는 기능을 가리켰다. `versionProfile.test.ts` 가 `workspaceStages` 에 `final` 이 있는
것과 에셋 섹션이 있는 것을 **같은 조건**으로 잠근다.

**원천과 최종을 별개 행으로 두지 않는다.** 그 버전에서 합성 단계가 없으므로 최종본을 따로 만들면
같은 영상이 두 카드가 된다("영상" 과 "최종 영상" 에 하나씩). 한때 그렇게 만들었다가 되돌렸다.

**보관함도 그래서 원천 표에서 채워진다.** 보관함에 담을 때 최종 행을 새로 만드는 방법이 있었는데,
그러면 방금 되돌린 결정이 되살아난다(한 영상이 두 표에 생긴다). 대신 `marketing_video_projects` 가
최종 표와 같은 `location` 컬럼을 갖고, 그 버전에서는 이 표의 행이 그대로 보관함으로 옮겨간다.
어느 표가 보관물을 갖는지는 `versionProfile.archiveSource` 가 정하고 그 판정은 BFF 한 곳에서만 한다
(`lib/server/marketing/archiveTarget`). 자세한 이유는 아래 "보관함은 축이 다르다".

**구역이 없으면 그 구역을 만드는 동작도 없다.** 세트 적용 피커와 그 하단 동작이 최종 구역과 함께
사라진다. 그 자리는 **보관함 보내기**가 대신한다. 최종 구역이 없는 버전에서는 영상 구역이 곧
완성본이라, 고른 뒤에 갈 곳도 최종 구역이 아니라 보관함이다. 그래서 하단 바의 자리 규칙이 두
버전에서 같아진다: 위 = 다운로드(보조), 가운데 = 이동. 보관함 화면의 하단 바도 같은 규칙이라, 같은
일을 하면서 화면마다 버튼을 다시 찾을 일이 없다.

#### 썸네일은 그 영상에 붙고, 카드에서 따로 열어 본다

생성 결과 화면에서 만든 썸네일은 **그 영상 프로젝트의 컬럼**(`thumbnail_upload_id`)이다. 별도
산출물이 아니라 그 영상의 대표 이미지다.

BFF 가 카드에 실어 주는 그림(`thumbnailUrl`)은 **사람이 붙인 썸네일이 먼저**이고 없으면 첫 씬
이미지로 떨어진다(고른 것이 자동으로 뽑힌 첫 장면보다 그 사람의 의도에 가깝다). v1.5 는 씬 이미지를
만들지 않으므로 그 값은 붙인 썸네일뿐이다.

**그런데 그 그림을 영상 위에 얹지는 않는다.** 완성본 카드는 그 자리에서 영상을 재생하는데, 사람이
만든 썸네일을 `poster` 로 주면 그 그림이 영상의 첫 화면처럼 보여 **영상에 들어간 것으로 읽힌다.**
실제로는 별개 파일이고 배포처에 올릴 때만 쓰인다. 그래서 그 버전에서 카드는 poster 없이 영상 자기
화면을 보여주고, 썸네일은 카드 아래 '썸네일' 로 원래 크기의 창을 열어 거기서 파일로 받는다. 첫 씬
이미지는 반대다: 영상에서 나온 한 컷이라 그대로 poster 로 남는다.

두 갈림이 **한 값으로 갈린다**(`VideoProjectGrid` 의 `thumbnailPreview`). 그 값이 말하는 것은 "이
카드의 그림이 사람이 만든 것인가" 이고, 켜면 따로 열어 보는 버튼이 생기고 poster 자리는 빈다. 판정
근거는 호출부에 있다(그 버전이 씬 이미지를 만드는가). 창은 그리드가 하나만 들고 어느 카드의 것인지만
바꾼다(카드마다 두면 목록 수만큼 마운트된다).

#### 기획안 구역이 없으면 저장이 곧바로 렌더로 이어진다

기획안 구역을 걷는 것은 화면 하나를 지우는 일이 아니다. 거기 두 가지가 걸려 있었다.

1. **자동 저장을 굴리는 것이 그 구역의 라이브 배치**(`PlanBatch` 의 `onProposalComplete`)다. 함께
   빼면 만들어진 기획안이 저장되지 않는다.
2. **기획안을 골라 '영상 만들기'** 가 영상을 만드는 유일한 길이었다. 고를 자리가 없으면 아무도 누르지
   않아 영원히 기획안으로 남는다.

그래서 라이브 배치는 구역이 사라져도 남고, **목록의 첫 구역**(v1.0 은 기획안, v1.5 는 영상)에서 돈다.

**다만 도는 것과 보이는 것은 다르다.** v1.5 의 워크스페이스는 **배치된 영상만 담는다**. 만드는 중인
것도, 다 만들어졌지만 아직 확정하지 않은 것도 그리지 않는다: 그 버전에서 만드는 중이라는 사실은 생성
진행 화면이 말하고, 워크스페이스에 또 칸을 만들면 완성본만 보면 되는 화면에 "아직 영상이 아닌 것" 이
다시 생긴다.

그 규칙이 두 자리에 걸린다. 하나만 막으면 다른 쪽이 그대로 뜬다.

| 자리 | 무엇을 막는가 | 어떻게 |
|---|---|---|
| 라이브 배치 | 기획 생성 중 타일 | `PlanBatch` 가 마운트만 되고 아무것도 그리지 않는다(`showsPlanTiles`) |
| 영상 목록 | 확정 전 프로젝트 카드 | `workspaceRenders(items, placedOnly)` 가 배치된 것만 남긴다 |

판정 근거는 **진행 화면의 유무**(`hasGenerationProgress`)다. 그 화면이 있는 버전은 확정 단계도 함께
갖는다. 없는 버전은 반대로 이 목록이 렌더를 지켜보는 유일한 자리라, 걸러 내면 누른 뒤 아무 흔적도
남지 않는다.

**취소 알림은 이 필터와 무관하다.** 그쪽은 원본 목록을 보므로, 그리지 않는 항목이 사라진 이유도
그대로 통보된다. 진행 화면이 자기 렌더를 찾는 경로도 무관하다(레이아웃의 목록 쿼리를 직접 본다).

한때 그 자리에 기획안 타일이 그대로 그려졌다. 요청 개수만큼 칸이 서고, 눌러 기획안 상세가 열리고,
실패하면 "기획서를 생성하지 못했습니다" 라고 말했다. 컴포넌트를 남긴 이유(자동 저장)와 그리는 것을
가르지 않아서다. 그리고 기획안 구역이 없는
버전에서는 **저장이 끝나는 즉시 영상을 만든다**(`autoCreateVideo`). 사람이 누르는 '영상 만들기' 와
같은 호출이고 모델 점검도 같이 하지만, 멱등키만 다르다: 이 경로는 저장본 하나당 정확히 한 번이라
저장본 id 로 키를 만든다(자동 저장이 재시도로 두 번 성공해도 렌더 잡이 둘이 되지 않게). 사람이 누르는
쪽은 같은 기획안으로 다시 만드는 것이 정상이라 매번 새 키를 쓴다.

**보여주지 않는 것은 받아 오지도 않는다.** 저장된 기획안 목록, 최종 영상 목록, 에셋 세트 SSR 로드를
그 구역이 있는 버전에서만 부른다. 그러지 않으면 답이 정해진 조회를 채널을 열 때마다 하고, 쓰지도 못할
세트 목록을 받아 온다. 화면에서 걷어내는 것과 요청을 걷어내는 것은 다른 일이라, 앞의 것만 하면 낭비가
조용히 남는다(v1.5 의 이미지 GPU 폴링이 같은 경우였다).

### 제작 단계 토글은 단계를 밟는 버전에만 있다

v1.0 은 세 단계를 사람이 순서대로 밟는 구성이라 **지금 어느 단계에 있는지가 곧 화면의 상태**다.
v1.5 는 구역이 하나뿐이라 그 조작이 하는 일 없이 한 번 더 눌러야 하는 자리가 된다. 그래서 v1.5 에는
토글이 없다(`hasStageTabs`).

**하단 확정 바의 동작과 삭제 대상은 "지금 다루는 단계"(`stage`) 하나로 갈린다.** 토글이 있으면 주소가
그 값을 정하고(`?tab=`), 없으면 구역이 하나뿐이라 그것이 답이다. 두 버전이 같은 이름을 읽으므로 그
분기들에는 버전 조건이 하나도 없다.

한때 토글이 없는 버전에서 **선택**이 그 값을 정했다(구역을 여럿 쌓아 두고, 다른 구역을 고르면 이전
선택을 비웠다). 그 버전이 한 구역으로 줄면서 고를 구역이 없어져 그 장치도 함께 걷었다. 같은 이유로
구역 제목도 없다: 토글이 있는 버전은 토글이 말하고, 없는 버전은 나눌 것이 없다.

**빈 구역의 모양은 갈린다.** 토글이 있으면 그 구역이 곧 화면 전체라 크게 비우고, 없으면 짧게 알린다
(`emptyBoxClass`). 빈 구역이 화면 높이만큼 차지하면 새 채널의 첫 화면이 통째로 여백이 된다.

**빈 상태는 그리드가 아니라 그것을 놓는 자리가 갖는다.** 무엇이 없는지도, 그래서 무엇을 하면 되는지도
자리마다 다르기 때문이다(기획안에서 골라 만들라 / 결과 확인에서 저장하라 / 워크스페이스에서 보내라).
한때 `VideoProjectGrid` 가 기본 문구를 들고 있었는데, 그 문구가 맞는 자리는 셋 중 하나뿐이라 나머지
둘이 각자 앞에서 갈라 주고 있었고(보관함은 그 우회를 주석으로 적어 두기까지 했다) 기획안 구역이 없는
버전에서는 화면에 없는 단계를 가리켰다.

**`createModes` 만 버전 사이가 아니라 버전 *안*에서 갈리는 축이다.** v1.5 는 영상 한 편이
목적지라 들어가는 길이 둘이다: 컨셉에서 출발해 기획안을 받거나(`concept`), 만들 영상을 직접
적거나(`prompt`). v1.0 은 기획서가 산출물이라 그 갈림이 없다.

그럼에도 프로필이 갖는 이유는 이 파일의 존재 이유와 같다. 어느 버전이 어떤 방식을 쓰는지는 곧
화면 구성이고, 화면마다 다시 판단하면 버전 조건이 흩어진다. **탭은 방식이 둘 이상일 때만
그린다**(하나뿐인 버전에서 그리면 고를 것이 없는 탭이 된다). 배열의 첫 항목이 기본이고, 모달은
열릴 때마다 거기로 되돌린다. 지난번에 고른 방식이 남아 있으면 다른 것을 만들려고 연 사람이 자기가
고르지 않은 폼을 마주한다.

**목적 키워드는 탭 위에 있다.** 무엇을 다룰지는 어느 방식으로 만들든 같은 결정이라, 방식 안에
두면 탭을 옮길 때마다 같은 값을 다시 고르는 것처럼 보인다. 그래서 키워드 검색 화면도 위저드가
직접 그린다(그 화면은 본문을 통째로 대신하므로 어느 방식에서 열었든 같아야 한다).

모달 본문 머리는 세 줄이다: **무엇을 만드는지**(`createEyebrow`) → **지금 어떤 방식인지**(모드
제목) → **그 방식으로 무엇을 하는지**(모드 설명). 방식을 바꾸면 아래 두 줄이 함께 바뀌고 윗줄은
그대로다. 만드는 것은 방식과 무관하게 같기 때문이다.

윗줄이 따로 필요한 이유는 제목 자리를 방식 이름이 가져가서다. 모달 헤더(`createLabel`)는 지금
누른 동작의 이름이고, 윗줄은 그 동작이 향하는 산출물이다. **머리글도 탭과 같은 조건으로**
그린다(방식이 둘 이상). 하나뿐인 버전에서는 제목이 늘 같은 값이라 헤더가 이미 말한 것을
되풀이하는 줄이 된다.

**컨셉입력 폼은 두 버전이 다르다.** 무엇을 몇 씬으로 담을지를 어디서 정하느냐가 갈린다.

| | v1.0 | v1.5 |
|---|---|---|
| 기획서 구성(기획안 개수, 씬 개수) | 고른다 | **없다** |
| 인포그래픽 배제 | 있다 | 없다(그 섹션 안에 있다) |
| 씬 / 사용자 입력사항 | 없다 | **있다** |
| 제한사항 입력 | 없다 | **있다** |
| 영상 설정(모델, 세그먼트) | 없다 | **있다** |

**직접 적는 지시 두 칸은 한 플래그로 묶는다**(`hasDirectBriefs`). 둘은 같은 결정의 앞뒤다.
무엇을 담을지(씬 입력)와 무엇을 피할지(제한사항)를 사람이 직접 적는다는 것이고, 그래서 늘 함께
있거나 함께 없다. 화면에서는 **카테고리 선택을 사이에 두고** 갈라 놓는다. 무엇을 만들지와 어떤
톤으로를 정한 뒤에야 "다만 이건 하지 말 것" 이 말이 되기 때문이다. 먼저 물으면 아직 정하지 않은
것에 대한 제한을 적게 된다. 프롬프트에서는 반대로 **붙여 둔다**: "이렇게 만들되 이건 피하라" 가
한 덩어리로 읽혀야 한다.

**둘은 서로 배타적이다.** v1.0 은 기획서를 여러 개 뽑아 고르는 흐름이라 몇 개를 몇 씬으로 만들지가
선택이고, v1.5 는 영상 한 편이 목적지라 그 구성을 씬/사용자 입력사항이 정한다. 두 자리에서 같은
것을 정하면 값이 어긋날 수 있고, 그때 모델이 무엇을 따를지 알 수 없다. 그 배타성은
`versionProfile.test.ts` 가 잠근다.

**영상 설정 묶음은 그와 다른 플래그다**(`hasVideoSettings`). 지금은 두 플래그가 같은 버전에서
켜지지만, 무엇을 적을지와 무엇으로 만들지는 다른 결정이다. 한 플래그로 묶으면 한쪽만 필요한
버전이 생기는 날 그 사실이 이름에서 사라진다. `hasNarrationToggle` 은 이 묶음의 **하위 플래그**라
묶음 없이 켜면 아무도 그리지 않는 값이 되고, 그 관계도 같은 검사가 잠근다.

**기획서 생성 프롬프트 바로가기는 v1.0 의 모달에만 둔다**(`hasPlanPromptShortcut`). 그 버전의 모달은
제목이 '기획서 생성' 이라 이 버튼이 지금 만드는 것을 그대로 가리킨다. v1.5 의 모달은 '영상 생성'
이고 기획안은 거기까지 가는 중간 산출물이라 헤더가 만드는 것과 다른 이야기를 하게 되며, 그 버전은
프롬프트 단계가 여럿이어서(기획 → 씬/영상) 그중 하나만 헤더로 끌어올리는 것이 임의적이다.

**편집 경로가 사라지는 것은 아니다.** 같은 편집기를 프로세스 섹션이 사슬 문맥 안에서 연다(편집
가능한 단계에 버튼이 붙고, `canEditSettings` 게이트가 걸린다). 모달은 열 때마다 값을 리셋하므로
그 화면으로 나갔다 오는 비용도 입력 손실이 아니다. 그 근거가 무너지지 않도록 "바로가기가 없는
버전에는 프로세스 섹션이 있다" 를 `versionProfile.test.ts` 가 잠근다.

입력 방식으로 가리지 않는다. 헤더는 그 창 전체의 동작을 담는 자리라 본문 탭에 따라 나타났다
사라지면 안 된다. **모달 마운트도 같은 플래그로 가린다.** 그 중첩 모달은 위저드가 붙어 있는 동안
늘 마운트되고 그 쿼리는 열림 여부가 아니라 채널만 보므로(`enabled: channelId != null`), 버튼만
지우면 그 버전이 쓰지 않는 프롬프트를 채널 페이지마다 계속 받아 온다.

### 생성 진행 화면은 한 번 눌러 영상까지 가는 버전에만 있다

v1.5 의 '영상 생성' 은 한 번 누르면 영상 한 편이 나올 때까지 이어지고 그 사이가 길다(세그먼트마다
모델 호출). 그래서 모달을 닫는 대신 **같은 창을 진행 화면으로 바꾼다**(`hasGenerationProgress`).
별도 창을 하나 더 띄우지 않는 이유는 같은 창의 다른 화면이기 때문이다. 키워드 검색이 이미 그
방식으로 자리를 나눠 쓰고 있어, 위저드는 `view` 하나로 셋을 표현한다(`form` / `keyword` /
`progress`). 불리언을 하나 더 두면 둘 다 참인 표현 불가능한 상태가 생기고, 그때 무엇을 그릴지는
조건문의 순서가 정하게 된다.

v1.0 에는 두지 않는다. 그 버전의 산출물은 기획서 여러 벌이고 영상은 사람이 다음 단계에서 따로
만들어, 진행 화면이 말하는 단계(세그먼트 생성, 영상 병합)를 밟지 않는다. 게다가 그리드 타일이
기획안 도착을 하나씩 보여주고 있어 창을 붙잡아 둘 이유도 없다.

**단계와 가중치는 뷰모델이 소유한다**(`marketing-video/generationProgress.ts`). 가중치 합이 100
이라는 것이 그 표의 계약이고, 어긋나면 다 끝난 생성이 87% 에서 멈춘 것처럼 보인다. 세그먼트 단계의
진척은 **백엔드 `_compose_progress` 와 같은 규칙**(완료 1, 렌더 중 0.5)을 쓴다. 나중에 그 값을 받아
쓸 때 화면의 수가 튀지 않아야 하기 때문이다. 두 규칙 모두 `generationProgress.test.ts` 가 잠근다.

**닫기(Esc/X)는 취소가 아니다.** 생성은 계속 돌고, 그리로 돌아가는 길은 하단 탭이 맡는다(아래).
멈추는 것은 하단의 '생성 취소' 뿐이고, 그 차이를 화면이 한 줄로 말한다. `CenterModal` 은 Esc 를
무조건 닫으므로 막을 수단도 없고, 막을 이유도 없다.

**취소하면 창을 닫는 대신 입력 폼으로 돌아가고, 적어 둔 값은 그대로 남는다.** 취소하는 사람은 대개
무언가를 고쳐 다시 만들려는 것이라, 닫아 버리면 고치려던 자리에서 한 걸음 멀어진다(아래 초안 탭을
거쳐 다시 들어와야 한다). 값이 남는 것은 코드가 아니라 **구조로** 보장된다: 취소 경로가 `open` 을
건드리지 않으므로 리셋 `$effect` 가 돌지 않는다.

#### 끝내지 않은 작업은 하단 탭으로 남는다

**창을 닫아도 하던 일은 계속되는데, 닫고 나면 그리로 돌아갈 길이 없었다.** 이 버전은 완성본을
마지막에 배치해야 워크스페이스에 서므로(아래 '만든 것과 배치한 것은 다르다'), 돌아가지 못한다는
것은 만든 영상을 잃는다는 뜻이다. 완성 전까지 워크스페이스에 아무것도 그리지 않는 버전이라
(기획안 타일이 없다) 무엇이 돌고 있는지 볼 자리도 없었다.

그래서 콘텐츠 열 맨 아래에 **끝내지 않은 작업을 탭으로 남긴다**(`hasWorkContinuity`).

| | | 이유 |
|---|---|---|
| 자리 | 콘텐츠 열 안(사이드바 오른쪽) | 사이드바를 덮지 않고 콘텐츠 폭만 차지한다 |
| 흐름 | in-flow 행(`fixed` 아님) | 본문을 가리지 않는다. 탭이 생기면 본문이 그 높이만큼 줄어들 뿐이다 |
| 목록 | 아래 네 종류 | 비면 바 자체가 렌더되지 않는다(빈 줄이 본문을 좁히지 않게) |
| 누르면 | 그 작업의 화면 | 창이 빈 폼이 아니라 그 작업이 서 있던 자리로 열린다 |

**무엇이 하나의 작업인가, 그리고 그 근거가 어디에 있는가.** 뒤엣것이 새로고침 생존을 가른다.

| 종류 | 근거 | 새로고침 |
|---|---|---|
| 작성 중인 초안(여럿) | 세션 저장소의 폼 값 | 남는다 |
| 미배치 영상 프로젝트 | 서버 행(`placed_at` 이 비어 있고 되돌려지지 않은 것) | 남는다 |
| 라이브 배치 | 이 탭의 메모리(`planGenerationStore`) | 사라진다 |
| dev 미리보기 | 창의 목 상태 | 사라진다 |

**배치가 아니라 프로젝트가 그 작업의 대표다.** 배치는 기획안을 만드는 짧은 구간, 그러니까 서버에
아직 아무것도 없는 동안만 탭을 갖는다. 프로젝트가 생기면 배치 쪽 탭은 빠진다. 둘 다 두면 한 작업이
탭 둘로 보이고, 그중 하나는 새로고침에 사라져 같은 일이 둘이었다는 착각만 남는다.

**그 대표가 넘어간 시점을 배치가 적어 둔다**(`GenerationBatch.projectId`). 저장본 id 만으로 찾으면
"아직 안 만들어졌다" 와 "만들어졌다가 사라졌다" 가 같은 모양(못 찾음)이 된다. 되돌려진 행은 다음
조회부터 목록에서 빠지므로, 그 구분이 없으면 판정이 **되돌림 전이를 실은 응답 한 번**을 붙잡는 일에
걸린다. 그 한 번은 브라우저 탭이 백그라운드였거나 다른 탭이 먼저 받으면 놓친다. id 를 적어 두면
판정이 확정적이다. 적어 뒀는데 목록에 없으면 그 프로젝트는 되돌려졌거나 지워진 것이다.

그 id 를 적는 것은 프로젝트를 만든 화면의 성공 콜백이라 그 사이 화면을 떠나면 유실될 수 있다.
그때는 전이를 실은 응답을 보는 기존 근거가 그대로 남는다(둘 중 하나면 걷는다). 잃는 것은 확정성뿐이다.

**되돌아가기는 상태 복원이 아니다.** 진행은 창의 상태가 아니라 서버 상태의 투영이라(아래 '진행
화면은 서버 상태의 투영이다'), 무엇을 관측할지(배치 또는 프로젝트)와 시작 시각만 있으면 창을 닫은
사이의 진행까지 그대로 다시 그려진다. 시작 시각은 **창이 아니라 그 작업이 갖는다**: 배치는
`GenerationBatch.startedAt`, 프로젝트는 서버의 `created_at` 이다. 창이 열 때마다 `Date.now()` 를
쓰면 3분째 돌던 생성이 00:00 부터 다시 세어진다.

**끊을 대상이 없으면 '생성 취소' 를 그리지 않는다.** 새로고침 뒤 프로젝트로 되돌아온 작업은 그
생성을 붙잡고 있던 배치가 이 탭의 메모리와 함께 사라졌다. 버튼을 남기면 눌러도 아무 일이 일어나지
않는다. 그 작업은 서버에서 끝까지 돌고, 이 화면은 결과를 이어 보여준다.

**탭이 사라지는 자리는 전부 그 작업이 끝난 순간이다.**

| 언제 | 어떻게 |
|---|---|
| 배치를 확정했다 | 서버가 `placed_at` 을 찍어 미배치 목록에서 빠진다(셸은 그 배치와 입력 초안도 함께 걷는다) |
| 생성을 취소했다 | 취소 사가의 `releaseBatch` |
| 렌더가 되돌려졌다 | 목록에서 빠지고, 셸이 그 배치도 걷는다(적어 둔 프로젝트가 목록에 없다) |
| 초안을 비웠다 | 저장 칸이 비고 탭도 함께 사라진다(따로 지우는 자리가 없다) |

되돌려진 행은 다음 폴링부터 목록에서 빠지므로(`visibleRenders`) 그대로 두면 진행률이 멈춘 채 굳는다.
사유를 여기서 또 알리지는 않는다. 같은 전이를 보고 워크스페이스가 이미 알림을 띄운다.

**완료된 작업은 남긴다.** 배지가 진행률에서 '결과 확인' 으로 바뀌어 눌러야 할 이유를 말한다. 여기서
걷으면 배치하지 않은 완성본으로 돌아갈 길이 사라진다.

#### 적어 두던 것도 하나의 작업이고, 여러 개를 가져간다

**폼을 채우다 닫은 창도 탭으로 남는다.** 이 창은 열 때마다 값을 리셋하므로, 탭이 없으면 닫는 순간
적어 둔 것이 사라졌다. 새로고침이면 더 확실히 사라졌다. 그래서 폼 값을 세션 저장소에 담고
(`create/planDraft.ts`) 그 탭으로 이어 쓴다.

**초안은 여럿이다.** 하나만 두면 새 영상을 만들려고 창을 여는 순간 앞서 적던 것이 지워진다. 영상
작업은 여러 개를 동시에 가져가는 일이고(생성이 이미 그렇다) 그 시작점이 초안이라, 초안도 각자 id 를
갖고 각자 탭을 갖는다. 목록은 스토어가 들고(`planDraftStore`) 저장소 읽기, 쓰기는 그 아래
`planDraft` 가 한다. 두 곳이 함께 보기 때문이다: 창은 그중 하나를 편집하고 셸은 전부를 탭으로 세운다.

| 무엇을 하면 | 초안은 |
|---|---|
| 나브의 생성 버튼 | 새 id 로 시작한다(앞서 적던 것은 자기 탭을 지킨다) |
| 초안 탭 | 그 id 를 폼에 올려 이어 쓴다 |
| 제출 | 남는다. 그 배치가 가리키므로 탭에는 서지 않는다 |
| 취소로 폼 복귀 | 같은 id 로 돌아온다(값이 폼에 그대로다) |
| 만든 영상을 배치 | 함께 정리된다(그 입력으로 만들 것을 다 만들었다) |
| 배치가 실패로 걷힘 | 남아 다시 탭으로 선다(적은 것으로 다시 시도한다) |
| 폼을 비움 | 그 자체로 사라진다(내용 없는 초안은 저장이 아니라 제거다) |
| 탭의 닫기(×) | 그 하나만 버린다 |

**빈 폼은 초안이 아니다.** 브랜드와 연출 조합과 영상 모델은 창이 열리면서 저장값으로 스스로
채워지므로 그것까지 세면 열어 보기만 하고 닫아도 탭이 생긴다. 사람이 실제로 손댄 자리는 셋이다:
씬 입력사항, 제한사항, 목적 키워드.

**적는 중인 화면에서 저장한다.** 폼과 키워드 검색 둘이다. 폼만 세면 목적 키워드를 고르러 들어간
사이에 적어 둔 것이 초안이 아니게 되고, 그 상태로 새로고침하면 적은 것이 전부 사라진다. 사람이
보기에 그 화면은 여전히 적는 중이다.

**제출한 초안은 지우지 않는다.** 되살릴 수 없는 것은 돌던 생성이고 사람이 적은 입력은 아니다.
자세한 이유와 정리 시점은 아래 "열려 있던 창은 열린 채로 다시 선다" 에 있다.

**저장과 탭은 다른 시점이다.** 저장은 적는 동안 늘 하고(새로고침을 넘기려면 그 순간의 값이 이미
남아 있어야 한다), 탭으로 세우지 않는 것은 **지금 편집 중인 그 하나뿐이다.** 열려 있는 창이 곧 그
초안이라 겹쳐 세울 이유가 없고, 세우면 in-flow 인 바가 오버레이 뒤에서 자리를 차지해 본문이 밀려
올라간다. 나머지 초안은 그대로 둔다: 창을 여닫을 때마다 줄 높이가 요동치지 않는다. 어느 것이
편집 중인지는 창만 아는 사실이라 셸에 함께 보고한다(`editingDraftId`).

**초안 탭은 닫기(×)를 갖는 유일한 탭이다.** 여기서 끝낸다는 것은 적어 둔 것을 버린다는 뜻이고 그
판단은 이 줄에서 끝난다. 돌고 있는 생성은 그렇지 않다. 끊는 것은 유료 작업을 되돌릴 수 없게
버리는 일이라 확인을 거쳐야 하고, 그 자리는 창 안의 '생성 취소' 다. 바에 ×를 달면 스치는 손짓
하나로 몇 분치 렌더가 사라진다.

**×는 스토어와 창 둘 다에 닿는다.** 목록에서 빼는 것으로 끝나지 않는다. 그것이 지금 편집 중인
초안이면 폼도 비워야 한다. 값이 남아 있으면 다음 입력에 같은 id 로 다시 저장돼 탭이 되살아난다.

**세션 저장소를 쓴다.** 수명이 그 약속과 같기 때문이다. 이 도구는 새 탭으로 열리고, 그 탭을 닫는
것은 사람이 이 작업을 접은 것이다. 브라우저를 다시 켰을 때까지 남으면 언제 적었는지 모르는 입력이
폼에 들어와 있다. 칸은 채널과 버전으로 갈린다. 두 워크스페이스는 별개 제품이라 한 칸을 나눠 쓰면
다른 채널에서 적던 것이 이 폼에 뜬다.

**채널을 옮기면 창을 닫고, 그 채널의 칸을 새로 읽는다.** 이 셸은 채널 전환에 리마운트되지 않아
열려 있던 창과 이미 읽은 칸이 그대로 남는다. 창은 앞 채널의 작업을 가리킨 채 새 채널 목록에서
그것을 찾다가 빈 폼으로 떨어지고, 칸을 다시 읽지 않으면 옮겨 간 채널의 초안이 영영 보이지 않는다.
창 자체도 채널마다 다시 만든다(`{#key}`): 창은 자기 편집 버퍼를 들고 있으므로 그러지 않으면 앞
채널에서 적던 값이 다음 채널 칸에 저장된다.

**dev 진행 화면 미리보기도 자리를 하나 갖는다.** 그 흐름은 배치도 프로젝트도 만들지 않아 어느
목록에도 오르지 않는데, 그것만 탭 밖에 두면 dev 에서 '닫고 되돌아오기' 를 확인할 방법이 사라진다.
그 확인이 미리보기의 존재 이유다(아래 '끝맺음' 4번과 같은 근거). 그래서 창이 자기 상태를 셸에
알리고(`previewRunning`), 셸이 dev 에서만 그 자리를 만든다. 목 상태는 창을 닫아도 남아 있어
되돌아올 때 되살릴 것은 시계뿐이다.

#### 열려 있던 창은 열린 채로 다시 선다

**새로고침은 이 탭의 기억만 지운다. 하던 일은 대개 남아 있다.** 렌더는 서버에서 계속 돌고 적어 둔
것은 저장 칸에 있는데 창만 닫힌 채 다시 뜨면, 사용자는 자기가 보던 진행이 사라졌다고 읽는다. 그래서
창의 자리(열려 있었는가, 무엇을 다루던 창인가)를 함께 남긴다(`shared/workSession.ts`).

**남기는 것은 되살릴 수 있는 목표뿐이다.**

| 다루던 것 | 남기는 값 | 왜 |
|---|---|---|
| 서버 작업(프로젝트) | 그대로 | 서버 행이 근거다 |
| 작성 중인 초안 | 그대로(id 까지) | 저장 칸이 근거다 |
| 라이브 배치 | 그것이 만든 프로젝트, 아직 없으면 그 배치를 시작한 초안 | 배치는 메모리에만 있어 그 이름으로는 다시 찾을 수 없다. 무엇으로 대신 가리킬지는 셸이 안다 |
| dev 미리보기 | 남기지 않는다 | 목 상태라 되살릴 근거가 없다 |
| 목표 없이 폼을 채우던 창 | 편집 중인 초안으로 | 그대로 두면 다시 들어온 창이 리셋을 거쳐 새 초안을 시작한다 |

**서버 작업을 가리키던 창은 목록이 도착한 뒤에 세운다.** 그 작업이 아직 살아 있는지는 목록을 받아야
알기 때문이다. 받기 전에 열면 창이 없는 것을 관측하다가 빈 폼으로 떨어진다. 이미 배치했거나 사라진
작업이면 열지 않는다. 그 창은 할 일이 없고, 열어 두면 끝난 일을 다시 끝내라는 화면이 된다.

**복원이 끝나기 전에는 자리를 쓰지 않는다.** 그때의 화면은 아직 그 세션이 아니라서, 지금 쓰면
되살릴 값을 스스로 덮어쓴다.

**이어지지 않는 구간이 하나 있다.** 기획안 텍스트를 만드는 동안의 새로고침이다. 그 호출은 브라우저
쪽 쿼리라 탭과 함께 끊기고, 이 버전의 자동 저장은 그 응답이 도착한 뒤에 돌아 아직 아무것도 남지
않았다. 서버가 그 생성을 자기 것으로 들고 있게 되면 그때 프로젝트와 같은 자격으로 이 표에 들어온다.

**그래도 적은 것은 남는다.** 되살릴 수 없는 것은 돌던 생성이고 사람이 적은 입력은 아니다. 그래서
**제출한 초안을 지우지 않는다.** 배치가 자기를 시작한 초안을 가리키고(`GenerationBatch.draftId`),
새로고침으로 배치가 사라지면 창은 그 초안으로 다시 서서 적은 그대로를 보여준다. 다시 눌러 만들면
되고, 처음부터 다시 적지 않는다.

살아 있는 배치가 가리키는 초안은 **하단 탭에 서지 않는다.** 그 작업의 탭이 이미 그것을 대표하므로,
둘 다 세우면 한 작업이 탭 둘로 보인다. 그 초안이 정리되는 시점은 **만든 영상을 배치할 때**다(그
입력으로 만들 것을 다 만들었다). 배치가 실패로 걷히면 초안은 남아 다시 탭으로 선다.

**적는 중인 화면에는 키워드 검색도 든다.** 폼만 세면 목적 키워드를 고르러 들어간 사이에 적어 둔 것이
초안이 아니게 되고, 그 상태로 새로고침하면 적은 것이 전부 사라진다. 사람이 보기에 그 화면은 여전히
적는 중이다.

**바는 도메인을 모른다**(`shared/ui/navigation/BottomTabBar.svelte`). 담길 것을 탭 모양으로 옮기는
것은 도구 쪽이고(`marketing-video/shared/workTabs.ts`), 진행률은 창이 쓰는 것과 같은 번역
(`renderProgress`)을 지난다. 각자 계산하면 같은 순간에 다른 수를 말한다.

셸은 어느 목록에서 오는지만 정하고, **순서와 포함 규칙은 그 파일의 `composeWorkTabs` 하나가 갖는다.**
작업 종류가 늘 때 고칠 자리가 한 곳이고 그 규칙을 테스트가 잠근다. 탭 id 를 만드는 자리도 `switch`
라, 종류를 더하면서 빠뜨리면 컴파일이 막는다(if 사슬이면 새 종류가 조용히 남의 id 를 받는다).

자기 높이는
`bottomInsetStore` 에 등록하므로 하단 고정 오버레이(토스트, 선택 확정 바)가 그만큼 비켜선다.

**탭 하나가 요청 하나가 되지는 않는다.** 탭 전부가 목록 조회 하나에서 파생된다(그리드와 같은 키라
캐시와 폴링을 공유한다). 그 조회를 **탭이 있는 버전에서는 늘 켠다**: 이 목록이 곧 탭의 근거라
"탭이 있으면 켠다" 로 두면 켤 근거를 그 목록에서 얻어야 해서 아무것도 뜨지 않는다. 새로고침 직후가
정확히 그 상태다.

늘 켜도 상시 폴링은 아니다. 재조회 간격은 **렌더 중인 항목이 있을 때만** 붙고(`hasRendering`),
끝났는데 배치하지 않은 작업만 남으면 멈춘다. 그래서 4초 폴링이 도는 구간은 실제로 무언가 만들고
있는 동안뿐이고, 그때는 그 진행률을 보는 사람이 있다. 셸의 구독은 레이아웃 수명 하나뿐이라 섹션을
오가도 다시 받지 않는다.

#### 취소는 사가다

취소는 한 동작으로 보이지만 셋이고(요청 중단 → 목록 제외 → 캐시 제거), **순서가 틀리거나 중간에
멈추면 조용히 돈이 나간다.**

| 어긋남 | 결과 |
|---|---|
| 멈추기 전에 걷어냄 | 화면에서는 사라졌는데 LLM 은 끝까지 돌아 과금된다 |
| 멈추기만 하고 안 걷어냄 | 끝나지 않는 타일이 남는다 |
| 절반만 되고 폼으로 돌아감 | 사용자가 다시 누른다. 아직 도는 것과 새로 시작한 것 **둘 다** 과금 |

마지막 줄은 폼으로 돌아가게 되면서 새로 생긴 위험이다. 그래서 `cancelGeneratingBatch` 는 **전부
성공했을 때만 true** 를 주고, 진행 화면은 그 값이 참일 때만 폼으로 돌아간다. 실패하면 그 자리에
머물고 사유를 알린다(조용히 실패하면 멈춘 줄 알고 넘어간다).

**엔진은 `@csc/saga` 가 아니라 브라우저용 러너다**(`shared/lib/saga/clientSaga.ts`). 그 패키지는
단계 번호를 DB 에 적고 실행권으로 중복 실행을 막고 복구 스케줄러가 중단분을 이어 가는 durable
오케스트레이터인데, 셋 다 프로세스가 죽어도 상태가 남는다는 전제 위에 있다. 브라우저에는 그 전제가
없다: 탭이 죽으면 소켓이 닫혀 요청은 저절로 끊기고 적어 둔 것도 함께 사라지며 이어 갈 주체도 없다.
그래서 저장소와 실행권과 복구는 두지 않고 **계약(`name`/`execute`/선택적 `compensate`, 산출물은
컨텍스트로 반환)만 같게** 맞춘다. 한쪽을 읽은 사람이 다른 쪽을 그대로 읽을 수 있어야 하기 때문이다.

**보상이 하나 있다**: `releaseBatch` 는 되돌릴 수 있다. 걷어낸 뒤 단계가 실패하면 아직 도는 작업이
화면에서 사라진 채 남는데, 그때 사용자는 멈춘 줄 알지만 과금은 계속된다. 되돌려 놓아야 보이고 다시
시도할 수 있다. 그리고 **language-model 쪽 취소 엔드포인트가 생기면 이 배열에 단계로 들어온다**
(marketing-write-consistency.md 4.1 이 그 한계를 적어 둔다). 원격 호출이라 실패할 수 있고 실패하면 뒤
단계로 가면 안 되는데, 그 규칙이 이미 여기 있다.

**취소는 그리드 타일의 삭제와 같은 사가를 쓴다**(`lib/cancelGeneratingBatch.ts`). 그리고 쿼리 두 개는
**키가 어긋나도 에러를 내지 않는다.** 실제로 버전 축이 생성 쿼리에 추가됐을 때 취소 쪽 사본만 옛
모양으로 남아, 타일은 사라지는데 LLM 은 끝까지 돌아 조직에 과금됐다. 그래서 키 조립은
`plans.query.ts` 가 소유하고(`planBatchQueryKey`) 그것을 쓰는 취소 경로는 하나다.
`cancelGeneratingBatch.test.ts` 가 키와 순서와 실패 처리를 함께 잠근다.

**끝났다는 것은 값으로 받는다.** 단계 목록의 마지막은 가중치 0 인 종료 상태(`COMPLETED`)다.
"마지막 단계이고 세그먼트가 다 완료" 로 역추론하면 병합만 남은 순간과 진짜 완료가 구분되지 않는다.

**끝나도 결과로 자동으로 넘기지 않는다.** 그 사이에 재생성이 있을 수 있고, 넘어가 버리면 세그먼트를
다시 볼 기회가 없다. 그래서 완료는 화면을 바꾸는 대신 하단 버튼을 '생성 취소' 에서 **'결과 확인'** 으로
바꾼다(끊을 것이 남아 있지 않으므로 취소는 사라진다). 넘어갈 시점은 사람이 정한다. 경과 시간도 그때
함께 멈춘다. 끝난 작업의 시계가 계속 늘면 아직 도는 것처럼 읽힌다.

#### 결과 확인은 병합된 영상을 다룬다

세그먼트를 하나로 합치는 것은 진행 화면의 일이다(영상 병합 단계). 결과 확인 화면에 합치기 버튼이
없는 이유가 그것이다. 사람이 한 번 더 눌러야 할 일이 아니고, 누르지 않으면 아무것도 완성되지 않는
중간 산출물을 남기게 된다. 이 화면이 하는 일은 셋이다: 확인, 내려받기, 그리고 그 영상의 한 프레임으로
**대표 썸네일 만들어 붙이기**.

**정보 표는 값이 없는 줄을 그리지 않는다.** 빈 칸은 아직 오지 않은 값처럼 읽힌다. 그래서 길이를 모르면
세그먼트 수만 적는다(`0초` 라고 쓰면 길이가 0 인 영상이 만들어진 것처럼 읽힌다).

**외부 보관 주소(Google Drive 등)는 자리만 있고 값은 아직 없다**(`driveUrl`). 자리를 미리 두는 이유는
그 값을 넣는 곳이 생겼을 때 화면을 고칠 일이 없어야 해서이고, 지금 그럴듯한 주소를 채우지 않는 이유는
눌러 본 뒤에야 아무 데도 가지 않는다는 것이 드러나기 때문이다. 값이 있으면 줄과 함께 다운로드 안내
문장도 그 링크를 가리키도록 바뀐다. 주소는 표의 좁은 값 칸에 맞게 가운데를 줄여 적는다
(`shortLinkLabel`): 그대로 두면 그 한 줄이 표 높이를 두세 배로 늘려 위의 실제 정보를 가린다.

**다운로드는 `<a download>` 로 하지 않는다.** 결과물이 다른 오리진(file-upload)에 있어 그 속성이
무시되고, mp4 가 inline 으로 서빙되어 저장 대신 재생이 시작된다. 그 우회는 `downloadUrlAsFile` 이
이미 갖고 있다.

#### 만든 것과 배치한 것은 다르다

**렌더가 끝났다고 그 영상이 작업 공간의 것이 되지는 않는다.** 확정 단계를 가진 버전(v1.5)에서는
생성 창의 마지막 버튼('영상 생성')을 눌러 **배치**해야 목록에 선다. 그 표시가
`marketing_video_projects.placed_at` 이고, 목록 필터는 그 값 하나만 본다(`workspaceRenders`).

| | 확정 단계 있음(v1.5) | 없음(v1.0) |
|---|---|---|
| 워크스페이스에 서는 것 | **배치된 영상**만 | 만들어진 것 전부(렌더 중 포함) |
| 무엇이 확정인가 | 창의 마지막 '영상 생성' | '영상 만들기' 를 누른 그 순간 |
| `placed_at` | 그 버튼이 찍는다 | 보지 않는다(목록이 조건으로 걸지 않는다) |

그래서 확정 단계가 없는 버전에는 이 컬럼이 없는 것과 같다. 기본값을 두지 않는 이유가 그것이다:
값을 찍는 것은 그 단계를 가진 흐름뿐이다.

**완성 여부를 따로 걸지 않는다.** 배치는 완성본에만 열려 있으므로(서버가 400 으로 막는다) 배치된
것은 이미 완성본이다. 두 조건을 겹치면 같은 규칙을 두 곳에서 정하게 된다.

#### 끝맺음은 하단의 '영상 생성' 하나다

이 창의 마지막 버튼이 그 흐름을 끝낸다: **만든 영상을 썸네일과 함께 작업 공간에 배치하고 서버에
남긴다.** 라벨이 창을 연 버튼과 같은 이유는 그 한 번의 '영상 생성' 이 여기서 끝나기 때문이다.

**v1.0 과 근본적으로 다른 지점이 여기다.** v1.0 에서 산출물을 만드는 것은 워크스페이스의 '영상
만들기' 이고 생성 창은 기획서까지만 만든다. v1.5 에서는 창 안에서 파이프라인이 끝나고, 그 결과를
자기 것으로 확정하는 동작이 이 버튼 하나다. 그래서 이 버튼은 배치와 저장을 함께 한다.

**끝맺음을 둘로 두지 않는다.** 한때 썸네일 상자 안에 저장 버튼을 따로 두고 하단은 '닫기' 였는데,
그러면 어느 것을 눌러야 끝나는지 알 수 없었다. 지금 상자 안에 남은 것은 받아 가는 동작
('썸네일 다운로드')뿐이다.

네 가지가 이 동작의 계약이다.

1. **여러 번 눌러도 결과는 하나다.** 배치 시각은 처음 것을 유지하고 썸네일만 갈아 끼운다(서버가
   이전 그림을 지운다). 그래서 멱등키가 없다: 중복이 남기는 것도 쓰는 돈도 없다.
2. **실패하면 창을 닫지 않는다.** 닫아 버리면 방금 만든 영상이 어느 목록에도 없는 채로 사라지고
   되찾을 길이 없다. 사유를 알리고 그 자리에 머문다.
3. **그림을 만들지 못해도 배치는 한다.** 프레임이 다른 오리진이라 캔버스를 옮기지 못하는 경우가
   있는데, 그림이 없는 것과 영상을 잃는 것은 무게가 다르다.
4. **dev 프리뷰도 실제 행을 만든다.** 그 프리뷰가 있는 이유가 이 흐름을 돈 들이지 않고 끝까지 보는
   것이고, 이 버튼의 일에는 저장이 포함되므로 그것까지 가야 확인이 끝난다. 그래서 병합된 영상과
   썸네일을 실제로 올리고 dev 전용 경로(`[VIDEO-027]`)로 **완성 + 배치 상태의 행**을 만든다.
   렌더 잡만 없고 나머지는 실제 산출물과 같아, 그 뒤의 목록과 보관과 삭제가 실제와 같은 경로로
   동작한다.
   한때 카드를 목록 캐시에만 얹었다. 그러면 카드는 서지만 그 뒤 동작이 전부 서버가 모르는 id 로
   나가 400 이 되어(`-Date.now()` 가 경로에 실렸다) 확인하려던 흐름이 그 자리에서 끊겼다.
   **아끼는 것은 렌더 비용이고, 저장은 비용이 아니다.** 그 경로는 운영에 존재하지 않는다(BFF 와
   백엔드가 각각 404 로 답한다: 렌더 없이 완성본을 만드는 기능은 제품에 쓸 데가 없다).
   **이 경로만 위 1번의 예외다: 멱등키가 있다.** 실제 배치는 이미 있는 행을 고치므로 몇 번 눌러도
   결과가 하나지만, 이쪽은 누를 때마다 **행을 만든다.** 업로드가 끝난 뒤 등록만 재시도되면 같은
   영상이 두 카드가 된다.

**대가가 하나 있다.** 배치하지 않고 창을 닫으면 그 영상은 어느 목록에도 나타나지 않는다(만들어진
것은 서버에 있지만 화면에서 닿을 길이 없다). 그래서 진행 화면과 결과 화면이 그 사실을 각각 한 줄로
말한다. 미배치 영상을 되찾는 자리는 아직 없다.

**편집기는 그림 대신 '만드는 함수' 를 창에 건넨다**(`onExporterReady`). 저장이 창의 동작이고 그림은
편집기의 것이라, 미리 만들어 넘기면 그 뒤의 편집이 반영되지 않는다. 누르는 순간 그려야 "보이는 것이
곧 저장되는 것" 이 유지된다.

쓰기 자체(갱신 → 확정 → 실패 시 되돌리기)는 사가가 아니다. 되돌릴 것이 컬럼 하나뿐이라서다:
[marketing-write-consistency.md](./marketing-write-consistency.md) 4.2 의 씬 이미지 교체와 같은 모양이다.

#### 썸네일은 브라우저 안에서 끝난다

프레임 선택도 합성도 저장도 전부 캔버스가 한다(`thumbnailOverlay.ts` + `create/ThumbnailStudio.svelte`).
서버로 보내 자르고 받아 오는 왕복이 없어 슬라이더를 움직이는 대로 즉시 보인다.

**미리보기가 곧 결과물이다.** 화면의 미리보기와 저장되는 파일을 **같은 함수**(`drawThumbnail`)가
그린다. 미리보기를 DOM 으로 얹고 저장만 캔버스로 그리면 줄바꿈, 자간, 그림자가 미묘하게 달라져 "보이는
것과 받은 것이 다른" 상태가 되고, 그 어긋남은 파일을 열어 봐야 드러난다. 같은 이유로 문구의 위치와
크기는 **정규화 좌표(0~1)** 로 든다. 미리보기는 화면에 맞춘 작은 캔버스이고 저장본은 큰 해상도라
픽셀로 들면 둘이 어긋난다.

**받아 두기와 영상에 붙이기가 같은 그림을 쓴다**(`exportPng`). 하나는 상자 안의 다운로드, 다른 하나는
창 하단의 마지막 동작이고, 둘 다 누르는 순간 그려지므로 그때까지의 편집이 그대로 반영된다.

**영상 태그에 `crossorigin="anonymous"` 가 필요하다.** 없으면 프레임을 캔버스에 그리는 순간 캔버스가
오염되어 `toBlob` 이 던진다. file-upload 의 CORS 허용 목록에 web 오리진이 등록돼 있어 성립하는
전제이며, 그 전제가 깨지면 저장이 실패하고 화면이 사유를 알린다(프레임 없이 몰래 저장하지 않는다).

**바탕은 셋 중 하나다.** 고른 영상 프레임 → 대표 이미지(`posterUrl`) → 단색. 프레임이 먼저인 이유는
사람이 고른 것이 대표 이미지보다 그 사람의 의도에 가깝기 때문이고, 대표 이미지를 두는 이유는 프레임을
쓰지 못하는 경우가 여럿이기 때문이다(주소가 아직 없거나, 로드에 실패하거나, 캔버스로 옮기지 못하거나).
그때 한 장이라도 있으면 썸네일 만들기가 통째로 막히지 않는다. 프레임을 고르는 일만 못 한다. 셋 중
무엇이 쓰이는지는 스크러버 아래 한 줄이 말한다.

#### 진행 화면은 서버 상태의 투영이다

진행 값은 이 창의 상태가 아니라 **관측한 영상 프로젝트를 번역한 것**이다. 셸이 목록 쿼리(그리드와
같은 키라 캐시와 폴링을 공유한다)에서 이 배치의 프로젝트를 찾아 넘기고, 창은 그것을 화면 어휘로
옮긴다. 그래서 **창을 닫았다 다시 열어도 진행이 이어 보인다**: 창이 기억하고 있던 것이 아니라 서버가
말한 것을 다시 그리기 때문이다.

배치와 프로젝트를 잇는 실은 **저장본 id** 하나다(`planGenerationStore.linkRender`). 배치는 화면 쪽
개념이고 프로젝트는 서버 쪽 개념이라, 자동 저장이 남긴 그 id 말고는 둘을 잇는 값이 없다. 목록에서
"방금 만든 것" 을 시각으로 추정하면 연달아 두 번 누른 경우에 어긋난다.

번역 규칙은 `marketing-video/renderProgress.ts` 한 곳에 있다.

| 관측 | 단계 |
|---|---|
| 프로젝트 없음 + 나누는 중 | 세그먼트 나누기 |
| 프로젝트 없음 + 다 나눔 / 잡이 아직 안 집힘(PENDING) | 영상 준비 |
| 렌더 중 + 씬을 만드는 중(SCENES) | 세그먼트 생성 |
| 렌더 중 + 다 만들고 이어붙이는 중(FINALIZING) | 영상 병합 |
| 완료 | 완료 |

**이 화면은 '기획' 이라는 말을 쓰지 않는다.** 단계 이름이 오래 v1.0 의 산출물 이름이었는데
('기획안 작성', '프롬프트 생성') 정작 **v1.0 에는 이 화면이 없다**(`hasGenerationProgress`). 그래서
그 이름이 v1.5 에서만 보였고, 영상을 만들라고 누른 사람에게 지금 기획안을 쓰는 중이라고 말했다.
게다가 둘째 칸은 그 버전에서 프롬프트를 만들지도 않는다(저장하고 렌더 잡을 만드는 구간이다).

기획 LLM 호출 자체는 남는다. 그 버전에서 그것이 하는 일이 **입력을 세그먼트로 나누는 것**이고,
나뉜 결과가 곧 아래 격자의 칸이다. 화면은 그 일을 그 이름으로 부른다.

**격자는 프로젝트가 생긴 뒤에 나타난다.** 그 전에는 격자 자리에 로딩 인디케이터와 그 단계의 말
(나누는 중 / 준비하는 중)이 있고, 요약의 세그먼트 칸도 수가 아니라 "계산 중" 이다. 그 말은 단계
표(`generationProgress.ts` 의 `awaitingSegments`)가 갖는다. 화면이 단계마다 문장을 고르면 단계가
늘 때 화면도 함께 고쳐야 한다. 한때 화면이 브리프에서 번호를 세어 어림한 수만큼 대기 칸을 먼저
그렸는데, 개수를 정하는 것이 바로 그 나누기 단계의 서버(입력 정제 → 기획)라 어림값이 틀릴 수 있다
(`동영상1 (0-8초)` 는 세지 못해 칸 하나를 그렸다가 넷으로 바뀌었다). 틀린 수를 확신하듯 보여주는
것이 "계산 중" 보다 나쁘다. 칸이 하나씩 생겨나지는 않는다. 프로젝트가 생기는 순간 씬 수가 확정되어
칸이 한 번에 나타나고, 렌더가 세그먼트를 보고하기 시작하면 그 칸의 상태가 바뀐다. 칸 수의 출처는
서버 하나다(`project.scenes`, 그 뒤 `project.segments`). 창이 기억하는 값이 아니라 서버가 말한 것을
그리는 이 화면의 원칙과 같다.

**업로드 단계는 없앴다.** 렌더는 이어붙이기부터 저장까지를 한 흐름으로 처리하고 그 사이를 알리지
않는다. 관측되지 않는 구간을 그리면 화면이 실제와 무관하게 진행하는 척하게 되므로, 그 가중치는
'영상 병합' 이 함께 든다(합이 100 이라는 계약은 그대로다).

**렌더 구간을 모르면 세그먼트 생성으로 둔다.** 렌더 시간의 대부분이 그 구간이라 모를 때 가장 사실에
가깝고, 진행 바가 뒤로 가지 않는다.

**정체(STALLED)와 실패는 단계로 옮기지 않는다.** 그것은 진행이 아니라 진행이 멈춘 것이고, 화면이
따로 알린다. 단계로 옮기면 '세그먼트 생성' 이라고 적힌 채 영원히 서 있게 된다.

**세그먼트 단위 실패는 여전히 없다.** 렌더는 씬 하나가 실패하면 잡 전체를 실패시킨다(씬이 빠진 영상을
만들지 않으려는 것이다). 그래서 "다른 칸은 멀쩡한데 이 칸만 실패" 라는 상태는 관측되지 않고,
`SegmentProgress` 의 `error`/`attempt`/`etaSec` 는 dev 목에서만 채워진다.

**세그먼트 격자는 완료 뒤에도 남는다.** 렌더 상태 재조정은 비종료 행만 렌더에 물어보므로, 종료 전이
시점에 그 격자를 프로젝트 행에 굳힌다(`marketing_video_projects.segments`). 굳히지 않으면 완성된
영상의 세그먼트가 통째로 사라져, 어느 칸을 다시 만들지 고를 수가 없다.

같은 이유로 **재생성 버튼은 다시 만들 대상이 실제로 있을 때만 그린다.** 프리뷰는 목이, 실제 경로는
렌더 잡이 붙은 프로젝트가 그 대상이다. 아직 프로젝트가 없으면 그리지 않는다. 눌러도 아무 일 없는
버튼이나 영구 비활성 버튼은 "곧 된다" 는 거짓 약속이 된다.

**세그먼트 하나를 다시 만드는 것은 붙어 있는 잡을 다시 돌리는 것이다.** 새 잡을 만들면 렌더가 이어서
할 근거(씬 체크포인트)를 못 찾아 **전 씬이 다시 돌고 전액 재과금된다.** 그래서 렌더는 저장해 둔 씬
결과로 체크포인트를 되살린 뒤 대상 씬 하나만 버린다. 벤더 비용이 그 칸 하나에 그치는 근거가 그것이다.

#### 재생성은 프롬프트를 고치는 것에서 시작한다

재생성 버튼은 곧바로 다시 만들지 않는다. 먼저 그 세그먼트의 프롬프트를 고치는 창을 연다
(`create/SegmentRegenerateModal.svelte`). **고칠 수 없는 재생성은 같은 입력으로 같은 일을 다시
시키는 것**이라, 실패한 세그먼트에서는 대개 같은 이유로 다시 실패하고 마음에 들지 않아 누른
경우에는 마음에 들지 않는 것이 한 번 더 나온다. 무엇을 바꿔 다시 만들지 정하는 것이 그 버튼의 쓸모다.

그래서 `SegmentProgress` 가 `prompt` 와 `error` 를 갖는다. 프롬프트는 **placeholder 가 아니라 값으로**
채운다: placeholder 로 두면 고칠 수 없고 통째로 다시 적어야 하는데, 그 창의 제목은 '수정' 이다.
실패 사유는 무엇을 고칠지 정하는 근거라 같은 창에 둔다(사유를 찾으러 창을 나가게 하지 않는다).
빈 프롬프트로는 시작할 수 없다. 지시 없이 다시 만들라는 것은 재생성이 아니라 초기화다.

**세그먼트 칸은 만들어진 영상을 그대로 보여준다**(`previewUrl`). 눌러 재생하고, 길이 배지는 그 영상이
알려 준 길이를 먼저 쓴다(보여 주는 영상과 적힌 길이가 어긋나지 않게). 표시만 남기면 그 칸이 무엇이
되었는지 알 방법이 결과 영상을 끝까지 보는 것뿐인데, 그러면 **어느 칸을 다시 만들지 고를 수가 없다**.
그 판단을 하라고 있는 격자다. 주소가 없으면 만들어졌다는 표시만 남는다(빈 `video` 를 두면 깨진
재생기가 뜬다).

**병합된 최종 영상은 아직 없지만, 프리뷰는 진짜 영상으로 돈다.** 목이 외부 테스트 영상(CC0)을 세그먼트
칸마다, 그리고 결과의 영상 주소로 얹는다. 이 화면에서 깨질 수 있는 것은 대부분 영상을 다루는
부분이라(첫 프레임, 재생, 되감기, 프레임을 캔버스로 옮기기, 그 캔버스를 저장할 수 있는지) 그림 한
장으로는 어느 것도 확인되지 않는다. **프리뷰 세그먼트는 셋이다**: 칸마다 진짜 영상을 받아 오므로
개수가 곧 네트워크 부담이고, 셋이면 끝난 칸과 도는 칸과 대기 칸이 동시에 보인다.

**칸 수는 클립 수다.** 둘을 따로 두었더니 칸이 클립보다 많을 때를 대비한 분기가 생겼는데, 실제
설정에서는 한 번도 돌지 않는 코드였다. 하나로 묶으면 그 자리가 사라지고 "칸마다 다른 영상" 이 정의가
된다.

**칸마다 다른 영상이다.** 한때 한 클립을 셋으로 잘라 썼다. 그러면 결과가 조각들의 이어붙임이 되어
깔끔했는데, 실제로 프레임을 뽑아 보니 **세 조각이 거의 같아 보였다**(같은 탁자 위 같은 토끼, 같은
자리의 같은 인물). 이 격자는 어느 칸을 다시 만들지 고르라고 있는 것이라, 칸을 구분할 수 없으면 그
판단을 연습할 수 없다. 내용이 뚜렷이 다른 셋으로 바꾸고, 어느 칸에 어느 클립이 갈지는 **열 때마다
다시 섞는다**(늘 같은 순서면 두 번째부터는 그것을 배경으로 읽어 무엇이 바뀌었는지 알아채지 못한다).

**결과 영상은 프리뷰가 실제로 이어 붙인다.** 캔버스에 클립을 차례로 재생해 그리고 그 캔버스의
스트림을 녹화한다(`mergeMockSegments`). 나오는 것은 진짜 파일 하나라 결과 화면이 그것을 재생하고
되감고 프레임을 떠서 썸네일까지 만든다. 길이만 맞춘 대역을 놓아도 숫자는 맞았지만, 화면이 '합쳐진
최종 영상' 이라고 말하는 것과 재생되는 것이 다른 물건이었다. **이어 붙이기가 이 흐름의 핵심 단계인데
그것만 흉내면 프리뷰로 그 단계를 볼 수 없다.**

**녹화는 실시간을 벗어날 수 없어 빠르게 만드는 길이 둘뿐이다.** 첫째, **클립을 전부 미리 받아 둔 뒤에
녹화를 시작한다.** 순서대로 열면 각 클립의 내려받기 시간이 녹화 시간에 더해질 뿐 아니라 그 구간이
정지 화면으로 **결과물에도 남는다.** 미리 받으면 내려받기가 겹쳐 돌고 녹화는 실제 재생 시간만 쓴다.
둘째, **조각을 짧게 잡는다**: 그 길이가 곧 걸리는 시간이라 1초 × 3 = 3초다. 칸의 내용을 판단하는 데는
1초로 충분하고 카드는 눌러 반복 재생한다. 그리는 일도 `requestVideoFrameCallback` 으로 디코드된
프레임마다 한 번씩만 한다(rAF 는 60Hz 로 돌아 30fps 원본을 두 번씩 그린다).

한계 셋을 적어 둔다. (1) 녹화가 실시간이라 조각 길이의 합만큼 걸리므로 그동안 버튼이 '합치는 중' 을
말한다. (2) 소리는 담기지 않는다(캔버스 스트림에 오디오 트랙이 없다). (3) 나오는 webm 은 헤더에
길이가 없어 `duration` 이 Infinity 다. 그래서 **썸네일 편집기가 길이를 인자로 받는다**: 파일에게
되묻는 대신 만든 쪽이 아는 값을 쓴다. 못 만들면(브라우저가 녹화를 지원하지 않거나 클립을 열지
못하면) 길이만 맞춘 대역으로 떨어진다.

진짜 이어 붙이기는 서버(ffmpeg concat)의 일이고, 이것은 그 단계를 눈으로 보기 위한 dev 대체물이다.

한 가지가 따라온다. 구간만 쓰는 영상은 `duration` 이 구간이 아니라 **파일 전체**를 답한다. 그래서
길이 배지는 **선언된 값(`durationSec`)이 우선**이고 파일이 알려 준 길이는 그것이 없을 때의 대비책이다.
선언된 값이 이 세그먼트가 무엇인지 말하는 쪽(서버)의 값이기도 하다.

주소를 아무거나 쓸 수는 없다. **캔버스 캡처가 되려면 `Access-Control-Allow-Origin` 이 있어야 하고,
되감기가 되려면 Range 요청을 받아야 한다.** 흔한 샘플 영상 중에도 CORS 헤더가 없어 캔버스를 오염시키는
것이 있다(그러면 저장만 조용히 막힌다). 지금 쓰는 주소는 둘 다 확인했다.

목은 **자리표시 그림도 함께** 만들어 `posterUrl` 에 얹는다. 그 영상이 열리지 않을 때의 바탕이고,
그 경로는 실제로도 있다(로드 실패). 자리표시로 보이게 그려 dev 에서 본 것을 실제 결과로 착각하지
않게 한다. 세그먼트 수와 길이는 지어내지 않고 **진행 상태에서 계산한다**(`resultFromProgress`).
프리뷰에서 재생성을 눌러 세그먼트가 바뀌면 그 수가 그대로 따라온다.

**dev 목에는 실패한 세그먼트를 두지 않는다.** `advanceMock` 이 실패가 남아 있으면 거기서 멈추므로,
두면 프리뷰가 스스로 완료에 닿지 못해 결과 화면과 썸네일 편집기 앞에서 막힌다(사람이 재생성을 눌러
줘야 넘어갔다). 실패 카드의 모양과 재생성 버튼의 유무는 `SegmentStatusCard.svelte.test.ts` 가 네 상태를
모두 검사하므로 프리뷰가 그것까지 보여 줄 필요가 없다.

**그 묶음이 없는 버전에는 영상 설정을 실어 보내지 않는다.** 기본값이라도 실으면 아무도 고르지
않은 선택이 저장본에 남아, 나중에 그 행을 읽는 쪽이 사람이 정한 값으로 읽는다. 빼면 서버와 DB 의
기본값이 그대로 서고 그 값이 곧 '고른 적 없음' 이다(`segment_mode ''`).

**반대로 인포그래픽 배제에는 플래그를 두지 않는다.** 그 토글이 없어야 할 버전은 기획서 구성
섹션 자체가 없는 버전이라, 플래그의 꺼진 쪽이 그려질 자리가 없었다. 화면을 봐도 확인되지 않는
조건은 규칙이 아니라 잡음이다. 두 경우를 가르는 기준은 **꺼진 쪽이 관찰되는가**다.

**v1.5 의 개수는 고르는 값이 아니라 파생값이다.** 기획안은 하나(영상 한 편)이고, 씬 수는 브리프에서
읽는다(`sceneCountFromBrief`: `씬1:` 처럼 번호를 붙인 줄을 센다). 줄글로 적었거나 비었으면 기본값으로
떨어진다. 틀린 수로 지시하는 것보다 낫고, 브리프가 있으면 그 내용이 프롬프트에 함께 실려 모델이
그것을 따른다. 줄 수가 아니라 번호를 세는 이유는 한 씬을 여러 줄로 적는 사람이 있어서다.

**영상 모델과 세그먼트 연결 방식은 저장본에 스냅샷으로 남는다.** 고르는 시점(생성 모달)과 렌더
시점이 떨어져 있어, 남기지 않으면 그 사이 바뀐 설정이나 렌더 기본으로 돌아 고른 것과 다른 결과가
나온다. 브랜드 축 조합을 스냅샷하는 것과 같은 규칙이다.

> **벤더로 나가는 스펙은 기획안이 아니라 예약 행에서 조립된다**(`buildSpecFromRow`).
> `prepareFromPlan` 의 스펙은 자산 사전검증에만 쓰인다. 그래서 렌더에 도달해야 하는 값은
> **행에도 있어야 한다**(`marketing_video_projects`). 기획안에만 두면 잡 params 에 실리지 않고,
> 그 상태는 조용하다: 고른 방식과 무관하게 기본으로 돌아간다. 재렌더가 같은 방식으로 도는 것도
> 행에 있기 때문이다.

### 입력 방식마다 자기 폼

**두 방식은 각자 폼 컴포넌트를 갖는다**(`ConceptForm` / `PromptForm`). 겹치는 칸이 많지만 두 방식이
하는 일이 다르다. 컨셉입력은 저장된 브랜드/컨셉 세트를 시작점으로 삼아 톤을 고르고 그 선택이
기획안의 주제이자 씬 이미지를 다시 만들 때의 기준이 된다. 그래서 브랜드 조회와 선택 유효성 유지가
그 폼에만 있고, **버전 분기도 그 폼에만 있다**(v1.0 은 기획서 구성을 고르고 직접 적는 칸이 없다).
프롬프트는 v1.5 가 들여온 방식이라 그 폼에는 버전 분기가 하나도 없어, 어떤 칸이 있는지가 파일을
읽으면 그대로 보인다.

플래그 하나로 한 폼을 재활용하면 그 두 가지가 조건문으로 흩어지고, 칸을 옮기는 일이 늘 두 방식
모두의 회귀 위험이 된다.

| 담는 것 | 컨셉입력 | 프롬프트 |
|---|---|---|
| 기획서 구성 / 인포그래픽 배제 | v1.0 만 | 없다 |
| 씬 / 사용자 입력사항, 제한사항 | v1.5 만 | 있다 |
| 브랜드(저장된 세트) | 있다 | **없다** |
| 연출 성격(7축 카테고리) | 있다 | **없다** |
| 영상 설정(모델, 세그먼트) | v1.5 만 | 있다 |

**두 방식의 차이는 고를 것이 있느냐다.** 컨셉입력은 저장된 세트와 카테고리가 톤을 정해 두고, 씬
입력은 그 위에 무엇을 담을지만 더한다. 프롬프트는 **고르는 것이 하나도 없다**: 적은 문장이 주제이자
연출이고, 적히지 않은 것(표현 형식, 무드, 화법, 인물, 장소)은 모델이 그 문장에 맞춰 정한다.

한때 프롬프트 방식에도 7축을 직접 적는 칸을 두었다. 걷어낸 이유는 그것이 '자율' 과 반대이기
때문이다. 고를 것을 없앤 방식에 적을 것을 일곱 개 만들면 컨셉입력보다 손이 더 간다. 톤을 정해 두고
만들려면 컨셉입력 탭이 이미 그 방식이다.

**그래서 씬 입력 칸의 예시(플레이스홀더)도 두 방식이 다르다.** 같은 칸이지만 지는 몫이 다르고, 한
벌을 공유하면 두 방향으로 어긋난다.

| | 컨셉입력 | 프롬프트 |
|---|---|---|
| 이 칸에 적는 것 | **무엇을 담을지만** | 화면, 분위기, 인물, 말까지 전부 |
| 톤과 연출 | 브랜드와 카테고리가 정한다 | 적지 않으면 모델이 정한다 |
| 비워도 되는가 | 된다 | **안 된다**(주제가 사라진다) |

컨셉입력에서 톤까지 적게 하면 **같은 것을 두 자리에서 정하는 셈**이 된다(카테고리와 이 칸). 두 값이
어긋나면 모델이 무엇을 따를지 알 수 없다. 반대로 프롬프트에서 컨셉입력의 예시를 쓰면 "이 정도만
적으면 되는구나" 로 읽혀, 연출이 통째로 모델에게 넘어간 줄 모른 채 결과를 받는다.

예시 첫 줄이 그 칸이 하는 일을 말하고 나머지 줄이 형태를 보여준다. 칸 옆에 설명문을 따로 두지 않는
이유는 적어 둔 것을 보여 주는 편이 짧고 정확해서다. 그래서 **입력칸 높이도 예시 줄 수에서
파생시킨다**: 예시가 이 칸의 유일한 안내인데 마지막 줄이 잘려 보이면 안내가 아니다.

**대신 영상 설정 묶음은 공유한다**(`VideoSettingsSection`). "무엇으로 어떻게 만들지" 는 방식과 무관한
같은 결정이고, 그 묶음까지 복제하면 설정을 하나 더할 때마다 두 폼을 고쳐야 한다. 저장값 조회
(`myAiModelQuery`, `configuredProviders`)도 이 묶음이 갖는다. 같은 쿼리 키라 어느 폼에서 열어도
네트워크는 한 번이다.

방식마다 넘기는 값이 다르므로 **공통 prop 모양을 강제하지 않는다.** 강제하면 갈라 둔 것을 다시
합치는 셈이 된다. 위저드는 `{#if mode}` 로 갈라 각 폼에 그 폼의 값만 넘긴다.

프롬프트 방식에서는 브랜드 자동 선택이 일어나지 않는다. 그 폼이 브랜드를 조회하지 않아 구조적으로
그렇다. 플래그로 껐다면 보이지 않는 선택을 채우는 코드가 남아, 나중에 그 방식에서 생성을 열 때
고른 적 없는 브랜드가 조용히 실려 나갈 수 있다.

### 직접 적은 지시는 기획 앞에서 정제된다

두 칸(씬/사용자 입력사항, 제한사항)은 자유 서술이다. 사람은 거기에 무엇이든 적는다. 실제로 들어온
입력 하나는 이랬다. 동영상마다 `(0-8초)` 구간과 `[해당 단계: 훅, 씬1]` 태그가 붙고, 한 동영상 안에
`(8-11초)`, `(11-16초)` 하위 구간별 묘사가 있고, 대화내용은 전부 `없음` 인데 나레이션은 동영상 밖에
`전체 나레이션 (0-30초)` 으로 따로 모여 있고, 클로징 컷에는 로고가 등장한다.

이 파이프라인은 그중 어느 것도 받지 않는다. 길이는 말에서 정해지고(시간을 받지 않는다), 말은
동영상마다 하나이며(따로 모은 목록을 나눠 붙일 규칙이 없다), 화면에 글자와 로고는 넣지 않는다.
그 해석을 기획 LLM 에 맡기면 같은 입력이 생성마다 다른 개수와 다른 화자로 나온다. 화면의 셈도
깨진다: `sceneCountFromBrief` 는 `동영상1:` 만 세므로 `동영상1 (0-8초)` 는 세지 못해 기본값 1 을
보내고, 프롬프트는 "정확히 1개" 라 말하면서 원문에는 넷이 적혀 있게 된다.

그래서 **기획 LLM 앞에 정제 호출을 하나 둔다.** 정제기는 창작하지 않는다. 옮기고, 형식에 맞지 않는
것만 고치고, 무엇을 고쳤는지 적는다.

| 무엇 | 어디 |
|---|---|
| 하는가, 어느 모델로 | 파이프라인 표의 `briefRefinerLlm`(v1.5 = `claude-sonnet-5`, v1.0 = 없음) |
| 무엇을 묻는가 | 그 버전 조립기의 `briefRefinerSystemPrompt` / `briefRefinerUserPrompt`(`prompt/v15/brief-refiner.ts`) |
| 어떻게 묻고 읽는가 | `BriefRefinerPort` 하나(`LanguageModelBriefRefinerAdapter`). 응답 스키마가 이 도메인의 것이라 버전과 무관하다 |
| 결과를 어디에 | 정제본을 `renderRefinedBrief` 로 글로 되돌려 기획 유저 프롬프트의 `[사용자 입력사항]`, `[제한사항]` 절에 싣는다 |

**정제본은 화면의 입력 예시와 같은 모양이다**(`동영상N:` + 장면 구성 + 대화내용 + 나레이션, 쓰지
않는 말은 `없음`). 사람이 그 모양으로 적은 것과 정제기가 만든 것이 기획 LLM 에 같은 글로 닿아,
정제가 끼어도 기획 프롬프트의 계약은 바뀌지 않는다. 정제기와 기획 시스템 프롬프트가 말하는 한계
(말 40자, 클립 10초, 동영상 1~8개)는 같은 상수에서 나온다(`prompt/v15/limits.ts`, 그리고 `plan-counts.ts`
가 재노출하는 `@csc/tool-versions` 의 상한).
한쪽만 바뀌면 정제기가 통과시킨 문장을 기획 LLM 이 다시 줄이거나 정제기가 이유 없이 줄인다.

규칙 다섯.

1. **정제가 확정한 동영상 수가 요청의 씬 수를 이긴다.** 화면의 셈은 번호 표기에 의존한 어림값이다.
   브리프를 적지 않고 제한사항만 적었으면 동영상은 없어야 하고(모델이 지어냈어도 버린다) 씬 수는
   요청값을 쓴다.
2. **두 칸이 모두 비면 부르지 않는다.** 유료 호출이라 정제할 것이 없는데 부르면 돈만 나간다. 브랜드
   검증 뒤에 부르는 것도 같은 이유다(없는 브랜드로 온 요청에 먼저 과금하지 않는다).
3. **실패하면 생성을 멈춘다.** 원문으로 조용히 진행하면 정제가 없던 때의 결과가 아무 신호 없이
   나온다. 브리프를 적었는데 정제 결과에 동영상이 하나도 없으면 그것도 실패다(빈 정제본을 넘기면
   기획 LLM 이 사용자 입력사항 없는 프롬프트를 받는다).
4. **별도 활동으로 기록한다**(`plan.brief_refined`). 유료 호출이라 원장에 자기 행이 있어야 금액이
   맞고, 그 행의 상세에 원문과 정제본과 바꾼 것의 목록이 나란히 남는다. "왜 내 지시가 이렇게
   바뀌었나" 의 답이 거기 있다. 기획 행은 `brief_refined` 로 앞 행과 이어진다. 거절된 호출도 이미
   돈이 나간 것이라 `failed` 로 남는다.
5. **동영상은 8개까지다.** 정제 결과가 그 수를 넘으면 합쳐서 맞추지 않고 거절한다(400, 본문
   `code: SEGMENT_LIMIT_EXCEEDED`). 합치면 작업자가 나눈 단위가 말없이 바뀐다. BFF 는 그 코드의 400
   만 서버 문장과 코드를 그대로 통과시키고, 화면은 우하단 알림으로 사유를 보인 뒤 배치를 걷어 진행
   화면을 폼으로 되돌린다(취소 버튼과 같은 사가 `cancelGeneratingBatch`). 번호를 세어 미리 알 수 있는
   입력은 유료 호출 전에 화면이 같은 문장으로 막는다. 상한 수와 오류 코드와 안내 문장은 서버와 화면이
   함께 쓰는 커널 `@csc/tool-versions`(`limits.ts`)가 갖는다. 버전마다 상한이 갈리는 날 그 값은
   파이프라인 표의 사실로 옮긴다.

프로세스 화면은 이 스텝을 기획 단계의 첫 스텝으로 그린다(`refine-brief`). 가격표의 LLM 호출 수는
정제하는 버전에서 최대 2회다(두 칸을 다 비우면 1회).

### 무엇을 주제로 삼는가

제출 조건은 하나다: **주제가 있는가.** 방식마다 그 주제가 어디서 오는지가 다르다.

| 방식 | 주제 | 없으면 |
|---|---|---|
| 컨셉입력 | 고른 브랜드(브랜드 설명이 무엇을 파는지 말한다) | 제출 불가 |
| 프롬프트 | **적은 씬 입력 본문**(그것이 곧 만들 영상이다) | 제출 불가 |

목적 키워드는 어느 방식에서도 선택이다. 있으면 그것이 중심이 되고 위의 주제가 각도를 준다. 없으면
위의 주제가 중심을 맡는다. 그래서 시스템 프롬프트의 주제 지시가 **세 갈래**다(키워드 / 브랜드 /
사용자 입력사항).

**연출 성격이 화면과 말에 닿는 연결도 고정부다.** 시스템 세그먼트 `concept-direction` 이 표현 형식과
무드를 `sceneComposition` 에, 톤앤매너를 화법에, 나머지 축을 각자의 자리에 매고 모든 동영상에
일관되게 적용하라고 말한다. 브랜드만 고르고 축을 비우면 스스로 정하되 일관되게 하라는 문장으로
바뀌고, 프롬프트 방식에서는 빠진다(그 갈래의 주제 지시가 같은 말을 한다). 편집 지침에 두지 않는
이유: 채널이 지침을 통째로 고치면 그 줄이 빠질 수 있고, 그러면 컨셉입력에서 고른 연출이 유저
프롬프트에 데이터로만 실린다. 영상 모델은 `sceneComposition` 만 읽으므로 거기 드러나지 않은 연출은
영상에 없다. 축 이름은 카탈로그(`BRAND_CONCEPT_AXES`)에서 읽어 유저 프롬프트의 `[연출 성격]` 줄과
같은 이름이다. v1.0 은 그 문장이 편집 지침에 남아 있다.

**키워드만으로는 제출할 수 없다.** 그 키워드를 무엇에 붙일지 알 수 없기 때문이다. 판정은 BFF 와
위저드 양쪽에 있다: 화면이 버튼을 막고, 화면을 우회한 요청은 400 이 된다.

브랜드가 없으면 `brandName` 을 **빈 문자열로 보낸다.** 서버는 그 값을 보고 세트를 아예 조회하지
않는다(없는 이름으로 찾다가 404 가 나면 그 방식 자체가 막힌다). DB 는 이미 빈 브랜드명을 허용한다
(`brand_name` NOT NULL DEFAULT '').

화면 구성이 아닌 버전 차이가 하나 더 있다. **어떤 AI 모델을 쓰는가**는
`marketing-video/aiModelOptions.ts` 가 갖는다.

| 담는 것 | 쓰는 곳 |
|---|---|
| `AiCapability.versions` (그 버전의 파이프라인에 있는 단계) | 설정 섹션 + 가격표 그룹 + 단계별 필요 역량 + 씬 이미지 화면 |
| `AiModelOption.versions` (그 버전이 쓰는 모델) | 설정 > AI 모델 선택지 + 가격표 행 |
| `AI_MODEL_DEFAULTS[version]` (역량별 기본 모델, **없을 수 있다**) | 고른 적 없는 역량의 표시값 + "기본" 배지 |
| `effectiveAiModel(cap, saved, version)` (실제로 쓰일 모델) | 설정 표시값 + 생성 전 점검 |
| `usesSceneImages(version)` (역량 축에서 파생) | 기획안 카드의 이미지 자리 + 씬 이미지 오케스트레이션 + 자동 저장 조건 |

**모델 격자는 두 버전이 같다.** 제공자 → 회사 → 타일이라는 모양을 버전마다 다르게 하면 같은 도구가
두 개처럼 보인다. 갈리는 것은 그 위에 얹는 것뿐이다: 한 역량의 선택지가 임계치를 넘으면 검색창과
요약 한 줄이 붙는다(`aiModelSearch.ts`).

**그 판정은 버전이 아니라 선택지 수다.** 버전으로 갈랐다면 v1.0 의 선택지가 늘어나는 날 같은 문제를
다시 겪고 버전 분기를 하나 더 넣게 된다. **지금은 어느 역량도 임계치를 넘지 않아 검색창이 하나도
없다.** 규칙만 남아 있고 목록이 늘면 저절로 붙는다. 그 상태를 `aiModelSearch.test.ts` 가 고정하므로,
검색이 붙기 시작하는 날 검사가 실패해 그 화면을 실제로 보게 된다.

요약 줄은 **모든 모델에 해당하는 사실만** 담는다(경유 플랫폼, 개수). 타일마다 반복하면 같은 말이
모델 수만큼 나온다. 키 미등록 안내도 전부 같은 이유로 막혔을 때는 한 번만 적는다.
다만 **요약 줄을 그리지 않을 때는 타일에서 빼지 않는다.** 개수와 무관하게 빼면 그 사실을 어디에서도
말하지 않는 화면이 된다.

**모델을 고른 뒤 더 받아야 하는 값이 있으면 격자 아래에 작은 입력 묶음이 붙는다.** 지금 둘이다.
자체 영상 모델의 생성 방식, edge-tts 의 음성과 피치. 둘 다 **개인이 고르는 값**이라 여기 있다.

여기에 들어오지 않는 것도 같은 기준으로 갈린다. 조직 전체가 공유하고 그 값을 볼 수 있는 사람이
정해져 있으면 조직 API 등록으로 간다(아래 ElevenLabs 음성).

프로필로 끌어오지 않은 이유: 목록과 기본은 같이 움직여야 한다(기본이 목록에 없으면 그 역량이
아무것도 고르지 않은 것처럼 보인다). 둘 다 카탈로그의 사실이라 떼어 두면 오히려 갈라진다.
그 불변식은 `tests/unit/pages/marketing-video/aiModelCatalog.test.ts` 가 지킨다.

지금 갈린 것 셋.

**1. 파이프라인에 어떤 단계가 있는가.** 두 버전이 갈리는 지점이다.

| | v1.0 | v1.5 |
|---|---|---|
| 기획 문안 | 외부 LLM(Claude) | **단계 없음** |
| 씬 이미지 | 만든다(GPT Image) | **단계 없음** |
| 씬 비주얼 | 씬 이미지 → 클립(슬라이드쇼 / Grok image-to-video) | Higgsfield 영상 모델이 텍스트에서 직접 |
| 대사(인물이 말한다) | **없다** | 영상 모델이 립싱크로 함께 만든다 |
| 나레이션(화면 밖 목소리) | Edge TTS(무료)로 합성해 얹는다 | **영상 모델이 대사와 함께 낸다** |

**"기획 문안 단계 없음" 은 고를 모델이 없다는 뜻이지 LLM 을 부르지 않는다는 뜻이 아니다.** v1.5 도
기획안을 LLM 으로 만든다(그것이 장면 구성과 대화내용을 쓴다). 다만 그 역량이 화면에 없어 **서버 기본
언어 모델**로 돌아간다. 그 상태를 바꾸려면 역량 축에 `llm` 을 되돌리면 되고, 그러면 선택지와 기본
모델이 함께 따라온다.

### 대사와 나레이션은 다른 층이되 배타는 아니다

v1.5 에서 처음 갈린다. 다른 층이라 표에서도 줄을 나눠 둔다.

| | 대사 | 나레이션 |
|---|---|---|
| 누가 말하나 | 화면 속 인물 | 화면 밖 |
| 입 모양 | 맞아야 한다 | 무관 |
| 씬의 자리 | `dialogue` | `narration` |

**한 영상에 둘 다 들어갈 수 있다.** 둘 다 영상 모델이 같은 패스에서 내므로 목소리가 겹치지 않게
차례를 정하는 것도 그 모델의 일이다. 그래서 씬은 두 자리를 갖고, 각각은 비어 있어도 된다
(말하는 인물이 없는 컷, 설명이 필요 없는 컷).

이전에는 배타였다. 나레이션만 **별도 TTS 로 합성해 얹었기** 때문이다. 합성한 목소리는 클립 안의
발화와 같은 패스에서 만들어지지 않아, 둘을 겹치면 한 화면에서 두 사람이 동시에 말했다. 그 합성을
걷어내면서 배타일 이유가 사라졌고, 생성 모달의 **나레이션 사용 스위치도 함께 사라졌다.**

**v1.0 은 그대로 합성한다.** 그쪽은 이미지→영상이라 모델이 말을 못 한다. Edge TTS 로 만들어 얹는
것이 그 버전의 유일한 소리이고, Edge TTS 는 키도 음성 ID 도 요구하지 않아 등록 없이 돈다.

**대사를 나레이션으로 대신할 수 없다.** 목소리를 따로 얹으면 인물이 입을 다문 채 말소리가 나거나,
입을 움직이는데 소리가 안 난다. 립싱크는 영상 픽셀과 함께 생성되어야만 맞는다.

**그래서 v1.5 영상 모델은 대사를 내는 것만 싣는다.** 오디오가 없는 모델은 이 파이프라인에 자리가
없다. 기준은 **한국어 대사의 립싱크 정확도**다. 산출물의 대사가 한국어라, 영어 대사만 잘하는 모델은
이 도구에서 못 쓰는 것과 같다. 등급이 갈리는 모델은 립싱크가 가장 정확한 등급만 남긴다.

| 기준을 만족하는 것 | 근거 |
|---|---|
| Kling 3.0 | 벤더가 한국어를 네이티브 립싱크 언어로 명시. 한 장면에 여러 인물이 말할 수 있다 |
| Seedance 2.0 | 음소 단위 립싱크, 한국어 포함. 대사와 효과음, 배경음을 한 패스에서 생성 |
| Veo 3.1 | 오디오 파이프라인이 가장 정교하다(48kHz, 립싱크 120ms 이내) |

**Veo 3.1 은 위 기준을 완전히 만족하지 않는다.** 대사 품질이 영어에 맞춰져 있어 한국어는 앞의 둘보다
약하다. 그럼에도 싣는 것은 제품 결정이고, 대신 두 가지로 그 사실을 드러낸다. 약점을 모델 설명에
적고, 목록 순서를 뒤에 둔다(이 목록은 이 도구에 맞는 순서로 정렬한다). 등급은 표준만 싣는다.

##### 그런데 지금 이 계정은 어떤 영상도 만들 수 없다 (2026-09-01 확인)

조직 키로 벤더의 텍스트→영상 전부에 **유효한 본문**을 제출해 확인했다(403/503 은 잡이 만들어지지
않아 과금이 없다).

| 사유 | 모델 | 뜻 |
|---|---|---|
| 403 `not_enough_credits` | Kling 3.0 / 2.1 / 2.5, MiniMax Hailuo 2.3, Wan 2.5 | **크레딧이 없다.** 채우면 살아난다 |
| 503 `model_disabled` | Seedance 2.0, Veo 3.1 | 벤더가 껐다. 크레딧과 무관하다 |

**빈 본문 POST 의 400 을 "통과" 로 읽으면 안 된다.** 이 경로들은 검증이 크레딧보다 먼저라, 400 은
파라미터가 맞다는 뜻일 뿐이다. 조사 중에 그것을 통과로 읽어 "일곱 모델은 부를 수 있다" 고 결론했다가,
유효한 본문을 보내자 전부 403 이었다. 확인은 **유효한 본문으로** 해야 한다.

립싱크 셋의 경로는 모두 **벤더 문서(OpenAPI)에 없다.** 문서의 Veo 3.1 에는 text-to-video 항목이 아예
없고(image-to-video, first-last-frame, reference 뿐), 문서의 Seedance 는 v1 계열이다. 즉 그 셋은 목록에
오를 때부터 이 계정에서 호출된 적이 없다.

**그렇다고 경로가 틀린 것은 아니다.** 벤더가 상태 코드로 둘을 구분해 준다(공식 표).

| 코드 | 뜻 | 벤더 권고 | 우리에게 |
|---|---|---|---|
| 404 | 이 계정에 그 모델이 없음 | 재시도 말 것 | 경로가 틀렸거나 접근이 없다 |
| 503 | 꺼짐 또는 준비되지 않음 | 나중에 | 경로는 인식된다 |
| 423 | 일시 차단 | 나중에 | 같음 |
| 403 | 크레딧 부족 | 충전 후 | 접근은 있다 |

Veo 3.1 t2v 와 Seedance 2.0 t2v 는 **503** 이다(404 가 아니다). 그래서 우리 쪽에서 고칠 경로가 없다.
Veo 는 t2v 와 i2v 가 **둘 다** 503 이라 모드를 바꿔도 소용없다. 반대로 문서에 실린
first-last-frame-to-video 와 reference-to-video 는 404 라, 문서에 있다고 접근이 있는 것도 아니다.
Seedance 는 표준 등급이 503, `fast` 등급이 423 이다.

**지금 상태를 보는 방법.** 벤더에 모델 목록 API 가 없어 하나씩 찔러 보는 것이 유일한 방법이다. 그
판정을 사람이 매번 기억하지 않도록 스크립트로 둔다(목록은 카탈로그에서 읽으므로 복제가 없다).

```bash
SERVICE_TOKEN_SECRET='<시크릿>' node scripts/probe-higgsfield-models.mjs --org <조직id>
```

기본은 dry 다(잡을 만들지 않는다). `--submit` 은 유효한 본문으로 제출하므로 **크레딧이 있으면 그
순간 유료 잡이 만들어진다.** 잔액과 한도는 API 로 볼 수 없고 Higgsfield Cloud 콘솔에서 본다.

**그 셋을 목록에 남기되, 꺼져 있는 둘은 고를 수 없게 한다**(카탈로그의 `comingSoon`, 화면 표기
"준비중"). 목록에서 지우지 않는 이유는 이 도구가 쓰려는 모델이고 열리는 날 한 줄로 되살아나기
때문이다. 지우면 고르는 사람이 그런 선택지가 있다는 것 자체를 모른다.

고를 수 없게 하는 이유는 **고른 뒤에 막히는 것이 더 나쁘기 때문**이다. 그 상태에서 사용자가 할 수
있는 일이 없는데(벤더 계정 사정) 생성까지 가서 실패하고, 그 실패는 영상 하나를 기다린 뒤에 온다.
그래서 셋을 함께 막는다.

| 자리 | 무엇을 하는가 |
|---|---|
| 설정의 AI 모델 목록 | 타일이 비활성 + "준비중" 배지 + 사유 한 줄 |
| 생성 모달의 영상 모델 | 같음(같은 카탈로그 판정을 쓴다) |
| 가격표 | 상태 칸이 "준비중"(키 미등록보다 앞이다: 키를 등록해도 못 쓴다) |
| 저장된 선택이 그 모델일 때 | 설정이 다시 고르라고 알리고, 생성 전 점검이 시작을 막는다(사유 `coming-soon`) |

**렌더러와 백엔드는 이 값을 모른다.** 벤더 상태는 우리 배포 없이 바뀌므로, 서버에 "사용 중지" 를
박으면 벤더가 켠 날 우리 코드가 그 모델을 막는다. 그래서 판정은 화면 카탈로그 한 자리에만 둔다.
그 사이에 어떤 경로로든 잡이 들어가면 렌더가 벤더 사유를 그대로 우하단 알림에 띄운다
(`vendor_http`: 재시도 없이 즉시, 사유 문구 포함).

**열리면 카탈로그의 `comingSoon` 줄만 지운다.** 그 판정이 코드 곳곳에 흐르지 않게 한 자리에 두는
이유가 그것이다. 지금 준비중인 둘: Seedance 2.0(표준), Veo 3.1(Higgsfield 경유). Gemini 경유 Veo 3.1
은 실제로 만들어 확인했으므로 준비중이 아니다.

**대신 파라미터를 확인해 둔 둘을 그 아래 싣는다.** 지금은 그 둘도 크레딧이 없어 만들지 못한다.
싣는 이유는 하나다: 크레딧이 들어오는 날 **받는 파라미터를 아는 모델**로 파이프라인 전체를 끝까지
확인할 수 있다(립싱크 셋은 문서에 없어 확인할 수 없다). 특히 Kling 2.1 Master 는 `aspect_ratio` 를
받아 세로를 지정할 수 있는 유일한 모델이다.

두 묶음을 섞지 않는다: 이 도구의 산출물은 사람이 한국어로 말하는 영상이고, 말을 못 하는 모델은 같은
종류의 선택지가 아니다.

| 대안 | 세로(9:16) 지정 | 한국어 대사 |
|---|---|---|
| Kling 2.1 Master | **가능**(`aspect_ratio` 를 받는다) | 확인되지 않음 |
| Kling 2.5 Turbo | 불가(가로로 만들어진다) | 확인되지 않음 |

세로를 함께 적는 이유: 렌더가 벤더 클립을 캔버스로 cover 크롭하므로, 가로로 만들어지면 가운데만
남아 인물이 잘린다.

**MiniMax Hailuo 2.3 과 Wan 2.5 프리뷰는 싣지 않는다.** 벤더 문서가 대사 생성을 말하지 않아 이 도구의
산출물에 쓸 자리가 없고, 세로도 지정하지 못한다. 확인해 둔 파라미터는 어댑터 주석에 남겼다(다시 실을
때 재확인이 필요 없게).

**확인되지 않은 것을 모델 설명에서 주장하지 않는다.** 고르는 사람이 그 문장을 근거로 고르기 때문이다.
그래서 둘의 설명은 화면 비율과 대사 여부를 있는 대로 적는다. 벤더 문서가 Kling 2.6 을 "대사가 영어와
중국어뿐" 이라고 적으므로, 그보다 낮은 판의 한국어 대사를 낙관하지 않는다.

**막힌 것을 푸는 일은 코드 밖이다.** 크레딧 충전(Kling 계열이 살아난다)과 Veo/Seedance 접근 활성화가
벤더 콘솔의 일이다. 크레딧이 들어오면 **가장 먼저** Kling 3.0 의 파라미터를 확인해 어댑터 표에 한 줄
추가한다(그 경로는 문서에 없어 지금 확인할 수 없고, 표에 없으면 프롬프트만 나가 세로와 길이를
지정하지 못한다. 어댑터가 그때마다 경고를 남긴다).

##### 모델마다 받는 요청 파라미터가 다르다

한 벌을 고정으로 보내면 받지 않는 모델에서 400 이 나고, 그 실패는 잡이 워커까지 간 뒤에 드러난다.
실제로 갈리며 아래는 라이브 API 로 확인한 값이다(일부러 열거값 밖의 길이를 보내 검증 응답만 받았다).

| 모델 | duration | aspect_ratio | resolution |
|---|---|---|---|
| Kling 2.1 Master | 5, 10 | 받는다(기본 1:1 이라 **9:16 을 보내야 한다**) | 없음 |
| Kling 2.5 Turbo | 5, 10 | 없음 | 없음 |
| (싣지 않음) Hailuo 2.3 | **6, 10** | 없음 | 없음 |
| (싣지 않음) Wan 2.5 | 5, 10 | 없음 | 480p / 720p / 1080p |

Hailuo 의 열거값이 다른 것이 이 표가 필요한 이유를 그대로 보여 준다. 공통 (5, 10) 으로 보내면 5 가
열거값 밖이라 400 이다. 그 모델을 싣지 않아도 규칙은 남는다(`_pick_duration` 이 열거를 인자로 받는다).

그래서 표를 어댑터가 갖는다(`higgsfield_video.py` 의 `_MODEL_PARAMS`). **표에 없는 모델은 프롬프트만
보낸다**: 추측한 파라미터로 400 을 만드는 것보다 벤더 기본값으로 만들어지는 편이 낫다. 청구 초도 같은
표를 보므로(`billable_seconds`) 보낸 값과 기록이 어긋나지 않고, 길이를 받지 않는 모델은 `None`
(모름)이라 청구 초 합계에서 빠진다(0 은 '쟀는데 0' 으로 읽힌다).

**대사 립싱크 셋은 표에 없다.** 지금 호출되지 않아 확인할 수 없기 때문이다. 문서의 형제 경로를 보면
Veo 는 duration 이 **문자열** 열거("4"/"6"/"8")이고 resolution 도 "720"/"1080" 이라 인코딩부터 다르다.
추측해 넣으면 첫 호출이 400 이거나, 더 나쁘게는 엉뚱한 값이 통과한다. 벤더가 열리는 날 위 확인 절차를
한 번 돌리고 그때 한 줄 추가한다.

그동안 그 셋으로 렌더하면 프롬프트만 나가므로 세로와 길이를 지정하지 못한다. 그 손실은 영상을 봐야
드러나므로 **어댑터가 경고를 남긴다**(표에 없는 모델을 부를 때마다). 조용한 화질 손실보다 로그의 흔적이
낫다.

| 뺀 것 | 근거 |
|---|---|
| Veo 3.1 Fast / Lite | 같은 모델의 낮은 등급. Lite 는 립싱크가 어긋난다 |
| Kling 2.6 | 대사가 영어와 중국어뿐이다 |
| Seedance 2.0 Fast / Mini | 같은 기능이지만 오디오 동기화가 표준 등급보다 느슨하다 |
| Gemini Omni | 립싱크가 1인 화자 6~7초에서 유지되고, Higgsfield 에서는 립싱크가 별도 기능으로 붙는다 |
| Wan / Happy Horse / MiniMax / LTX / PixVerse / Flux 3 | 대사 생성을 문서가 말하지 않는다 |

#### 합성하는가가 씬을 만드는 순서를 가른다

렌더가 소리를 합성하는지는 **행에 굳은 도구 버전**이 정한다(`pipelineFor(v).synthesizesSpeech` →
스펙의 `synthesizeSpeech`). 요청 시점의 버전이 아닌 이유는, 만든 규칙 그대로 렌더돼야 하기
때문이다. 그 값이 `compose.py` 의 순서를 가른다.

```
합성한다(v1.0)     1. TTS(대화내용 + 나레이션) → audio.m4a + duration  ← 길이가 여기서 정해진다
                   2. 영상 요청(duration_sec = 그 길이)
                   3. fit_to_duration(-an: 클립 오디오를 버린다)
                   4. mux_audio(합성한 소리를 유일한 오디오로)

합성하지 않는다     1. (TTS 없음)
(v1.5)             2. 영상 요청(프롬프트 = 장면 구성 + 발화 지시)  ← 모델이 픽셀과 같은 패스에서 낸다
                   3. normalize_clip_to_canvas(길이 불변, 오디오 보존)
```

**합성하지 않는 쪽에서 길이를 클립이 정하는 이유**: 발화가 클립 안에서 이미 끝나 있어 목표 길이로
자르면 문장이 잘린다. 이어붙이기가 요구하는 것은 같은 WxH/FPS/코덱이고 길이가 같아야 하는 것은
아니다. 대신 **요청할 길이는 두 문장을 합쳐 추정한다**(`speech_duration`). 하나만 재면 나레이션이
붙는 순간 클립이 말보다 짧아진다.

**렌더는 도구 버전을 모른다.** 스펙에 실린 `synthesizeSpeech` 하나만 본다. 버전 조건이 아니라 값이라,
나중에 v1.0 이 같은 방식으로 옮겨 와도 바뀌는 것은 코드가 아니라 스펙이다.

**발화 표기법의 주인은 video-model 이다.** 영상 모델은 대사를 별도 필드로 받지 않는다(벤더 요청
본문은 프롬프트, 길이, 화면비뿐이다). 그래서 프롬프트 안에 따옴표로 적어야 립싱크가 붙고, 그 문구가
`SCENE_DIALOGUE_PROMPT`(인물이 말한다)와 `SCENE_NARRATION_PROMPT`(화면 밖에서 읽는다)다. 둘 다 있으면
겹치지 않게 차례를 정하는 문장(`SCENE_SPEECH_ORDER_PROMPT`)이 뒤에 붙는다. 호출자는 "이 씬에서 이
문장들을 말한다" 까지만 안다.

그 결과 **프롬프트 상한을 발화가 먼저 차지한다.** 벤더가 프롬프트의 뒤를 자르므로 긴 장면 구성 뒤에
대사를 그냥 붙이면 대사가 통째로 사라지고, 인물이 입만 움직이는 영상이 나온다(그 사실은 결과물을
봐야 드러난다). 그래서 조립 시점에 장면 구성 쪽을 먼저 줄인다.

**글자 예산은 필드별이 아니라 합계로 준다.** 벤더 천장이 10초이고 초당 4~5음절이라 **두 문장을 합쳐
40자**가 상한이다. 필드마다 40자를 주면 합이 80자가 되어 절반이 잘린다. 배분은 LLM 이 씬마다 정한다.
고정 분할(각 20자)로 두면 대사만 있는 씬에서 남은 나레이션 몫을 못 가져와 쓸 수 있는 길이의 절반을
버리기 때문이다. 그래서 지시는 한 줄이되 **왜 그 수인지**를 함께 적는다. 근거가 있어야 모델이 한쪽을
늘릴 때 다른 쪽을 줄인다.

#### ElevenLabs 는 배선만 남아 있다

v1.5 가 TTS 를 쓰던 시절의 나레이션 모델 3종(v3 / Multilingual v2 / Flash v2.5)은 어느 버전에서도
고를 수 없다(`RETIRED_FROM_ALL_VERSIONS`). 어댑터와 자격증명 배선은 지우지 않았다. 이 저장소의
관용대로 노출만 껐고, 되살릴 때는 카탈로그 한 줄이면 된다.

아래는 그 시절의 결정 기록이다. 되살릴 때 다시 정하지 않으려고 남긴다.

**나레이션 모델을 하나로 좁히지 않은 이유**는 고를 때의 축이 셋으로 갈려서다: 표현력(v3),
안정성과 숫자 읽기(Multilingual v2), 속도와 문자당 절반 단가(Flash v2.5). 셋 다 한국어가 벤더
문서에 명시돼 있다. 영어 전용(`eleven_flash_v2`)과 문서가 대체됐다고 적은 1세대
(`eleven_turbo_v2_5`), 실시간 대화용(`eleven_v3_conversational`)은 싣지 않는다.

**음성은 이 화면에 없다. 조직 API 등록에 키와 함께 있다.** ElevenLabs 는 음성을 요청 본문이 아니라
경로로 받으므로(`POST /v1/text-to-speech/{voice_id}`) 키만으로는 한 번도 호출할 수 없다. 즉 음성은
"무엇으로 만들까"(개인 설정)가 아니라 "이 조직이 이 벤더를 쓸 수 있는가"(조직 자격증명) 쪽이고,
그래서 `ELEVENLABS` 프로바이더의 필수 필드 `voiceId` 다. 결과로 등록 완료 판정
(`hasRequiredCredentials`)이 음성까지 포함하고, 미등록은 모델 격자의 기존 게이팅이 그대로 덮는다.
음성 전용 상태를 화면 어디에도 만들지 않는다.

**개인 설정에 두지 않은 결정적 이유는 값을 구할 수 있는 사람이 정해져 있다는 것이다.** 음성 목록은
그 API 키를 가진 사람만 볼 수 있다. 도구 화면에서 개인에게 물으면 값을 얻을 길이 없는 사람 앞에
필수 입력을 놓게 된다. 덧붙여 한 번 등록하면 조직 전체가 같은 나레이터를 쓰므로, UUID 를 붙여
넣는 일이 조직당 한 번으로 끝난다.

`voiceId` 는 **비밀이 아닌 자격증명 필드**다(`CredentialFieldSpec.secret === false`). 저장 뒤에도
값이 뷰에 실려 입력칸에 보이고, API 키만 교체해도 유지된다. 비밀이 아닌 값을 시크릿으로 두면
확인할 방법이 재입력밖에 없다.

**드롭다운이 아닌 이유** 셋: 음성 ID 가 계정마다 다르고, 누구나 쓰는 기본 음성은 벤더 문서가
2026-12-31 만료를 못박았으며, 음성 라이브러리는 무료 플랜 계정에 API 로 열리지 않는다. 어댑터가
붙어 조직 키로 `GET /v2/voices` 를 부를 수 있게 되면 그때 드롭다운이 되고, 이 입력은 목록 밖 음성을
넣는 자리로 남는다.

조직에 나레이터가 둘 이상 필요해지면 그때 개인 설정에 **선택 항목**을 더한다(비우면 조직 값).
지금 그 갈래를 미리 만들면 아무도 지나가지 않는 분기만 남는다.

**안정성/유사도/스타일/속도는 받지 않는다.** 벤더 API 가 그 값들(`voice_settings`)을 *덮어쓰기*로
정의하고 보내지 않으면 음성에 저장된 설정을 쓴다. 그 설정은 소리를 들어 가며 맞추는 값이라,
미리듣기가 없는 우리 화면에서 숫자만 받으면 눈을 감고 고르게 된다. 저장 자리(컬럼)를 만들지 않은
것도 같은 이유다.

**v1.5 에 두 단계가 없는 이유는 같다: 고를 대상이 없다.** Higgsfield 영상 모델에 텍스트 인코더가
붙어 있어 텍스트를 받으면 바로 영상을 만든다. 그 사이에 씬 이미지도, 별도 언어 모델 호출도
존재하지 않는다.

이 사실은 **역량 축**으로 표현한다(`AiCapability.versions`). 모델 축(`AiModelOption.versions`)으로
그 역량의 선택지를 전부 비우는 것과 다르다: 선택지가 빈 역량은 화면이 "준비중" 으로 그리는데,
그건 곧 생긴다는 뜻이라 없는 기능을 기다리게 만든다. "모델을 고정해 두고 선택만 감춘다" 와도
다르다. 그랬다면 어느 모델로 만들어지는지 화면이 밝혀야 한다.

**백엔드도 같은 사실을 알아야 한다**(기획 생성이 이미지 단계를 건너뛴다). 한때 "언어가 달라 표를
공유할 수 없다" 고 보고 양쪽이 따로 선언한 뒤 `scripts/check-marketing-scene-images.mjs` 가 두 소스를
정규식으로 긁어 대조했다. 지금은 **한 표에서 나온다**(`@csc/tool-versions`): 화면의 역량 `versions` 는
그 표에서 파생하고(`versionsWhere`), 서버는 같은 표를 그대로 읽는다. 어긋남이 조용했던 것이 문제의
전부였는데(백엔드만 남으면 화면에 고를 자리가 없는데 서버가 저장된 옛 모델로 이미지를 만들어 사내
GPU 를 점유하고, 프론트만 남으면 화면이 이미지를 고르게 해 놓고 서버가 거절한다), 사본이 없으면 그
상태를 만들 수 없다.

> **v1.5 에 남은 것은 하나다**(원천 영상 생성 배선과 텍스트 출처는 끝났다).
>
> **Higgsfield 엔드포인트 경로가 확정되지 않았다.** 벤더 문서 둘이 서로 다르게 적는다.
> `docs/models` 표는 `POST /veo3.1/text-to-video`, `docs/openapi.json` 은 `POST /veo3.1` 이고,
> 지금 카탈로그의 key 는 **전부 앞쪽에서 왔다**(openapi 에는 이 목록의 모델이 하나도 없다).
> key 가 곧 호출 경로인 설계라 어느 쪽이 맞는지 정해야 하며, 실제 키로 한 번 호출해 보는 것
> 외에 방법이 없어 보인다. 어긋나면 증상은 404 다.

### 프로세스와 가격표는 그 버전의 사실만 말한다

두 화면은 두 버전에 다 있다(`versionProfile.sections`). 그런데 오래 **둘 다 v1.0 을 설명했다.**

**프로세스**는 서버가 만든 한 벌의 파이프라인 서술을 그대로 그린다. 그 서술에 버전 인자가 없어서
v1.5 화면이 그 버전에서 서버가 400 으로 막는 **씬 이미지 스텝**과, 세트를 만들 수 없어 일어날 수 없는
**최종 합성 단계**를 보여주고 있었다. 원천 영상 단계는 "이미지→영상" 이라고 적혔고, 씬 모션 프롬프트는
한 번도 나가지 않으면서 나가는 것과 같은 무게로 놓여 있었다.

이제 서술도 이음새다. `PlanProcessViewBuilder` 를 버전별로 두고 레지스트리가 고른다
(`core/domain/process/v10/view.ts`, `v15/view.ts`). 한 함수가 버전 인자를 받아 삼항으로 갈리던 것을
버전마다 평서문으로 적는 쪽으로 바꿨다. 레지스트리 키가 이미 버전을 말하므로 각 빌더는 자기 사실을
정적으로 알고, 사실 표를 다시 읽지 않는다.

공유하는 것은 키워드 준비 단계 하나다. 그 단계가 서술하는 코드가 실제로 한 벌이라 산문도 한 벌이어야
한다. 세그먼트 목록은 계속 입력으로 받는다(그 값이 실제 조립과 같은지 검사하는 스펙이 있고, 빌더가
직접 만들면 그 검사가 사라진다).

사실은 버전마다 **한 덩어리**로 모여 있다(`@csc/tool-versions` 의 `TOOL_VERSION_PIPELINES`).

| 사실 | v1.0 | v1.5 | 이것이 정하는 것 |
|---|---|---|---|
| `usesSceneImages` | 예 | 아니오 | 씬 이미지 스텝, 이미지 역량과 그 단가, 기획 생성의 이미지 게이트, **기본 씬 비주얼로 떨어질 수 있는가** |
| `usesFinalComposite` | 예 | 아니오 | 최종 합성 단계, 워크스페이스의 최종 구역, 보관물이 오는 표 |
| `synthesizesSpeech` | 예 | 아니오 | TTS 하위단계 셋, 나레이션 역량과 조직 키, 렌더 스펙의 `synthesizeSpeech` |
| `pinnedPlanLlm` | 없음 | `claude-sonnet-5` | 서버가 부르는 기획 모델, 설정의 선택기 유무, 가격표의 줄 |
| `briefRefinerLlm` | 없음 | `claude-sonnet-5` | 기획 앞의 입력 정제 스텝 유무와 그 모델, 프로세스 화면의 정제 스텝, 가격표의 LLM 호출 수 |
| `pinnedProposalCount` | 없음 | 1 | 한 번에 만드는 기획안 수, 개수 선택기 유무, 출력 토큰 예산의 배수 |
| `aspectRatio` | `4:5` | `9:16` | 렌더 캔버스, 씬 이미지 생성 크기와 구도 지시, 화면의 상자 비율 |

**사실마다 표를 따로 두지 않는다.** 한 버전을 이해하려고 표 넷을 오가야 하고, 새 사실을 더할 때 새
표를 만들고 소비자를 찾아다니는 일이 되어 빠뜨려도 조용하다. 덩어리면 `Record<ToolVersion, …>` 가
**모든 버전이 그 사실에 답하도록** 요구한다.

**씬 이미지를 만들지 않는 버전은 기본 씬 비주얼(slideshow)로 렌더할 수 없다.** 그 provider 는 씬
이미지 한 장을 받아 클립을 만들기 때문이다. 그래서 그 버전에서 영상 모델이 정해지지 않으면 렌더를
시작하지 않고 402 로 멈춘다(`assertVisualProviderRenderable`). 원인을 나열하지 않고 **결과 하나**를
막는다: 모델 미선택, 카탈로그에서 사라진 모델, 조직 키 미등록, 설정 조회 실패가 모두 같은 자리로
모이기 때문이다. 그대로 진행하면 워커까지 가서 "slideshow: 씬 이미지가 필요합니다" 로 죽고, 사용자는
고쳐야 할 것을 알 수 없다. 실제로 그렇게 죽은 렌더가 있었다. 402 인 이유는 조직 키 검사와 같다:
그 상태코드만 사유 문구를 화면까지 그대로 전달하고, 재시도 대신 설정을 고치라고 알린다.

**렌더러도 같은 자리를 막는다.** 위 게이트는 잡을 만들기 전의 검사라 잡이 만들어진 뒤의 사정은
막지 못한다. 워커가 그 provider 를 모르면(미배포, 또는 어댑터 추가 이전 코드로 떠 있는 워커) compose
는 기본 씬 비주얼로 폴백하는데, 씬 이미지가 없는 잡은 그것으로 만들 수 없다. 그래서 폴백 대신
**실제 원인**으로 끝낸다(`_pick_visual`: provider 이름 + 그 워커의 등록 목록). 폴백하면 사용자는
"씬 이미지가 필요합니다" 만 보고, 정작 고쳐야 하는 것은 워커 재기동이다(dev 워커는 의도적으로
리로드하지 않는다: 렌더가 씬당 수 분이라 편집마다 끊기면 안 된다). 그 실패가 실제로 두 번 있었다.
이미지가 있는 잡은 예전처럼 폴백한다: 그 잡은 기본 비주얼로 실제로 만들 수 있고, 씬 하나가
미배포 provider 때문에 통째로 실패하는 것보다 모션 없는 클립이 낫다.

**새 버전 추가 = 그 한 덩어리.** 채우면 서버(기획 게이트, 렌더 스펙, 프로세스 서술)와 화면(역량 노출,
가격표, 설정)이 함께 따라온다. 예전에는 같은 일이 파일 여섯 곳을 고치는 일이었고 그중 셋은 CI
스크립트가 잡아 주기 전까지 조용했다.

**"있으면/없으면" 헤지를 쓰지 않는다.** 한 문장이 두 버전을 다 설명하려 하면 어느 쪽 독자도 자기
파이프라인을 읽지 못한다. 갈리는 자리는 문장을 둘로 나눈다.

**가격표**는 반대로 이미 버전별로 걸렀다(설정 화면과 같은 판정). 문제는 거른 결과에 대해 화면이 하는
말이었다. v1.5 는 영상과 나레이션 두 역량뿐이고 모델 여섯이 전부 크레딧 과금이라 **공개 단가가 한 줄도
없는데**, 화면은 없는 내부 모델을 설명하고 청구 주체를 모델 제작사로 적고 "표시 단가는 각 회사가 공개한
API 요금" 이라고 적었다.

- **청구 주체는 벤더가 아니라 키를 등록하는 곳이다.** Kling/Seedance/Veo 는 만든 곳이 셋이지만 청구는
  전부 Higgsfield 다. 그 판정(`viaPlatform`)은 세 화면이 각자 복제하고 있어 카탈로그로 올렸다.
- **없는 것을 설명하지 않는다.** 내부 모델 안내와 공개 단가 각주는 그것이 있을 때만 그린다.
- **호출 횟수는 단가가 없어도 사실이다.** 영상 한 편에 무엇이 몇 번 나가는지를 따로 보여준다. 모든 줄이
  "요청마다 다름" 인 버전에서는 그것이 화면에 남는 유일한 숫자다. 금액은 지어내지 않는다.

### 프레임이 둘러싸고 영상이 그 안에 들어간다 (v1.0 최종 합성)

**두 버전이 영상을 다르게 낸다.** v1.5 는 영상 자체가 9:16 산출물이고 프레임 단계가 없다
(`workspaceStages: ['source']`). v1.0 은 마지막에 프레임을 입히며, 그 단계의 이름이 화면에서도
'프레임 적용' 이다.

| 순서(뒤 → 앞) | 레이어 |
|---|---|
| 1 | 검정 밑판(프레임의 투명 영역을 못박는다) |
| 2 | 프레임(캔버스를 덮는다. 캔버스 모양도 이것이 정한다) |
| 3 | 원천 영상(안전 구역에 비율 그대로 앉는다) |
| 4 | 제목과 자막(ASS 번인. 안전 구역 안에서 영상 위에 얹힌다) |

**영상을 프레임 위에 덮지 않는다.** 조직이 올리는 프레임은 전면 배경이라(가운데가 비고 위아래에
장식) 영상이 캔버스를 채우면 프레임이 100% 가려진다. 그 상태가 "프레임이 적용되지 않는다" 로
신고됐다.

#### 프레임 안전 구역 (제작 규약)

원천이 앉는 자리는 **프레임 안전 구역**이다(`ass_builder.content_band_pct`). 프레임의 장식은 이 구역
밖에 둔다는 약속이고, 그것이 프레임 제작 규약이다.

| 구역 | 캔버스 높이 대비 | 무엇이 놓이는가 |
|---|---|---|
| 위 | 0% ~ 12% | 프레임 장식(로고, 그림) |
| 가운데 | 12% ~ 82% | **원천 영상**. 제목과 자막도 이 안에서 영상 위에 얹힌다 |
| 아래 | 82% ~ 100% | 프레임 장식(브랜드 마크) |

경계의 주인이 오버레이 레이아웃인 이유는 같은 값이 텍스트 위치도 정하기 때문이다(제목은 구역
위쪽, 자막은 아래쪽에 붙는다). 두 곳에서 각자 정하면 한쪽만 옮겨져 텍스트가 장식 위로 나간다.

**텍스트 몫을 자리에서 빼지 않는다.** 레이어가 프레임 → 영상 → 텍스트라 텍스트는 영상 위에
그려진다. 예전에는 반대로 계산했다(제목 밴드 아래 ~ 자막 밴드 위 = 영상 자리). 그러면 영상이
자리의 88% 만 쓰면서 정작 텍스트는 구역 밖으로 나가, **제목이 프레임의 해 그림 위에 찍혔다.**

**이 구역의 비율이 생성 시점 화면비를 정한다.** 9:16 프레임에서 구역의 모양은 0.804 이고, 그 자리에
가장 잘 들어가는 카탈로그 값이 4:5(99.6% 사용)다. 그래서 v1.0 은 4:5 로 만든다. 구역이나 프레임
규약(`ffmpeg_ops.FRAME_CONVENTION_ASPECT`)을 바꾸면 `scripts/check-marketing-aspect.mjs` 가 화면비를
함께 보라고 알려 준다(후보별 사용률을 표로 출력한다).

프레임 아래에는 검정을 깐다. 프레임에 투명한 부분이 있으면 그 아래에 아무것도 없어 결과가 인코더의
알파 처리에 좌우되는데, 못박아 두면 어떤 프레임이 와도 같은 그림이 나온다.

**캔버스는 프레임 모양이다**(`resolve_final_canvas`). 프레임이 화면 전체이므로 결과의 모양도
그것이다. 원천을 따르게 두면 4:5 원천을 넣는 순간 최종이 4:5 로 나와 **9:16 프레임이 사라진다**
(배포처가 요구하는 모양도 함께 사라진다). 그래서 원천의 화면비는 그 자리를 얼마나 잘 채우는지만
정하고, 그 값은 버전이 갖는다(v1.0 = 4:5).

캔버스와 원천이 어긋나 얇은 검은 선이 남던 문제는 이 규칙과 무관해졌다. 그때는 원천을 캔버스에
직접 맞췄고(contain) 두 치수의 반올림 규칙이 달라 좌우 8px 이 남았다. 지금은 원천이 자리 안에
앉으므로 남는 여백이 곧 프레임이다.

**예전에도 프레임은 보이지 않았다.** 최초 구현(2026-07-22)부터 프레임을 배경으로 깔고 원천을 contain
으로 얹었는데, 원천이 캔버스를 그대로 채우는 크기라 프레임이 드러날 자리가 없었다. 원천 화면비가
프레임과 달랐던 프로젝트에서만 위아래로 보였다. 그래서 과거 최종본에는 프레임이 없고, 다시 만들어야
들어간다.

### 영상 모델에 닿는 두 경로 (플랫폼 경유 / 운영사 직접)

같은 모델이 두 경로로 존재할 수 있다. Veo 3.1 이 그렇다. 다른 것은 모델이 아니라 **누구의 키로
누구를 부르고 요금이 어느 계정에 붙는가**다.

| | 플랫폼 경유 | 운영사 직접 |
|---|---|---|
| 예 | Higgsfield → Kling, Seedance, Veo | Gemini → Veo |
| 조직이 등록하는 키 | 그 플랫폼 키 하나로 여러 회사 모델 | 그 회사 키로 그 회사 모델만 |
| 요금 | 플랫폼 계정(크레딧) | 그 회사 계정(공개 단가) |
| 막히는 방식 | 플랫폼이 모델을 끄면 그 경로 전체 | 그 회사 계정의 등급과 한도 |

**한 경로가 막혀도 다른 경로로 만들 수 있다는 것이 둘을 함께 두는 이유다.** 실제로 그 상황을 겪었다
(2026-09-01: 플랫폼 계정 크레딧 0 + Veo 와 Seedance 는 벤더가 꺼 둠 → 만들 수 있는 영상이 없었다).

**부류의 정의는 자격증명 카탈로그(`@csc/api-providers`)의 `kind` 다.** 모델 목록이 그 사실을 다시
선언하지 않는다. 등록 화면과 모델 목록이 같은 단어를 쓰는 것도 그래서다(같은 것을 두 이름으로 배우게
하지 않는다). 세 번째 부류는 **키 불필요**다. '사내' 라고 부르지 않는 이유는 키가 필요 없는 것과
우리가 호스팅하는 것이 다르기 때문이다(Edge TTS 는 Microsoft 의 무료 서비스다).

**경로가 둘 이상이면 화면은 탭으로 전환한다.** 한 번에 한 부류만 보여 목록이 짧아지고, 지금 보는
것이 어느 계정에 청구되는지가 화면에 남는다. 하나뿐이면 탭을 그리지 않는다(전환할 곳이 없는 탭은
누를 수 없는 장식이다). 지금 탭이 붙는 곳은 v1.5 의 영상 모델 하나다.

탭에서 지켜야 하는 규칙 둘이 있고 둘 다 테스트로 잠갔다.

- **저장된 모델이 있는 탭이 열린 채 시작한다**(`resolveRouteTab`). 첫 탭을 열면 강조된 타일이 없어
  아무것도 고르지 않은 화면처럼 보이고, 그러면 사람이 다시 고른다. 생성 모달에서 그 재선택은 곧
  '이번 생성만 변경' 이 된다.
- **검색과 요약은 지금 탭의 목록을 센다.** 전체로 재면 화면에 없는 모델까지 세어, 다섯 줄짜리
  목록 위에 검색창이 붙는다.

**라우팅은 카탈로그 key 의 접두사가 정한다.** `<라우트>/<그 안의 모델>` 이고, 라우트가 곧 video-model
의 provider key 이며 그 라우트가 요구하는 조직 키를 정한다(`VIDEO_ROUTES`). 그래서 새 경로를 붙이는
일이 표 한 줄 + 어댑터 하나이고, 모델을 더하는 일은 카탈로그 한 줄이다.

| 자리 | 무엇을 정하는가 |
|---|---|
| `aiModelOptions.ts` 의 key 와 `credentialProvider` | 화면이 무엇을 보여 주고 무엇을 게이팅할지 |
| `VIDEO_ROUTES`(csc-marketing) | 렌더가 어느 조직 키를 찾고 어느 어댑터로 보낼지 |
| `scripts/check-video-model-routes.mjs` | 위 둘이 **같은 답을 하는지** |

마지막 줄이 필요한 이유: 어긋나면 아무 에러도 나지 않는다. 화면은 키가 등록됐다고 보고 모델을 열어
주는데 렌더는 다른 프로바이더의 키를 찾아 402 로 끝난다. 경로가 하나뿐일 때는 어긋날 자리가 없었다.

**접두사가 없는 key 는 개명하지 않는다**(`grok-imagine-video`). 조직이 저장한 선택과 단가표가 그
문자열이라, 바꾸면 저장된 선택이 아무 모델도 가리키지 않게 된다.

### v1.5 의 기획 LLM 은 고르지 않고 고정한다

**두 버전 다 기획 LLM 을 부른다.** 영상 모델의 텍스트 인코더는 문장 하나를 클립 하나로 바꿀 뿐이라,
씬을 몇 개로 나눌지와 각 씬의 장면 구성/대화내용은 정하지 못한다. 그것을 쓰는 것이 기획 LLM 이다.

다른 것은 **고르는 방식**이다. v1.0 은 셋 중에서 고르고, v1.5 는 `claude-sonnet-5` 로 고정한다.
그 버전에서 고를 수 있던 자체 LLM 이 내려가면서 선택지가 0개가 됐기 때문이다.

고정하기 전에는 모델명을 **빈 값**으로 보냈고, language-model 이 자기 카탈로그 기본(내장 Qwen3)으로
떨어뜨렸다. 그 버전의 기획 품질을 아무도 고르지 않은 채 기본값이 정하고 있었고, 어느 모델이 쓰이는지
화면 어디에도 적혀 있지 않았다.

**"쓴다" 와 "고른다" 는 다른 축이다.** 한때 이 역량을 v1.5 의 역량 축에서 통째로 뺐는데 그건 틀렸다.
축에서 빼면 그 지출이 가격표에서 사라지고, 준비상태도 그 모델의 API 키를 요구하지 않는다. **실제로는
호출이 나가고 청구된다.** 반대로 넣기만 하면 고를 수 없는 선택기가 살아나고 "고른 적 없다" 가 생성을
막는다. 그래서 축을 둘로 나눈다.

| 축 | 무엇을 정하는가 | v1.5 의 LLM |
|---|---|---|
| `versions` | 이 버전이 이 단계를 밟는가 | 밟는다(가격표에 실리고 키가 필요하다) |
| `pinnedByVersion` | 밟되 고를 수 있는가 | 고를 수 없다(설정은 고정 표시만) |

| 읽는 자리 | 고정일 때의 결론 |
|---|---|
| 서버 | 저장값을 보지 않고 고정 모델로 부른다(`planLlmForVersion`) |
| 기획안 저장 | 실제로 부른 모델로 굳힌다. 저장값을 적으면 원장이 "모델 모름" 으로 남는다 |
| 설정 | 선택기 대신 어떤 모델이 쓰이는지 알린다 |
| 가격표 | 그 모델 한 줄만 싣는다(고를 수 없는 나머지의 단가는 그 버전의 정보가 아니다) |
| 준비상태 | 고른 적 없음으로 막지 않는다. 대신 그 모델의 키는 필요하다 |

**모델 키를 바꾸면 조직에 필요한 API 키가 바뀐다.** 외부 모델은 조직이 그 제작사 키를 등록해야
돌아간다(내장 모델은 필요 없었다). 값은 파이프라인 표 한 곳에 있고(`pinnedPlanLlm`) 서버가 부르는
모델과 화면이 말하는 모델이 거기서 함께 나온다. 예전에는 두 언어에 각자 적고
`scripts/check-pinned-models.mjs` 가 대조했다.

### 어떤 모델이 썼는지는 생성 응답이 말한다

위 표의 "실제로 부른 모델로 굳힌다" 를 성립시키는 배선이다. 고정 버전에서는 규칙이 저장값을 이기므로
무해했지만, **고를 수 있는 버전에서는 저장이 그 값을 알아낼 방법이 없었다.** 저장 시점에 채널 설정을
다시 읽는 방식이었고, 기획안을 뽑은 뒤 설정을 바꾸면 쓰지 않은 모델이 저장본에 남았다.

그래서 생성 응답이 기획안 배열 하나가 아니라 **봉투**다.

```ts
interface GeneratedPlans { proposals: PlanProposalEntity[]; llmModel: string; }
```

`llmModel` 은 활동 원장에 쓰는 값과 **같은 변수**다(`costModel`). 한 변수를 두 곳이 쓰므로 두 기록이
갈릴 자리가 없다. 저장 요청은 그 값을 그대로 되돌려 주고, `planLlmForVersion` 이 고정 버전에서 한 번
더 이긴다(요청이 무엇을 실어 왔든 그 버전이 부를 수 있는 모델은 하나다).

**저장 요청에서 이 필드는 필수다.** 선택으로 두면 사슬이 반쪽만 배포된 상태에서 저장이 조용히
성공하고 저장본은 "모델 모름" 으로 남는다. 그 값은 나중에 되메울 수 없다(무엇이 썼는지는 생성 순간에만
안다). 빠지면 400 이고 그 사유가 화면 우하단 알림에 뜬다. 다만 **빈 문자열은 막지 않는다.** 그 채널에
기획 LLM 을 고르지 않았고 language-model 도 모델 이름을 밝히지 않으면 원장도 같은 빈 값이라,
여기서 막으면 그 설정에서는 저장 자체가 불가능해진다.

같은 어긋남이 이미지 모델에도 있다. 씬 이미지는 씬마다 그때 모델로 그려지고 그 값이 응답에 실려
오지 않아, 고치려면 이미지 생성 경로까지 봉투로 바꿔야 한다. 지금은 저장 시점 설정에서 읽는다.

### 기획안 개수도 고정한다. 그리고 그 규칙은 서버에 있어야 한다

같은 축의 사실이 하나 더 있다. v1.0 은 서로 다른 기획안 여러 개를 받아 그중 하나를 고르고, v1.5 는
영상 한 편을 만들므로 기획안이 정확히 하나다. 그래서 그 버전에는 개수를 고를 자리가 없다.

**상한이 아니라 고정이다.** `≤N` 으로 두면 1~N 이 다 통과해 그 사실을 표현하지 못한다. v1.5 의 출력
스키마는 "배열의 항목은 정확히 1개다" 라고 말한다.

이 규칙이 **브라우저에만 있던 동안** 서버는 요청받은 수를 범위로만 걸러 그대로 썼다. 그 상태에서
낡은 탭이나 직접 호출이 6을 보내면 세 곳이 서로 다른 말을 한다.

| 자리 | 그때의 값 |
|---|---|
| 프롬프트 | 정확히 1개 |
| 출력 토큰 예산 | 여섯 배(어댑터가 기획안 수로 곱한다) |
| 파서 | 여섯 개까지 잘라낸다 |

예산의 배수는 상한이라 요금이 곧바로 여섯 배가 되지는 않지만, 잘림이 사라지는 대신 한 번의 요청이
그만큼의 여유를 잡는다. 그리고 씬 이미지에는 이런 요청을 막는 게이트가 있는데(400) 이 축에는 없었다.

**거절하지 않고 이긴다.** 400 은 "그 버전이 만들지 않는 산출물" 을 요청했을 때 쓰는 것이고, 기획안
3개를 받아 1개를 만드는 것은 다른 산출물이 아니라 그 버전의 유일한 산출물이다. 화면에 고를 자리가
없으므로 400 은 없는 UI 의 실수를 위한 실패 경로가 된다. 고정 모델이 저장값을 이기는 것과 같다.

**다만 조용히 이기지는 않는다.** 요청값이 고정값과 다르면 서버가 warn 을 남긴다. 그 로그가 뜨면
대개 화면 쪽 회귀이거나 낡은 탭이고, 남기지 않으면 그 회귀가 아무 신호 없이 지나간다(결과는 맞게
나오므로).

**브라우저의 규칙은 지우지 않는다.** 사내 GPU 보호(`resolvePlanComposeLimit`)와 브리프에서 개수를
읽는 일(`sceneCountFromBrief`)은 화면의 결정이다. 서버가 강제하는 것은 **개수 자체의 버전 규칙**
하나이고, 그것이 그 결정의 최종 방어선이다.

**씬(세그먼트) 수는 표에 넣지 않는다.** 버전이 정하는 사실이 아니다. v1.5 는 브리프의 번호에서
파생되고 v1.0 은 고르며, 상한 8 은 두 버전 공통의 서버 방어다.

### 로그는 반대로 버전을 가리지 않는다

프로세스와 가격표가 지금 보고 있는 버전의 사실만 말해야 하는 것과 달리, **활동 로그는 실제로 일어난
일을 말한다.** 그래서 이 화면만 버전으로 거르지 않는다. v1.5 를 보는 중이라고 v1.0 기록을 감추면 그
달에 나간 돈의 절반이 사라진다.

**열람은 관리급(루트, 대표, 팀장)이고 범위는 조직 전체다.** 두 버전 모두 같다. 채널 필터는 표시용이고
경계가 아니라, 통과한 사람은 남의 채널에서 일어난 활동도 본다. 팀장이 들어가는 이유는 공용 자산과
운영 화면(프로세스, 가격표)을 관리하는 사람이 그 조직에서 누가 어느 채널에서 무엇에 돈을 썼는지도
봐야 하기 때문이다. 직책 없는 조직원은 자기 채널을 갖고 영상을 만들 수 있지만 조직 전체 원장은
볼 수 없다.

| 지점 | 무엇을 하는가 |
|---|---|
| `lib/server/marketing/toolAccess.ts` | 판정의 단일 출처. `canViewActivityLogs` 가 관리급 판정을 감싼다 |
| `[toolSlug]/+layout.server.ts` | `canViewLogs` 플래그로 사이드바 항목을 가린다 |
| `.../log/+page.server.ts` | 직접 URL 진입을 워크스페이스로 되돌린다 |
| `api/marketing/activity-logs` BFF | `requireLogViewer` 가 집행한다. 조직 id 를 세션에서 확정하고 `all_orgs` 는 리터럴 false |

관리급과 같은 판정인데 함수를 따로 두는 이유. 두 정책은 지금 같을 뿐 같은 것이 아니다. 로그가 더
좁아지거나(감사 전용 권한) 부서 범위로 갈리는 날 `canViewActivityLogs` 와 `requireLogViewer` 의
반환값(열람 범위)만 바뀌고 나머지 지점은 그대로다. 클라이언트로 내리는 user 에는 직책이 없어
브라우저는 이 판정을 다시 할 수 없고, 서버가 내린 플래그만 쓴다.

거르지 않는 대신 **가린다.** 활동마다 `payload.version` 을 싣고 화면은 그것을 배지로, CSV 는 컬럼으로
내보낸다. 이 값이 없으면 원장만 보고는 답할 수 없는 것이 있다. 액션 이름이 두 버전에서 같아서
(`marketing.source.render_completed` 는 이미지→영상에서도 텍스트→영상에서도 같은 문자열이다) 어느
파이프라인이 돈을 썼는지 구분되지 않고, 두 버전의 영상 모델은 과금 방식까지 다르다(공개 단가 vs 크레딧).

| 성질 | 값 |
|---|---|
| 저장 위치 | `payload.version`(승격 컬럼 아님) |
| 마이그레이션 | 불필요. ClickHouse 는 `payload` 를 String 으로 들고 있다 |
| 옛 기록 | 값이 없다. 배지도 CSV 칸도 비운다(지어내지 않는다) |
| 거르기 | 지금은 못 한다. 필터로 쓰려면 승격 컬럼이 필요하다 |

**쓰는 쪽에서는 필수 필드다**(`ActivityLogEntry.version: ToolVersion`). 이 도구에서 버전은 주소의
축이라 버전 없이 일어나는 활동이 없고, 필수로 두면 새 활동이 값을 빠뜨릴 때 컴파일이 멈춘다. 선택
필드였다면 아무 일도 일어나지 않는다. 타입 검사가 통과하고, 로그는 실패해도 비즈니스 경로를 막지
않게 설계돼 있어 런타임도 조용하다. 몇 달 뒤 원장을 읽을 때에야 그 줄만 버전이 없는 것을 보게 되는데,
그때는 지나간 기록이라 되메울 수 없다.

읽는 쪽에서만 선택값이다. 값을 심기 전 기록에는 없기 때문이고, 같은 이유로 뷰어의 타입은 `VersionMode`
가 아니라 `string` 이다. 그 유니온은 **지금 쓸 수 있는** 버전이고 원장은 **그때 일어난** 일이라,
폐기된 버전의 기록을 좁혀 두면 타입은 없다고 말하면서 런타임에는 그대로 흘러든다.

### 소리를 누가 만드는가 (v1.5 는 영상 모델이 만든다)

**한 동영상의 말은 둘 중 하나다.** 필드는 둘이지만 한 동영상은 그중 하나만 채운다. 작업자가
'씬 / 사용자 입력사항' 에 적는 형식도 같은 모양이라, 쓰지 않는 쪽을 `없음` 으로 둔다.

| 필드 | 누가 말하는가 | 없으면 |
|---|---|---|
| `dialogue` | 화면 속 인물 | 말하는 인물이 없는 장면(제품 컷, 풍경) |
| `narration` | 화면 밖 목소리 | 인물의 말로 전하는 장면 |

**둘 다 오면 대화내용을 살린다.** 프롬프트가 하나만 쓰라고 지시하지만 지시는 계약이 아니므로,
v1.5 파서(`toScene`)가 대화내용을 남기고 나레이션을 비운다. 작업자가 둘 다 적어 온 경우에도 같은
규칙이다. 어느 쪽을 살릴지 정해 두지 않으면 같은 입력이 생성할 때마다 다른 화자로 나온다.

배타로 두는 이유는 둘이다. 클립이 최대 10초라 두 문장을 차례로 넣으면 둘 다 급해지고, 화면 밖
목소리와 인물의 말이 한 클립에서 번갈아 나오면 그 동영상이 무엇을 하는 장면인지 흐려진다.
(렌더는 이 보장에 기대지 않는다. 둘 다 온 씬에는 겹치지 않게 차례로 들리라는 지시를 붙인다.)

| 버전 | 소리를 만드는 곳 | 왜 |
|---|---|---|
| v1.0 | 렌더가 TTS 로 합성해 얹는다 | 이미지→영상이라 모델이 말을 못 한다. TTS 가 그 버전의 유일한 소리다 |
| v1.5 | **영상 모델** | 그 동영상의 말을 영상 프롬프트에 실어 화면과 함께 만들게 한다 |

**그래서 v1.5 의 설정에서 나레이션이 사라졌다.** 합성 단계가 없으면 고를 모델도, 조직 API 키도,
음성 ID 도 필요 없다. ElevenLabs 는 음성 ID 가 **벤더 API 경로에 들어가는 값**이라 뺄 수 없었고
(`POST /v1/text-to-speech/{voice_id}`, 기본 음성 엔드포인트가 없다), 등록된 값이 그 계정에 없는
id 라 렌더 잡이 계속 실패했다. 목소리를 만드는 곳을 하나로 모으면 그 표면이 통째로 없어진다.

**렌더는 버전이 아니라 값으로 가른다.** 잡의 `synthesize_speech` 가 "이 서버가 소리를 만드는가" 를
말하고, video-model 은 호출자의 버전을 몰라도 된다. 그 값은 `pipelineFor(v).synthesizesSpeech` 에서 온다.
(구 잡은 같은 것을 `use_narration` 이라는 이름으로 실었다. 그때는 "나레이션을 얹는가" 가 곧 "이
서버가 소리를 만드는가" 였으므로 옛 이름도 그대로 읽는다.)

**분량 예산은 40자다.** 클립이 최대 10초이고 한국어는 초당 4~5음절이라 40자가 9초 안팎이다.
넘치면 말이 끝나기 전에 동영상이 끝난다. 근거(10초)를 프롬프트에 함께 적는다. 숫자만 주면 모델이
그것을 창작 여지로 읽는다.

### 씬 길이는 그 씬의 말이 정한다

**규칙은 하나다: 씬 길이는 그 씬의 말을 하는 시간이다.** 재는 방법만 소리를 만드는 곳에 따라 갈린다.

| 소리를 만드는 곳 | 재는 방법 | 클립을 어떻게 다루나 |
|---|---|---|
| 렌더(TTS) | 음성을 만들어 그 길이를 **잰다** | 비주얼을 그 길이에 맞춘다(모자라면 마지막 프레임 고정) |
| 영상 모델 | 텍스트에서 **추정한다**(`speech_duration.py`) | **건드리지 않는다**(발화가 클립 안에서 끝나 있어 자르면 문장이 잘린다) |

**두 필드를 모두 보고 잰다.** 기획은 둘 중 하나만 채우지만 재는 쪽은 어느 쪽이 찼는지 묻지 않고
둘을 합쳐 잰다. 한쪽만 보면 나레이션으로 만든 동영상의 길이가 0으로 잡혀 기본값으로 떨어지고,
그 어긋남은 클립을 받아 봐야 드러난다.

아래 칸에 추정이 필요한 이유가 그 오른쪽 칸에 있다. 그 경로는 받아온 클립을 자르지도 늘리지도 않으므로
**요청 길이가 결과에 닿는 유일한 손잡이**다. 오래 그 값이 대화내용과 무관한 고정 4초였고, 기획
프롬프트는 같은 시기에 약 50자를 요구했다. 한국어 50자는 말하는 데 10초가 넘으므로 벤더는 말이
끝나지 않는 클립을 만들었고, 그것이 그대로 최종본에 실렸다.

**사람이 지정한 값(`durationSec`)이 있으면 추정하지 않는다.** 그래서 추정치를 그 컬럼에 채우지
않는다. 채우면 "사용자가 8초로 정했다" 와 "우리가 8초로 어림했다" 가 같은 값이 되어 우선순위 규칙이
뜻을 잃는다.

**분량 예산은 벤더 천장에서 나온다.** 영상 모델이 만들 수 있는 클립은 최대 10초다(Higgsfield 는 5초
아니면 10초만 받는다). 초당 4~5음절이면 40자가 9초 안팎이라, 프롬프트가 대화내용을 40자 이내로
요구한다. 그 숫자는 취향이 아니라 이 천장의 결과이고, 넘치면 두 경로가 다르게 망가진다(영상 모델이
만드는 쪽은 말이 잘리고, TTS 를 얹는 쪽은 초과분만큼 화면이 멈춘 채 소리만 이어진다).

**누가 말하는지는 정하지 않는다.** 세그먼트 하나에서 그 상황에 맞는 누군가가 대화내용을 말한다.
두 사람이 번갈아 말하라는 규칙은 두지 않는다: 그것은 장면이 정할 일이고, 규칙으로 박으면 인물이
하나뿐인 장면에서도 없는 상대를 만들어낸다.

### 화면비는 버전이 정한다

**영상이 화면 전체가 되는 버전과 프레임 안의 한 자리에 앉는 버전은 애초에 같은 모양이 아니다.**

| | v1.0 | v1.5 |
|---|---|---|
| 화면비 | `4:5` | `9:16` |
| 그 영상이 놓이는 곳 | 배경 프레임 안의 빈 자리 | 화면 전체 |
| 최종 캔버스 | 프레임 치수(프레임이 배경이다) | 원천 그대로(최종 합성 단계가 없다) |

v1.0 이 숏폼 규격을 따르지 않는 이유가 여기 있다. 그 버전의 배경 프레임은 위아래에 장식이 있고
가운데가 비어 있어, 영상이 앉는 자리(안전 구역)가 9:16 프레임에서 약 0.804 다. 9:16 원천을 그
자리에 넣으면 **자리의 70% 만 쓰고** 704x1280 이 504x896 으로 줄어 해상도까지 버린다. 4:5 는
99.6% 를 쓴다(위 안전 구역 절의 후보별 표). 한 값으로 묶어 둔 동안 실제로 그렇게 렌더됐다.

**같은 버전 안에서는 이미지와 영상이 한 값을 쓴다.** 이미지→영상 파이프라인(v1.0)에서 씬 이미지가
곧 영상의 한 프레임이라, 둘이 갈리면 렌더러가 이미지를 캔버스에 꽉 채워 자른다(`_cover`: scale 후
crop). 그래서 생성 크기와 프롬프트의 구도 지시가 **같은 한 줄에서** 나온다
(`plan-generation.service.ts` 가 그 버전의 화면비를 읽어 둘 다 만든다). 갈리면 결과 영상을 보고서야
드러난다.

**어느 값인지는 버전 사실 표가, 그 값의 해석은 공유 커널이 갖는다.**

| 소유 | 무엇 |
|---|---|
| `@csc/tool-versions` (`pipelineFor(v).aspectRatio`) | 이 버전이 만드는 영상의 화면비 |
| `@csc/video-capabilities` | 비율 문자열 → 생성 크기, 프롬프트 라벨, CSS 값, 세로 배수 |

커널에 "현재 화면비" 같은 값을 두지 않는다. 값을 하나 두면 버전을 모르는 자리가 그것을 집어 들고,
그 자리만 다른 버전의 모양으로 그린다(카드는 `object-cover` 라 그림이 멀쩡해 보여 조용하다).

| 파생값 | 쓰는 곳 |
|---|---|
| 이미지 생성 크기(v1.0 `1024x1280`) | 씬 이미지 생성 호출 |
| 이미지 프롬프트 라벨(v1.0 `vertical (4:5)`) | 같은 곳(확산 모델 구도 지시) |
| CSS 값(v1.0 `4 / 5`) | 기획안 타일, 세그먼트 카드, 미리보기 상자 |
| 세로 배수 | 캔버스로 그리는 산출물(인포그래픽 씬 이미지, 썸네일 초기 상자) |

**렌더러(video-model)만 문자열로 맞춘다.** Python 이라 그 파일을 import 할 수 없어 자기 픽셀표
(`ffmpeg_ops._DIMS`)와 폴백(`DEFAULT_ASPECT`)을 따로 든다. `scripts/check-marketing-aspect.mjs` 가
**버전이 선언한 화면비가 커널이 아는 값이고 화질 등급마다 픽셀표에 있는지**를 잠근다. 빠진 값은
폴백으로 접혀서, 고른 모양과 다른 모양이 말없이 나온다.

**이미 만들어진 영상은 바뀌지 않는다.** 화면비는 만들 때 프로젝트 행에 굳는다
(`marketing_video_projects.aspect_ratio`, 화질/모델과 같은 스냅샷 규칙). 그래서 예전에 만든 영상을
다시 만들어도 그때의 모양 그대로이고, **영상 카드도 버전이 아니라 그 행의 값으로 상자를 그린다**
(규칙에서 다시 파생하면 옛 영상이 새 상자에 담겨 잘려 보인다).

### v1.5 의 씬은 두 필드다

영상 모델에 넣을 텍스트의 출처가 정해졌다. **기획 LLM 이 그 모델을 위해 직접 쓴다.**

한때는 씬의 화면 묘사(`imagePrompt`)를 그대로 영상 프롬프트로 보냈다. 그 문장은 정지 이미지 한 장을
위한 브리프라 "글자, 자막, 로고를 넣지 말 것" 같은 이미지 규칙 아래 쓰이고 움직임을 말하지 않는다.
즉 영상 모델이 자기를 위해 쓰이지 않은 글을 받고 있었다.

**담을 항목을 나열하는 것만으로는 부족하다.** 그렇게만 쓰면 모델이 한 문장으로 끝내도 모든 항목을
형식적으로 만족한다. 영상 모델이 화면에 대해 아는 것은 이 문장뿐이므로 밀도 자체가 결과물의 품질이다.
그래서 셋을 함께 못박는다.

| 무엇 | 어떻게 |
|---|---|
| 분량 | 세 문장 이상(다섯 항목을 한 문장에 접을 수 없게) |
| 순서 | 배경 → 조명 → 카메라 → 동작과 전환 → 질감. 쓰는 차례를 정해야 빠지는 항목이 없다 |
| 형태 예시 | 밀도는 설명보다 보여 주는 편이 정확하다. 소재를 따라 쓰지 말라고 함께 적는다 |

**예시는 출력 계약과 어긋나면 안 된다.** 모델이 그대로 흉내 내는 글이라, 푸터가 금지한 문자가 예시에
있으면 그 금지가 스스로 무너진다(가운뎃점이 그 경우다). `assembler.spec.ts` 가 그것을 잠근다.

| | v1.0 (이미지→영상) | v1.5 (텍스트→영상) |
|---|---|---|
| 단위 이름 | 씬 | **동영상**(= 세그먼트) |
| 화면 | `sourceDirection` + `imagePrompt`(정지 브리프) | `sceneComposition`(움직임과 카메라를 포함한다) |
| 말 | `narration`(화면 밖) + `subtitle` | `dialogue`(화면 속 인물)와 `narration`(화면 밖) 중 하나 |
| 자막 | 있다 | **없다** |
| 인포그래픽 | 있다 | 없다 |

**두 필드뿐이라 자막 트랙이 만들어지지 않는다.** 렌더의 자막 트랙은 씬 `subtitle` 에서 나오는데 그
자리가 없으므로 `captions_file_id` 가 비고, 최종 합성이 번인할 것이 없다. 영상에 글자가 나오지 않는
것이 이 버전의 형식이다.

**필드를 유니온으로 가르지 않는다.** 두 형식을 판별 유니온으로 두면 파서, DTO, jsonb 타입, 카드 UI 가
전부 두 벌이 되는데 정작 물어야 하는 것은 "어느 쪽이 채워졌는가" 하나뿐이다. 그래서 선택 필드로 두고
읽는 쪽이 **값의 유무로** 가른다(`isSegmentFormat`). 화면이 버전을 prop 으로 나르지 않으므로 조건이
버전 수만큼 늘지 않고, 그 값을 빠뜨린 화면이 다른 형식으로 그리는 일도 없다.

렌더도 같은 근거를 쓴다: `compose.py` 가 씬 이미지 유무로 프롬프트의 뜻을 가른다.

**누가 말할지는 영상 설정이 아니라 동영상마다 정해진다.** 화면 밖에서 읽을 문장과 인물이 말할 대사는
문체가 다르고(`이 제품은 ~합니다` ↔ `엄마, 이거 뭐야?`), 그 선택은 동영상 하나하나의 장면이 정할
일이라 생성 화면의 설정으로 묶이지 않는다. 작업자는 '씬 / 사용자 입력사항' 에 동영상별로 적고,
적지 않으면 모델이 그 장면에 맞는 쪽을 고른다. 영상 모델과 세그먼트 연결 방식은 영상 전체에 걸리는
선택이라 지금처럼 저장 시점에 스냅샷으로 붙는다.

**프롬프트 파일이 갈렸다.** 위 형식 차이가 개수 지시와 출력 스키마를 통째로 다르게 만들어, v1.5 는
`core/domain/prompt/v15/{system,user}.ts` 를 자체로 갖는다. 공용이었던 배열은 v1.0 의 것이 되어
`core/domain/prompt/v10/{system,user}.ts` 로 옮겼다(두 버전이 대칭이라 어느 쪽도 기본이 아니다).
버전을 모르는 것만 그 위에 남는다: 조립 엔진(`prompt-segment.ts`), 카탈로그, 입출력 형태
(`prompt/context.ts`). 기본 편집 지침도 버전마다 다르다(그 버전 출력 형식을
전제로 쓰인 문장이라, 한 벌을 공유하면 없는 필드를 만들라는 지시가 된다). 그래서 조립기가
`defaultInstructions` 를 노출하고 서비스가 그것을 읽는다(저장 정규화와 폴백 둘 다).

**2. 어느 모델을 노출하는가.** 카탈로그 항목과 단가 카드, 백엔드 배선은 그대로 두고 노출만 끈다.
저장된 값을 읽는 `findAiModelOption`/`describeAiModel` 은 이 축을 보지 않는다: 다른 버전에서 만든
산출물의 모델 이름은 여전히 읽혀야 한다. 어느 버전도 쓰지 않게 된 모델(자체 Qwen3, Wan 2.2, FLUX)은
`RETIRED_FROM_ALL_VERSIONS` 로 표시한다(빈 배열 리터럴은 실수로 비운 것과 구분되지 않는다).

모델이 **자기 역량이 없는 버전**을 가리키지 않아야 한다. 그 선언은 아무 효과가 없으면서(역량 축이
먼저 걸러낸다) 읽는 사람에게는 "그 버전에서 쓴다" 로 보여 카탈로그가 거짓을 말하게 된다.

**3. 기본 모델은 조직 API 키를 요구하지 않는 모델만 될 수 있다.** 키가 필요한 모델을 기본으로 두면
"고르지 않아도 이걸로 만들어진다" 가 거짓이 된다(키 없는 조직에서는 그 기본으로도 만들어지지
않는다). 지금은 두 버전 다 남은 역량이 전부 조직 키를 요구해 기본이 하나도 없다.

기본이 없는 역량을 고르지 않은 채로 생성을 시작하면 **막고 우하단 알림으로 알린다**
(`aiModelReadiness.ts`). 백엔드는 빈 값을 받으면 자기 기본값(자체 LLM, 슬라이드쇼)으로 만들기
때문에, 막지 않으면 화면이 말한 적 없는 모델의 결과물이 나오고 그 사실은 다 만들어진 뒤에야
드러난다. 골라 둔 모델을 그 버전이 더는 쓰지 않을 때도(`retired`) 같은 알림이 나가되 문구가 갈린다.
"안 골랐다" 로 뭉뚱그리면, 고른 기억이 있는 사용자가 화면을 의심하게 된다.

**어댑터 유무는 더 이상 이 점검의 사유가 아니다.** 예전에는 카탈로그에 `backendReady: false` 라는
임시 표식을 두고 이 점검이 그것도 막았는데, 그 표식은 "어댑터를 붙이면 제거한다" 는 약속이 붙은
것이었고 v1.5 어댑터가 붙으면서 아무 모델도 그 값을 갖지 않게 됐다. 닿지 않는 분기를 남겨 두지
않는다. 다시 필요해지면(모델을 어댑터보다 먼저 싣는 상황) 그때 되살린다.

| 단계 | 필요한 역량 | 근거 |
|---|---|---|
| `plan` (기획서 생성) | llm, image | `plan-generation.service` 가 읽는 `aiModels.llm/image` |
| `sourceVideo` (원천 영상) | video, tts | `video-project-spec-builder` 가 읽는 `aiModels.video/tts` |

**이 표는 버전에 따라 좁아진다**(`stepCapabilities(step, version)`): v1.5 의 `plan` 은 이미지를
요구하지 않는다. 좁히는 규칙은 역량 축 하나에서 파생되며, 기획서 분량 제한(`planComposeOptions`)도
같은 함수를 본다(같은 질문에 두 답이 생기지 않게 한다).

최종 영상(프레임 적용)은 합성이라 AI 모델을 쓰지 않아 단계에 없다.

`Record<VersionMode, VersionProfile>` 이라 버전을 늘리면 컴파일이 빠진 프로필을 잡는다.
가시성과 게이트가 같은 값(`hasSection`)을 보는 것이 중요하다: 예전에는 v1.5 가 에셋을 nav 에서
감추기만 해서 `/assets` 를 주소로 직접 열면 그대로 들어가졌다.

**서버 게이트는 섹션마다가 아니라 `[channelSlug]/+layout.server.ts` 한 곳에 있다.** 모든 하위 섹션이
그 레이아웃을 지나므로 지금 있는 섹션도 나중에 생길 섹션도 자동으로 덮인다. 섹션마다 두면 새 섹션이
게이트 없이 추가될 수 있고, 그 빠짐은 주소를 직접 쳐 봐야 드러난다(그 사고가 이미 한 번 있었다).
판정은 nav 하이라이트와 같은 함수(`sectionFromPath`)를 쓴다: 둘이 갈리면 사이드바에서 눌리는데
열리지 않는 자리가 생긴다.

**버전 전환은 URL 이동이다**(상태 변경이 아니다). 채널/섹션/쿼리를 그대로 들고 가며, 대상 버전에
없는 섹션이면 워크스페이스로 접는다(`swapVersion`). 저장값 PUT 은 그 이동의 부수효과(다음 진입
기본값)이고 실패해도 화면은 이미 옳다.

**전역 스토어는 없다.** 예전에 스토어가 필요했던 이유는 고르는 자리(앱바)와 반응하는 자리(자식 셸)가
다른 레이아웃이라 prop 경로가 없어서였다. 버전이 URL 에 있으면 둘 다 `page.params` 를 읽는다.

## 캐시(쿼리 키)

마케팅 쿼리 키는 전부 **버전을 index 1** 에 갖는다.

```
['marketing-saved-plans', version, channelId]
['marketing-my-ai-model',  version]
['marketing-channels']                          ← 버전 무관(두 버전이 공유)
```

버전이 키에 있으면 전환 시 **무효화가 아예 필요 없다**(다른 키 공간이라 서로를 못 본다). 예전에는
버전이 키에 없어 전환할 때마다 무효화 목록을 손으로 유지해야 했고, 실제로 두 자원을 빠뜨려 v1.0
목록이 v1.5 화면에 그대로 남았다.

index 1 인 이유: 워크스페이스 그리드가 `useIsFetching({ queryKey: ['marketing-plans'] })` 로 접두사를
훑어 "생성중" 을 띄운다. 버전을 맨 앞에 두면 그 표시가 **에러 없이** 사라진다.

**키를 손으로 다시 적는 자리를 두지 않는다.** 생성 배치 키는 `plans.query.ts` 의
`planBatchQueryKey` 하나가 만들고, 취소 경로도 그것을 쓴다. 키를 사본으로 들고 있으면 축이 하나
늘어날 때 그 사본만 옛 모양으로 남는데, `cancelQueries`/`removeQueries` 는 **어긋난 키에 에러를
내지 않고 조용히 아무 일도 하지 않는다**. 실제로 그렇게 되어 타일만 사라지고 LLM 은 끝까지 돌았다.

## 버전을 하나 더할 때

1. `csc-marketing` `shared/domain/tool-version.ts` 의 `ToolVersion` 과 `TOOL_VERSIONS` 에 한 줄.
2. web `lib/shared/lib/versionMode/versionMode.ts` 에 같은 값 한 줄. 빠뜨리면
   `check-marketing-version-scope` 가 `[어휘]` 에서 막는다(두 값 공간이 어긋난 채로는 통과하지 못한다).
3. 컴파일러가 나머지를 센다: `VersionRegistry` 세 곳(프롬프트/원천/최종)과 web `versionProfile` 이
   그 버전 항목을 요구한다.
4. 프롬프트를 갈 거면 `core/domain/prompt/vXX/assembler.ts` 를 추가한다. 아니면 기존 조립기를
   그 슬롯에 가리킨다.

DB 마이그레이션은 필요 없다(값이 varchar 이고 CHECK 제약을 두지 않았다: 버전 추가가 마이그레이션
작업이 되지 않게).

## 버전을 뺄 때 (먼저 정할 것)

**어휘에서 값을 지우는 것만으로는 끝나지 않는다.** 그 버전으로 만든 행이 DB 에 남아 있고, 매퍼가
`toolVersionOrDefault` 로 읽는다. 즉 폐기된 값을 가진 행은 **조용히 기본 버전으로 읽혀** 남은 버전의
파이프라인으로 다시 렌더된다. 지금은 어느 버전도 폐기하지 않았으므로 이 경로가 발생하지 않지만,
폐기하는 날 둘 중 하나를 먼저 정해야 한다.

| 고르는 것 | 하는 일 |
|---|---|
| 남은 파이프라인으로 흡수 | 지금 동작. 목록에 그대로 보이고 다시 렌더도 된다. 결과물이 예전과 달라질 수 있다 |
| 읽기 전용으로 남긴다 | 매퍼가 폐기 값을 보존하고, 재렌더 경로에서 거절한다. 산출물은 보이되 다시 만들 수 없다 |

정하지 않고 값만 지우면 첫 번째가 **선택하지 않은 채로** 적용된다.

## 범위 밖

- **video-model / language-model 은 버전을 모른다.** 두 서버는 여러 도구에 서빙하므로 마케팅 도구의
  UI 버전을 알 이유가 없다. 렌더 자체가 갈려야 하면 **스펙 값의 차이**로 표현한다(provider key 분화가
  가장 싸다: `_build_provider_registry` 에 한 줄, 디스패치는 이미 `params["provider"]` 기반).
- **AI 도구를 둘로 쪼개지 않는다.** 엔타이틀먼트(`AiToolKey.MarketingVideo`)는 하나다.
- **채널/에셋/세트는 버전별로 가르지 않는다**(원칙 4).
